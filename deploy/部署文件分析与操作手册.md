## 一、结论速览

| 问题 | 结论 |
|---|---|
| 部署文件在哪 | 只有一层：**根 `docker-compose.yml` + `deploy/`**（应用容器化）。原 `devops/`（基础设施 / CI/CD / K8s / 监控）已于 2026-10-18 移除 |
| 最快跑起来 | 3 条命令：`cp backend/.env.example backend/.env` → `docker compose build` → `docker compose up -d`，访问 `http://localhost:8080` |
| 对外端口 | 只有一个：**8080（Nginx）**。后端 8000 只在 compose 内网暴露，不映射到宿主机 |
| 需要数据库容器吗 | **默认不需要**。向量库是嵌入式 Milvus Lite（单文件 `data/milvus.db`），任务是 JSON 文件；只有切到「独立 Milvus 集群」时才会多起 etcd + minio + milvus 三个容器 |
| 数据会不会丢 | 默认落在命名卷 `agent-data` → `docker compose down` 不丢，`down -v` 会丢 |
| 生产推荐路线 | **L1 单机容器化**（当前唯一形态）：构建 → 启动 → 健康检查 → 数据卷备份 |
| 有没有坑 | 前端已收敛为唯一实现 `frontend/web/vue-element-plus`，`deploy/frontend/Dockerfile` 的 COPY 路径**已修正**，原多前端相关的偏差已闭环，详见 [第十节](#十当前代码结构与部署文件的剩余偏差) |

## 三、目录与文件层级结构（逐文件说明）

### 3.1 第 1 层：应用容器化

```
agent/
├── docker-compose.yml                  ★ 主编排：backend + web(nginx)，对外 8080
├── .dockerignore                          构建上下文裁剪（排除 node_modules/.venv/data/.env/dist…）
├── .gitignore                             忽略 .env / dist / node_modules / __pycache__
├── README.md                              仓库总览与快速开始
├── backend/
│   ├── Dockerfile                       ⚠ 遗留旧镜像文件（未被 compose 引用，见第十节）
│   ├── requirements.txt                   pip 依赖清单（镜像构建只 COPY 这一个 + pyproject）
│   ├── pyproject.toml                     Python 包元数据（requires-python >=3.10,<3.13）
│   ├── .env.example                     ★ 密钥模板（必须复制为 .env 并填写）
│   └── .env                             ★ 实际密钥（gitignore，由 compose 的 env_file 注入）
├── frontend/                              默认前端（唯一实现）
│   ├── web/vue-element-plus/           ★ 源码：Vue 3 + TS + Vite + Element Plus + Pinia + Router
│   ├── docs/                               接口契约 / SSE 协议 / 设计 Token
│   ├── scripts/build-frontend.mjs       ★ 构建默认前端并拷贝到 frontend/dist
│   ├── scripts/smoke.mjs                   后端 35 端点端到端冒烟
│   └── dist/                              【生成物】后端 StaticFiles / nginx 托管的静态产物
├── doc/                                  文档集（analysis / knowledge / deployment）
└── deploy/
    ├── README.md                          第 1 层的完整说明文档
    ├── 部署文件分析与操作手册.md          ★ 本文：文件全景 + 两条路线 + 验收清单 + 排错
    ├── backend/
    │   ├── Dockerfile                   ★ 后端镜像：python:3.11-slim + 依赖 + playwright chromium
    │   └── entrypoint.sh                ★ 启动脚本：建 data 子目录 → 可选 RAG 入库 → exec uvicorn
    ├── frontend/
    │   └── Dockerfile                   ★ 前端镜像：node:22-alpine 构建 vue-element-plus → nginx:1.27-alpine 运行
    ├── nginx/
    │   ├── nginx.conf                     主配置（gzip / 日志 / client_max_body_size 100m）
    │   └── conf.d/agent.conf   ★ 站点配置：静态直出 + /api 反代 + SSE 关缓冲 + SPA 回退
    └── docker-compose.milvus.yml          可选覆盖文件：etcd + minio + milvus standalone
```

| 文件 | 关键点 |
|---|---|
| `docker-compose.yml` | 项目名 `agent`；服务 `backend`（`expose 8000`，不映射宿主）+ `web`（`${HOST_HTTP_PORT:-8080}:80`）；网络 `agent-net`；卷 `agent-data:/app/data`；`web` 依赖 `backend` 的 `service_healthy` |
| `deploy/backend/Dockerfile` | 构建参数 `PIP_INDEX_URL` / `APT_MIRROR` / `INSTALL_PLAYWRIGHT`；分层先装依赖再拷代码以复用缓存；内置 HEALTHCHECK 打 `/api/v1/health`；`ENTRYPOINT entrypoint.sh` + `CMD uvicorn` |
| `deploy/backend/entrypoint.sh` | `RUN_INGEST=true` 时启动时自动跑 `python -m scripts.ingest_data`；末尾 `exec "$@"` 保证 PID 1 收信号优雅退出 |
| `deploy/frontend/Dockerfile` | 多阶段：`npm ci` → `npm run build`（构建 `frontend/web/vue-element-plus`）→ 产物拷进 nginx 的 `/usr/share/nginx/html`；运行镜像只有 nginx + dist（当前实测约 74MB） |
| `deploy/nginx/conf.d/agent.conf` | `resolver 127.0.0.11` + 变量式 `proxy_pass`（backend 重建换 IP 也能解析）；`proxy_buffering off` / `gzip off` / `X-Accel-Buffering: no` / 3600s 超时（SSE 必须）；`/assets/` 7 天强缓存；`location /` SPA 回退；`/nginx-healthz` 自检 |
| `deploy/docker-compose.milvus.yml` | 追加 `milvus-etcd`(2379) / `milvus-minio`(9000) / `milvus`(19530)，并把 backend 的 `MILVUS_DB_PATH` 覆盖为 `http://milvus:19530` |
| `.dockerignore` | 排除 `backend/.env`、`.env`、`**/dist`、`**/node_modules`、`backend/data/*`、`doc`、`docs` —— **注意它同时排除了 `dist`，会影响第十节的修复方案 A** |

## 四、部署形态与运行时架构

### 4.1 形态 A：Docker Compose 单机（默认、推荐先跑通这个）

```
浏览器 ──► http://<host>:8080/  ──►  agent-web (nginx:1.27-alpine)
                                       ├─ / , /assets/*      → Vue 构建产物（静态直出）
                                       ├─ /api/v1/*          → backend:8000（SSE：proxy_buffering off）
                                       ├─ /docs,/redoc,openapi.json → backend:8000
                                       └─ /nginx-healthz     → 自身自检
                                              │ compose 内网 agent-net
                                              ▼
                                     agent-backend (python:3.11-slim)
                                       uvicorn app.main:app 0.0.0.0:8000（单 worker）
                                              │ /app/data
                                              ▼
                                     命名卷 agent-data
                                       ├─ milvus.db      （Milvus Lite 向量库）
                                       ├─ research/      （深度研究任务 tasks.json + 报告 md）
                                       └─ outputs|uploads|pdf|logs|browser_data
```

关键设计决策（来自 `deploy/README.md`）：

| 决策 | 选择 | 理由 |
|---|---|---|
| 前端容器 | 多阶段构建（node 构建 → nginx 运行） | 运行镜像不含 node_modules，体积小、启动快 |
| 静态资源由谁托管 | **Nginx，不由 FastAPI** | 容器内不存在 `frontend/dist`，`app/main.py` 自动降级为纯 API 服务，职责分离 |
| 对外端口 | 只暴露 8080，backend 仅 `expose` | 单一入口，便于加 TLS/限流，后端不直接对外 |
| SSE 流式 | `proxy_buffering off` + `gzip off` + `X-Accel-Buffering: no` + 3600s 超时 | 否则前端收不到逐字流式，会一次性吐出或超时断开 |
| 服务发现 | `resolver 127.0.0.11` + 变量式 `proxy_pass` | backend 容器重建换 IP 时不会「启动即 502」 |
| 启动顺序 | backend `healthcheck` 打 `/api/v1/health` + web `depends_on: service_healthy` | 保证 nginx 起来时后端已就绪 |
| 密钥 | compose 的 `env_file: ./backend/.env` | 密钥不进镜像层，镜像可安全分发 |
| 后端 worker 数 | **固定 1** | `ResearchManager` 是进程内线程池 + 内存任务字典，多 worker 会导致任务状态不一致 |

> ⚠️ **扩容硬约束**：Milvus Lite 是进程内嵌的单文件向量库，多副本会各写各的 `milvus.db`。
> 要水平扩容必须先切到外部 Milvus（`MILVUS_DB_PATH=http://milvus:19530`）。

## 五、部署前置条件

### 5.1 软件环境

| 项 | 要求 | 备注 |
|---|---|---|
| Docker | ≥ 27（实测 29.5.2） | 需含 Compose v2（`docker compose version`） |
| Docker Compose | ≥ v2.20 | 项目用到 `env_file: path/required`、`pull_policy` 等较新语法 |
| Docker Desktop 内存 | ≥ 12 GB（实测 15.5 GB） | 后端镜像约 3.96GB，且构建时要编译 C 扩展 |
| 磁盘 | ≥ 20 GB 可用 | 镜像层（后端实测 ≈3.96 GB，主要来自 Chromium 与 chromadb/langchain）+ 数据卷 |
| Python | 3.10 ~ 3.12（镜像内 3.11） | 仅开发态直启需要本机 Python |
| Node | ≥ 20（镜像内 node:22-alpine） | 仅本地构建前端或跑 `build-frontend.mjs` 时需要 |

### 5.2 密钥（决定哪些能力链可用）

复制模板并填写：

```bash
cp backend/.env.example backend/.env
```

| 变量 | 用途 | 是否必需 |
|---|---|---|
| `DASHSCOPE_API_KEY` | Agent 主链路（Skill / MCP / 代码执行）、RAG 的 embedding | **必需** |
| `LLM_API_KEY` | RAG 链路（DeepSeek 兼容） | **必需**（RAG 要用） |
| `BOCHA_API_KEY` 或 `SERPER_API_KEY` | 深度研究（第 5 链）检索引擎，二选一 | 深度研究必需 |
| `OPENAI_API_KEY` | Web Research 链路 | 可选 |
| `SERPER_API_KEY` | MCP 搜索 Server | 可选 |
| `GAODE_API_KEY` | 高德 MCP | 可选 |

> 未配置 `DASHSCOPE_API_KEY` 时服务仍能启动（健康检查 200），但 SSE 会返回
> `error: 未配置 DASHSCOPE_API_KEY`。这是排查"页面能开但对话报错"的第一检查项。

### 5.3 端口占用自查

```bash
for p in 80 3000 3001 5000 8080 8081 8082 8090 9090 9093; do
  printf '%-6s ' "$p"; lsof -nP -iTCP:$p -sTCP:LISTEN >/dev/null 2>&1 && echo OCCUPIED || echo free
done
```

完整端口表见 [附录 A](#附录-a端口总表)。

### 5.4 国内网络源适配（构建成败的关键）

| 用途 | 默认源 | 国内可用替代 | 传入方式 |
|---|---|---|---|
| Debian apt | `deb.debian.org` | `mirrors.ustc.edu.cn` | `--build-arg APT_MIRROR=`（需手动加到 compose 的 args） |
| pip | `pypi.org` | `pypi.tuna.tsinghua.edu.cn/simple` | `PIP_INDEX_URL=… docker compose build` |
| npm | `registry.npmjs.org` | `registry.npmmirror.com` | `NPM_REGISTRY=… docker compose build` |

> 经验：**构建卡住先换源，不要重试**。

## 六、操作步骤（核心）

> 两条路线：**开发联调 → 6.1**；**要一个能对外服务的系统 → 6.2**。
> 6.3 是可选开关（切换到独立 Milvus 集群），与 6.2 并列而非叠加。

### 6.1 路线 L0：开发态直启（不打包）

适合改代码时联调，不适合对外服务。

```bash
# 终端 1：后端（绑定地址与端口只由 .env 的 HOST/PORT 决定，P1-10）
cd backend
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
cp .env.example .env                     # 填写密钥；HOST/PORT 决定绑定地址与端口
./.venv/bin/python -m scripts.ingest_data            # 可选：RAG 入库（需要 PDF + API Key）
./.venv/bin/python -m app.main                        # 统一入口（读 .env 的 HOST/PORT）

# 终端 2：前端开发服务器（vite 的 /api 代理指向 .env 的 PORT）
cd frontend/web/vue-element-plus
npm install
npm run dev                              # http://localhost:5173
```

> **本机形态默认只监听回环**（`HOST=127.0.0.1`）。需要让局域网访问时，
> 在 `.env` 里**显式**设 `HOST=0.0.0.0`——不要再用命令行 `--host` 覆盖，
> 否则配置与实际绑定会脱节（这正是 P1-10 修复的问题）。

单端口形态（由后端托管静态资源）：

```bash
node frontend/scripts/build-frontend.mjs  # 构建默认前端 → 拷贝到 frontend/dist
cd backend && ./.venv/bin/python -m app.main
# 访问 http://127.0.0.1:<PORT>/
```

### 6.2 路线 L1：容器化单机部署（生产形态）

**三步启动：**

```bash
cd agent                        # docker-compose.yml 所在目录

# ① 准备密钥
cp backend/.env.example backend/.env
vim backend/.env                         # 至少填 DASHSCOPE_API_KEY / LLM_API_KEY

# ② 构建（首次较慢，主要耗时在 playwright chromium 与 chromadb 编译）
docker compose build
#   国内加速可选：
#   PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
#   NPM_REGISTRY=https://registry.npmmirror.com \
#   INSTALL_PLAYWRIGHT=false docker compose build

# ③ 启动
docker compose up -d
docker compose ps                        # 期望两个服务都是 Up (healthy)
```

**国内网络/低配机器的推荐构建参数：**

| 参数 | 默认 | 建议 |
|---|---|---|
| `INSTALL_PLAYWRIGHT` | `true` | 不用小红书 MCP Server 时设 `false`，**显著缩短构建时间并减小约 1GB 体积** |
| `PIP_INDEX_URL` | pypi.org | 国内改清华源 |
| `NPM_REGISTRY` | npmjs.org | 国内改 npmmirror |

**访问与冒烟：**

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/                  # 200 前端
curl -s http://localhost:8080/api/v1/health                                      # {"status":"ok",...}
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/nginx-healthz      # 200
curl -N -X POST http://localhost:8080/api/v1/agent/run -H 'Content-Type: application/json' \
     -d '{"message":"你好"}'                                                      # SSE 应逐字输出
open http://localhost:8080/docs                                                  # Swagger
```

**修改对外端口：**

```bash
HOST_HTTP_PORT=80 docker compose up -d
```

**初始化 RAG 向量库（需要 PDF + API Key）：**

```bash
# PDF 放 backend/data/pdf（宿主机），再执行：
docker compose exec backend python -m scripts.ingest_data
# 或让容器启动时自动入库：在 compose 里把 RUN_INGEST 设为 "true"
```

**提交一个深度研究任务（验证第 5 链）：**

```bash
curl -X POST http://127.0.0.1:8080/api/v1/research \
  -H 'Content-Type: application/json' \
  -d '{"task":"2026 年新能源汽车市场竞争格局","max_workers":4,"max_iterations":3}'
curl http://127.0.0.1:8080/api/v1/research/<task_id>
curl -N http://127.0.0.1:8080/api/v1/research/<task_id>/stream
```

### 6.3 可选开关：切换到独立 Milvus 集群

默认用嵌入式 Milvus Lite（零额外容器）。需要多容器共享向量库 / 独立扩容 / 接 attu 时：

```bash
docker compose -f docker-compose.yml -f deploy/docker-compose.milvus.yml up -d
# 该命令额外拉起 milvus-etcd(2379) / milvus-minio(9000) / milvus(19530)
# 并把 backend 的 MILVUS_DB_PATH 覆盖为 http://milvus:19530

# 重要：原 milvus.db 的数据不会自动迁移，需要重新入库
docker compose exec backend python -m scripts.ingest_data
```

## 七、验收清单

| # | 验收项 | 期望 | 命令 |
|---|---|---|---|
| 1 | 镜像构建 | 成功 | `docker compose build` |
| 2 | 容器健康 | 两个 `Up (healthy)` | `docker compose ps` |
| 3 | 前端首页 | 200 `text/html` | `curl -o /dev/null -w '%{http_code}' http://localhost:8080/` |
| 4 | 静态资源 | 200 + 7d 缓存头 | `curl -I http://localhost:8080/assets/index-*.js` |
| 5 | SPA 回退 | 深路径返回 index.html | `curl -o /dev/null -w '%{http_code}' http://localhost:8080/some/deep/route` |
| 6 | 后端健康 | `{"status":"ok","skills_loaded":6}` | `curl -s http://localhost:8080/api/v1/health` |
| 7 | SSE 反代 | `text/event-stream` + 逐字到达 | `curl -N -X POST http://localhost:8080/api/v1/agent/run …` |
| 8 | 未知 API 路径 | 404（由后端返回，不落到 SPA 回退） | `curl -o /dev/null -w '%{http_code}' http://localhost:8080/api/v1/nope` |
| 9 | 数据持久化 | 重启后 milvus.db 与 outputs 完好 | `docker compose restart backend` 后检查 |
| 10 | 服务发现 | backend 重建换 IP 后仍可代理 | `docker compose restart backend` 后再请求 `/api/v1/health` |
| 11 | Swagger | 200 | `curl -o /dev/null -w '%{http_code}' http://localhost:8080/docs` |

## 九、排错速查

| 现象 | 原因 / 处理 |
|---|---|
| `docker compose up` 报找不到 `./backend/.env` | 复制 `backend/.env.example` 为 `backend/.env` |
| 构建报 `failed to resolve … docker/dockerfile:1.7` | Dockerfile 里不要写 `# syntax=` 指令（本机加速器拉不到 BuildKit frontend） |
| `Head "https://<mirror>/v2/.../manifests/...": EOF` | 镜像加速器缺少该仓库/标签，换加速器或去掉 `registry-mirrors` 后重试 |
| 构建极慢 / playwright 下载超时 | `INSTALL_PLAYWRIGHT=false docker compose build` |
| 访问 `/` 正常但 `/api/v1/health` 502 | backend 未 healthy；`docker compose logs backend` |
| 页面能开但对话报错 `未配置 DASHSCOPE_API_KEY` | `.env` 未填密钥，或改了 `.env` 没 `docker compose up -d` 重建容器 |
| 流式回答一次性出现 | Nginx 缓冲；确认用的是 `deploy/nginx/conf.d/agent.conf`（`proxy_buffering off`） |
| 研究报告重启后消失 | 数据卷被删（`down -v`）或未挂载；`docker volume inspect agent-data` |
| 端口 8080 被占用 | `HOST_HTTP_PORT=8081 docker compose up -d` |
| 深度研究提交即失败 | 未配置 `BOCHA_API_KEY` 或 `SERPER_API_KEY`（设计如此，会立即失败并给出原因） |
| 容器内时间不对 | compose 已注入 `TZ=Asia/Shanghai`，镜像内也装了 tzdata |

## 十、当前代码结构与部署文件的剩余偏差

分析过程中发现的**实际偏差**，按影响程度排序。

> **2026-10-19 更新**：原 5 条偏差中的 **#1（前端 Dockerfile COPY 路径失效）** 与
> **#3（根 README 前端结构过期）** 已随「前端收敛为唯一实现 `frontend/web/vue-element-plus`」一并修复；
> #5 随方案 B 的落地不再适用。**当前仍需关注 2 条：#2 与 #4。**

### ✅ 1.（已修复）`deploy/frontend/Dockerfile` 的 COPY 路径

原问题：`frontend/` 曾被重构为多平台实现集合，Dockerfile 仍写 `COPY frontend/package.json ./`，导致构建失败。

当前状态：前端已收敛为唯一实现，Dockerfile 固定构建该目录，路径与实际一致：

```dockerfile
COPY frontend/web/vue-element-plus/package.json frontend/web/vue-element-plus/package-lock.json ./
RUN npm ci --no-audit --no-fund --registry="${NPM_REGISTRY}"
COPY frontend/web/vue-element-plus/ ./
RUN npm run build
```

`docker-compose.yml` 的 `web.build.args` 只保留 `NPM_REGISTRY`；不再有 `FRONTEND_APP` /
`WEB_TAG` / `frontend/active` 这套「多实现切换」开关。

### 2. `backend/Dockerfile` 是遗留文件，与 `deploy/backend/Dockerfile` 重复且已过时

- 未被任何编排引用（compose 用的是 `deploy/backend/Dockerfile`）；
- 依赖写死在 Dockerfile 里（与 `requirements.txt` 双份维护，易漂移）；
- `COPY pyproject.toml ./` 后并未使用，且无 `entrypoint.sh`、无 `TZ`、无分层缓存优化。
- **建议**：删除，或至少在文件头注明 "DEPRECATED, see deploy/backend/Dockerfile"。

### 3. `deploy/backend/Dockerfile` 支持 `APT_MIRROR`，但 compose 未暴露该 arg

`deploy/backend/Dockerfile` 支持 `APT_MIRROR`（Debian 源），但 `docker-compose.yml` 的
`backend.build.args` 只声明了 `PIP_INDEX_URL` 与 `INSTALL_PLAYWRIGHT`。
国内环境想改 apt 源需手动加一行：

```yaml
      args:
        APT_MIRROR: "${APT_MIRROR:-}"
```

### 4. `.dockerignore` 排除了 `**/dist`

当前前端在**镜像内从源码构建**（见 #1），`frontend/dist` 不需要进构建上下文，
因此 `**/dist` 保持排除是正确的。

若将来改为「宿主机预构建 + 镜像只做 nginx 托管」，则必须从 `.dockerignore` 移除 `**/dist`，
否则 `COPY frontend/dist` 会拿到空目录。
