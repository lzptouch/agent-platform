## 1. 设计目标与约束

### 1.1 功能性需求

| 需求编号 | 描述 | 优先级 |
|----------|------|--------|
| F1 | 接受用户自然语言查询，自动检索并生成带引用的回答 | P0 |
| F2 | 支持中英文查询自动识别（Pipeline 版 `serper_service.py:26`） | P0 |
| F3 | 支持 Pipeline 极简版与 Notebook 工业级两套实现 | P0 |
| F4 | 支持本地文档检索（Notebook 版 Milvus + BGE-M3） | P1 |
| F5 | 支持 LLM 流式输出，提升长答案体验 | P1 |
| F6 | 提供 RAG 引用追溯能力（reference locator） | P1 |
| F7 | 多 URL 并发抓取，提升端到端速度 | P2 |

### 1.2 非功能性需求

| 维度 | 目标 | 实际指标 |
|------|------|----------|
| 端到端耗时 | 简单查询 < 30s | 单次 ~10~20s |
| 并发能力 | 10 URL 并行抓取 | `threading.Thread` × 10 |
| 检索召回 | top-20（Pipeline）/ 全集合（Notebook） | TOP_K=20, 50 batch insert |
| 错误恢复 | 单 URL 抓取失败不影响其他 | 异常隔离 + 长度阈值过滤 |
| 可观测性 | 全流程打印 | `print` 日志 |
| 可扩展性 | 模块独立，可替换嵌入/检索/LLM | 各模块均为类 |

## 2. 关键设计决策（Decision Records）

### 决策 1：采用 Chroma 内存向量库（而非 Milvus/FAISS/Pinecone）

**问题**：Pipeline 版需要快速验证 RAG 思路，向量库选型是什么？

**选项**：
- A. Chroma（**Pipeline 最终选择**）
- B. FAISS（Facebook）
- C. Milvus
- D. Pinecone（云）

**理由**：
- Chroma 是 LangChain 原生集成的内存向量库，`pip install chromadb` 即可用，无外部服务；
- 本项目 Pipeline 版每次查询都"重新创建"向量库（`retrieval.py:47-50`），无需持久化；
- Notebook 版用 Milvus Lite（本地嵌入式 Milvus），满足"工业级混合检索"的演示需求。

**佐证**：
- [官方] Chroma — `https://docs.trychroma.com/`
- [官方] LangChain Vector Stores

### 决策 2：采用 BGE-M3 同时输出稠密+稀疏向量（而非单向量）

**问题**：Notebook 版如何兼顾语义匹配与关键词精确命中？

**选项**：
- A. 仅稠密向量（BGE-large / OpenAI Embedding）
- B. BGE-M3 稠密+稀疏（**Notebook 最终选择**）
- C. BM25 + 向量双库

**理由**：
- BGE-M3 是首个支持"多语言（Multi-Lingual）+ 多功能（Multi-Functionality）+ 多粒度（Multi-Granularity）"的 Embedding，单次推理同时输出稠密与稀疏（`https://arxiv.org/abs/2402.03216`）；
- 单一模型同时承担两种召回，避免维护两套模型与索引；
- Notebook cell 20 `WeightedRanker(sparse_weight=0.7, dense_weight=1.0)` 实现加权融合，sparse 权重略低以让语义匹配占主导。

**佐证**：
- [论文] BGE M3-Embedding — Chen et al., 2024
- [官方] Milvus Hybrid Search

### 决策 3：采用多线程 Thread（而非 ProcessPool / asyncio）

**问题**：如何并行抓取多个 URL？

**选项对比**：

| 维度 | threading.Thread | multiprocessing.Process | asyncio |
|------|------------------|-------------------------|---------|
| 启动开销 | 极低 | 高（pickle） | 低 |
| 共享内存 | 共享 | 独立 | 共享 |
| CPU 密集 | 受 GIL | 真并行 | 单线程 |
| I/O 密集 | 真实并发 | 真实并发 | 真实并发 |
| 与 requests 兼容 | 直接兼容 | 需 fork | 需 aiohttp |

**理由**：
- URL 抓取是 I/O 密集型任务，`threading.Thread` 在 GIL 释放时真实并发（`fetch_web_content.py:51`）；
- 与现有 `requests` 库无缝集成，避免引入异步生态复杂度；
- 限制：实际并发数受限于 Serper/目标站点的速率限制。

**佐证**：
- [官方] threading — Python Docs

### 决策 4：采用 Prompt 中的引用规则（而非后处理强制抽取）

**问题**：如何让 LLM 主动输出可追溯的引用？

**选项**：
- A. Prompt 强约束 + 事后正则解析（**最终选择**）
- B. 后处理 LLM 输出做对齐
- C. Function Calling 强制结构化

**理由**：
- Prompt 约束 + 正则解析（`locate_reference.py:35-44`）是兼容性最强的方案，不依赖模型是否支持 Function Calling；
- 后处理对齐成本高、效果不稳定；
- 副作用：偶尔 LLM 输出不规范引用，需正则容错（`locate_reference.py:17` 的 `-1` 异常返回）。

**佐证**：
- [官方] Prompt Engineering Guide
- [博客] How Perplexity builds citations — Perplexity AI Blog

### 决策 5：采用 sentence-transformers MiniLM（而非 OpenAI Embedding）

**问题**：Pipeline 版的嵌入模型选什么？

**选项**：
- A. `sentence-transformers/all-MiniLM-L6-v2`（**Pipeline 最终选择**）
- B. OpenAI `text-embedding-3-small`
- C. BGE-base / BGE-large

**理由**：
- MiniLM-L6-v2 模型小（80MB）、速度快、本地推理无 API 成本；
- LangChain 原生集成 `SentenceTransformerEmbeddings`（`retrieval.py:43`）；
- 适用于 Pipeline 版的"快速本地 demo"场景；
- 局限：英文为主，对中文支持一般（这是 Notebook 版用 BGE-M3 的原因）。

**佐证**：
- [官方] sentence-transformers/all-MiniLM-L6-v2 — Hugging Face

### 决策 6：采用 LlamaParse 解析 PDF（Notebook）

**问题**：Notebook 演示如何把 PDF 产品手册转为结构化文本？

**选项**：
- A. `PyPDF2` / `pdfplumber`
- B. LlamaParse（**Notebook 最终选择**）
- C. 自研 PDF 抽取

**理由**：
- LlamaParse 是 LlamaIndex 官方云服务，对表格 / 多栏 PDF 解析质量最高（`https://docs.llamaindex.ai/en/stable/llama_cloud/llama_parse/`）；
- Notebook cell 5-6 演示端到端 PDF → Markdown → 切分 → 向量化的工业流程；
- 限制：需 `api_key`，且为云服务。

**佐证**：
- [官方] LlamaParse — LlamaIndex

### 决策 7：采用 Plan/Memory/Tool/Answer 四模块 Agent

**问题**：Notebook 版如何让销售助手"会规划、会查资料、会整理记忆、会回答"？

**选项**：
- A. 单轮 RAG（问→查→答）
- B. Plan/Memory/Tool/Answer 四模块（**最终选择**）
- C. LangChain Agent / LangGraph

**理由**：
- 四模块结构清晰对应 ReAct 范式（Reason + Act）的扩展；
- Plan 让 LLM 自主决定"本地 vs 网络搜索"，比硬编码规则更灵活；
- Memory 累积多轮证据，避免重复检索；
- Tool 把"本地文档搜索"与"网络搜索"作为两个 Tool，LLM 自主选择；
- 不引入 LangChain 黑盒，便于教学与改写。

**佐证**：
- [博客] LLM Powered Autonomous Agents — Lilian Weng
- [论文] ReAct: Synergizing Reasoning and Acting in Language Models — Yao et al., ICLR 2023

## 3. 模块划分原则

### 3.1 单一职责原则

每个模块只负责一件事：

| 模块 | 唯一职责 |
|------|----------|
| `serper_service.py` | 封装搜索 API |
| `web_crawler.py` | 单 URL 抓取与正文提取 |
| `fetch_web_content.py` | 搜索+并发抓取的胶水层 |
| `retrieval.py` | 向量化与 top-k 检索 |
| `llm_answer.py` | 组装 Prompt + LLM 生成 |
| `locate_reference.py` | 解析答案中的引用 |
| `config.yaml` | 集中配置 |

### 3.2 依赖倒置原则

- 各模块只通过"输入参数 + 返回值"交互，无强耦合；
- 替换实现（如换嵌入模型）只需修改 `__init__` 中的常量。

### 3.3 配置与代码分离

- 所有 API Key、Prompt 模板、模型名集中在 `config/config.yaml`；
- Notebook 中的 API Key 也在 cell 顶部集中（虽然演示用）。

## 4. 数据模型与状态设计

### 4.1 Pipeline 状态机

```
init(query)
   │
   ├─ fetch() ──→ (ordered_contents, serper_response)
   │
   ├─ retrieve_embeddings(contents, links, query)
   │   ──→ List[Document] (top-20)
   │
   ├─ _format_reference(docs, link_list) (TOP_K=10)
   │   ──→ formatted_reference 字符串
   │
   ├─ get_answer(query, formatted, ...)
   │   ──→ AIMessage (gpt-4o 含 [n])
   │
   └─ locate_source(answer, serper_response)
       ──→ reference_cards JSON
```

### 4.2 Notebook 状态机

```
init(memory_global=[])
   │
   ├─ agent_plan(query)    ──→ [plan_items] (JSON)
   │
   ├─ for plan_item in plan:
   │     ├─ tool = "本地文档搜索" → retrieval(prompt) → docs
   │     └─ tool = "网络搜索" → web_search(prompt) → docs
   │     └─ memory_global.extend(docs)
   │
   └─ final_answer(memory_global, user_query)
       ──→ 流式 reasoning_content + content
```

### 4.3 关键数据类

| 数据结构 | 位置 | 字段摘要 |
|----------|------|----------|
| `web_contents` | `fetch_web_content.py:10` | `[{url, content}]` 列表 |
| `error_urls` | `fetch_web_content.py:11` | 抓取失败的 URL 列表 |
| `serper_response` | `serper_service.py:56-63` | `{query, language, count, titles, links, snippets}` |
| `Chroma Document` | `retrieval.py:38-39` | `{page_content, metadata:{url}}` |
| `reference_cards` | `locate_reference.py:77-80` | `[{index, sent, url, source, titles, snippets}]` |

## 5. 关键技术对比与选型

### 5.1 搜索 API 选型对比

| 搜索 API | 中文质量 | 合规性 | 返回字段 | 选型 |
|----------|----------|--------|----------|------|
| Google Serper | 高（Google 后端） | 需海外网络 | title/link/snippet | ✓ |
| Tavily | 中 | OK | 摘要 + 来源 | ✗ |
| Bing Search | 中 | OK | 标准 | ✗ |
| DuckDuckGo | 低 | OK | 简化 | ✗ |

**结论**：Serper.dev（`https://serper.dev/api`），原因：Google 搜索质量最高、价格便宜、返回字段完整。

### 5.2 嵌入模型对比

| 模型 | 维度 | 多语言 | 同时输出稀疏 | 选型 |
|------|------|--------|--------------|------|
| `all-MiniLM-L6-v2` | 384 | 弱 | ❌ | ✓ Pipeline |
| OpenAI `text-embedding-3-small` | 1536 | 中 | ❌ | ✗ |
| `bge-large-zh-v1.5` | 1024 | 中 | ❌ | ✗ |
| `BAAI/bge-m3` | 1024 | 强（100+ 语种） | ✅ | ✓ Notebook |

**结论**：Pipeline 用 MiniLM（轻量），Notebook 用 BGE-M3（多语言+稀疏）。

### 5.3 向量库对比

| 向量库 | 持久化 | 混合检索 | 部署复杂度 | 选型 |
|--------|--------|----------|------------|------|
| Chroma | 文件 | ❌ | 极低 | ✓ Pipeline |
| FAISS | 文件 | ❌ | 低 | ✗ |
| Milvus Lite | 文件 | ✅ | 中 | ✓ Notebook |
| Pinecone | 云 | ✅ | 低 | ✗ |

**结论**：Pipeline 用 Chroma（最简），Notebook 用 Milvus Lite（混合检索+本地）。

## 6. 接口设计原则

1. **最小惊讶原则**：类名 `WebContentFetcher` / `GPTAnswer` / `ReferenceLocator` 直接表达意图。
2. **可选参数优先**：所有可调参数（TOP_K、chunk_size）有默认值。
3. **错误显式化**：抓取失败 → URL 进入 `error_urls`；引用解析失败 → 返回 -1（`locate_reference.py:17`）。
4. **进度可观测**：Pipeline 各步骤通过 `print` 输出耗时与状态；Notebook cell 间有清晰的 Markdown 说明。

## 7. 错误处理与降级策略

| 错误类型 | 处理策略 | 代码位置 |
|----------|----------|----------|
| Serper API 失败 | `requests.request` 抛出 → 顶层异常 | `serper_service.py:32` |
| 单 URL 抓取失败 | 长度< 300 或异常 → 进入 `error_urls`，不影响其他 | `fetch_web_content.py:30,39` |
| 内容过短 | rule=0 → rule=1 升级抓取 | `fetch_web_content.py:26-28` |
| LLM 输出无引用 | `split('\nReferences:')` 返回 ≠ 2 → 返回 -1 | `locate_reference.py:16-17` |
| Chroma 空结果 | `retriever.get_relevant_documents` 返回空 | `retrieval.py:55` |
| PDF 文件 | 直接跳过（不下载） | `web_crawler.py:34-36` |

## 9. 安全设计

| 风险点 | 设计方案 |
|--------|----------|
| 恶意查询 | 当前无内容审核；建议接入第三方审查 |
| API Key 泄露 | Pipeline 通过 `config.yaml` 集中；Notebook 应使用环境变量 |
| Prompt 注入 | LLM 输出用正则解析，避免直接执行 |
| 抓取滥用 | 8 秒超时；< 300 字符过滤；尊重 robots.txt（未实现） |
| PDF 滥用 | 跳过 `.pdf` URL 避免下载大文件 |

## 10. 本章设计原理与依据

### 原理 1：最小惊讶原则（Principle of Least Astonishment）

- **核心思想**：API 设计应符合用户已有认知，降低学习成本。
- **在本项目中的体现**：`WebContentFetcher(query).fetch()` 命名直观；`GPTAnswer().get_answer(query, docs, ...)` 参数顺序符合"用 docs 回答 query"的语义。
- **为什么有效**：降低使用门槛，让代码读起来像文档。

### 原理 2：防御性编程（Defensive Programming）

- **核心思想**：假设任何外部输入都可能出错，代码应主动检测并优雅降级。
- **在本项目中的体现**：每个 URL 抓取都用 `try/except`；LLM 输出格式异常时 `locate_source` 返回 -1。
- **为什么有效**：网络不稳定场景下，整体可用性显著提升。

### 原理 3：可观测性优先（Observability-Driven Design）

- **核心思想**：系统在设计阶段就内置"对外部可见"的进度与状态。
- **在本项目中的体现**：每个 Thread 打印 `Starting/Completed`；Notebook 每个 cell 有 Markdown 标题。
- **为什么有效**：RAG 流水线涉及多个外部 API，调试时必须有进度反馈。

### 原理 4：单一可观察状态源（Single Source of Truth）

- **核心思想**：所有状态集中在一个对象，避免分散维护导致的不一致。
- **在本项目中的体现**：Pipeline 用 `serper_response` 字典贯穿"搜索→抓取→引用定位"全流程；Notebook 用 `memory_global` 列表贯穿 Plan/Tool/Answer。

### 原理 5：配置外置与运行时可调

- **核心思想**：可变参数（API Key、Prompt、模型名）应在配置文件中，便于运行时调整而无需改代码。
- **在本项目中的体现**：`config.yaml` 集中 `openai_api_key`、`serper_api_key`、`model_name`、`template`（Prompt）。

### 原理 6：依赖注入与可测试性

- **核心思想**：通过参数注入依赖，而非内部硬编码。
- **在本项目中的体现**：`WebContentFetcher(query)` 通过构造函数注入查询；`SentenceTransformerEmbeddings(model_name=...)` 注入模型名。

### 原理 7：迭代收敛保证

- **核心思想**：任何循环都必须有明确的终止条件。
- **在本项目中的体现**：
  - Thread 池 `for thread in threads: thread.join()`（`fetch_web_content.py:57`）
  - URL 抓取两段式（rule=0/1）确保不会无限重试
  - Notebook Plan 阶段 LLM 输出 JSON 列表，单轮决定工具序列
