## 1. 端到端主流程

### 1.1 主流程文字描述

WebResearch 的端到端流程（以 Pipeline 版为例）包含 5 个阶段：

1. **搜索**（Serper API）：根据 query 调用 Google 搜索，获取 top-10 organic 结果
2. **并发抓取**（N × Thread）：每 URL 启动一个 Thread，两段式提取主内容
3. **向量化与召回**（Chroma + MiniLM）：切分 → 向量化 → top-20 召回
4. **LLM 生成**（ChatOpenAI）：用 top-10 文档 + Prompt 模板生成含 `[n]` 引用的答案
5. **引用定位**（正则解析）：从答案中解析引用，反向匹配 serper 元数据

### 1.3 主流程核心步骤详解

#### 步骤 1：搜索（`SerperClient.serper`）

**做什么**：
1. 构造请求参数 `{"q": query, "page": 2}`
2. 中文查询自动追加 `{"gl": "cn", "hl": "zh-cn"}`
3. POST 到 `https://google.serper.dev/search`
4. 返回 organic 数组（通常 10 条）

**为什么这么做**：
- `page=2`：Serper 单页固定返回 10 条；
- `gl/hl`：让 Google 返回目标地域的本地化结果（`serper_service.py:27`）；
- 异常透传：失败由上层捕获。

**输入 → 输出**：

```
Input:  "介绍一下小米汽车"
Output: {
    "organic": [
        {"title": "...", "link": "https://...", "snippet": "..."},
        ...
    ],
    "searchParameters": {"q": "...", "gl": "cn", "hl": "zh-cn"},
}
```

#### 步骤 2：并发抓取（`_crawl_threads_launcher`）

**做什么**：
1. 从 serper_response 提取 `links` 列表（通常 10 个 URL）
2. 为每个 URL 启动一个 `threading.Thread`
3. 每个 Thread 调用 `WebScraper.scrape_url(url, rule=0)`
4. 若 `len(content) < 800`，重试 `rule=1`
5. 若 `len(content) > 300`，加入 `web_contents`（受 Lock 保护）
6. `thread.join()` 等待全部完成
7. 按 url_list 顺序重新排序，构造 `ordered_contents`

**为什么这么做**：
- 线程池适合 I/O 密集任务，避免 GIL 复杂度（用 threading 而非 multiprocessing）；
- 两段式抓取平衡速度与覆盖；
- 300 字符阈值过滤导航页/JS 页；
- 顺序重排保证 contents[i] 与 links[i] 一一对应。

#### 步骤 3：向量化与召回（`EmbeddingRetriever.retrievel_embeddings`）

**做什么**：
1. `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=0)` 切分
2. 构造 `metadatas = [{'url': link}]`
3. `Chroma.from_documents(texts, embedding=MiniLM-L6)`
4. `db.as_retriever(search_kwargs={"k": min(TOP_K=20, len(texts))})`
5. `retriever.get_relevant_documents(query)` 召回

**为什么这么做**：
- 1000 字符 ≈ 500 token，适配 MiniLM 的 max_seq_length；
- chunk_overlap=0 简单优先；
- URL 作为 metadata 让检索结果可反向追溯原文；
- top-20 给 GPTAnswer 提供足够候选，由它筛选 top-10。

#### 步骤 4：LLM 生成（`GPTAnswer.get_answer`）

**做什么**：
1. `_format_reference(docs, link_list)` 把 top-10 Document 转为：
   ```
   Webpage[1], url: https://...:
   content...

   Webpage[2], url: https://...:
   content...
   ```
2. `_rearrange_index()` 处理索引去重（同一 URL 多处引用复用编号）
3. `PromptTemplate.format(context_str=docs, language=lang, query=query, format=fmt, profile=profile)`
4. `ChatOpenAI(temperature=0.0, streaming=True).stream(prompt)`
5. `StreamingStdOutCallbackHandler()` 实时打印到 stdout

**为什么这么做**：
- temperature=0.0 保证事实稳定；
- streaming=True 改善长答案体验；
- `_rearrange_index` 确保引用编号唯一且连续，简化下游解析。

#### 步骤 5：引用定位（`ReferenceLocator.locate_source`）

**做什么**：
1. `answer.split("\nReferences:")` 切分正文与引用块（失败返回 -1）
2. `_handle_sentences_in_answer`：用 `(?<=[\n\.\!]).*?\[\d+\]` 找含 `[n]` 的句子
3. `_match_references`：用 `\[\d+\]`、`https://[^\n]+`、`Quoted sentence: (.*?)\n` 提取 [n] URL: Quoted sentence
4. `_match_web_info`：通过 `link_list.index(url)` 反查 serper 的 titles/snippets

**为什么这么做**：
- 三段式正则让每步独立可调；
- Prompt 强制 `\nReferences:` 分隔符（`config.yaml:10`）让 split 稳定；
- 失败时返回 -1 而非抛异常，便于上层决定如何处理。

## 2. 关键子流程

### 子流程 A：两段式抓取

```
WebContentFetcher._web_crawler_thread(thread_id, urls)
   │
   ├─ url = urls[thread_id]
   │
   ├─ scraper = WebScraper()
   │
   ├─ content = scraper.scrape_url(url, rule=0)  # 仅 h[1-6] + p
   │     │
   │     └─ get_webpage_html(url): GET, 8s 超时
   │     └─ convert_html_to_soup(html): BeautifulSoup + lxml
   │     └─ extract_main_content(soup, rule=0): 提取 h[1-6] + p，长度 > 10 词
   │
   ├─ if 0 < len(content) < 800:
   │     content = scraper.scrape_url(url, rule=1)  # 升级到 h[1-6] + p + div
   │
   ├─ if len(content) > 300:
   │     with web_contents_lock:
   │         web_contents.append({"url": url, "content": content})
   │
   └─ except Exception as e:
         with error_urls_lock:
             error_urls.append(url)
```

**每步原理**：
- **rule=0 优先**：覆盖大多数新闻/百科页，速度快；
- **rule=1 兜底**：覆盖 div 包裹的现代网页，覆盖更广；
- **300 字符阈值**：过滤噪声，避免污染向量库；
- **Lock 保护**：多线程并发写共享列表，避免竞态。

### 子流程 B：Hybrid Search（Notebook）

```
hybrid_search(col, dense_emb, sparse_emb, sparse_w=0.7, dense_w=1.0)
   │
   ├─ sparse_req = AnnSearchRequest(
   │     data=[sparse_emb], anns_field="sparse_vector",
   │     param={"metric_type": "IP"}, limit=10)
   │
   ├─ dense_req = AnnSearchRequest(
   │     data=[dense_emb], anns_field="dense_vector",
   │     param={"metric_type": "IP"}, limit=10)
   │
   ├─ rerank = WeightedRanker(sparse_w, dense_w)  # 加权融合
   │
   ├─ res = col.hybrid_search(
   │     [sparse_req, dense_req],
   │     rerank=rerank, limit=10,
   │     output_fields=["text"])[0]
   │
   └─ return [hit.get("text") for hit in res]
```

**每步原理**：
- **两次 AnnSearchRequest**：分别对 sparse 和 dense 字段做近邻搜索；
- **WeightedRanker**：加权融合（0.7 / 1.0 略偏向 dense）；
- **IP 距离**：BGE-M3 的稠密与稀疏都用内积度量。

### 子流程 C：销售 Agent 决策（Notebook）

```
agent_plan(query)
   │
   ├─ prompt = "你是销售助手规划模块，根据用户查询决定使用本地文档搜索/网络搜索..."
   │
   ├─ response = qwen-plus.chat(
   │     messages=[...], response_format={"type": "json_object"})
   │
   └─ JSON 解析：
       [
           {
               "action_name": "本地文档搜索" | "网络搜索",
               "prompts": [original_query, "扩展问题1", "扩展问题2"]
           }
       ]
```

**每步原理**：
- **JSON Mode**（`response_format={"type": "json_object"}`）：保证输出可解析；
- **规则在 Prompt 中**：让 LLM 决定用哪个 Tool，比硬编码灵活；
- **prompts 扩展**：原始查询 + 1-2 个相关问题，扩大召回面。

### 子流程 D：流式推理输出（Notebook cell 4327-4345）

```
for chunk in completion:
    if not chunk.choices:
        print("Usage:", chunk.usage)
    else:
        delta = chunk.choices[0].delta
        if hasattr(delta, 'reasoning_content') and delta.reasoning_content:
            print(delta.reasoning_content, end='', flush=True)
            reasoning_content += delta.reasoning_content
        else:
            if delta.content != "" and not is_answering:
                print("\n===完整回复===")
                is_answering = True
            print(delta.content, end='', flush=True)
            answer_content += delta.content
```

**每步原理**：
- **`reasoning_content`**：DeepSeek-R1 的"思考过程"（CoT）；
- **`content`**：最终回复；
- **区分流式输出**：让用户先看到思考过程，再看到答案，体验更好；
- **`flush=True`**：强制立即输出，不缓冲。

## 5. 各流程的"为什么这样设计"原理

### 原理 1：先检索后生成（Retrieve-then-Read）

- **核心思想**：在 LLM 生成答案前，先从外部知识库检索证据。
- **本项目体现**：所有 RAG 流程（Pipeline、Notebook）都遵循"Serper → WebScraper → Chroma/Milvus → GPT"的顺序。
- **为什么有效**：这是 RAG 论文（Lewis et al., 2020）的核心范式，显著减少幻觉。

### 原理 2：流式优于一次性（Streaming over Blocking）

- **核心思想**：LLM 生成是长任务，应通过流式回调逐步输出。
- **本项目体现**：`ChatOpenAI(streaming=True, callbacks=[StreamingStdOutCallbackHandler()])`（`llm_answer.py:49`）；Notebook `for chunk in completion`（cell 4327）。
- **为什么有效**：首 token 延迟 < 2s，用户体验更好。

### 原理 3：两段式 / 兜底策略（Graceful Degradation）

- **核心思想**：先尝试快速方案，失败再升级到慢速但更可靠的方案。
- **本项目体现**：抓取 `rule=0 → rule=1`（`fetch_web_content.py:26-28`）；引用解析三层降级（`locate_reference.py`）。
- **为什么有效**：平衡速度与覆盖率，避免因小失败整体重试。

### 原理 4：基于 `[n]` 的可追溯生成（Citation-based RAG）

- **核心思想**：用 `[n]` 编号让 LLM 显式标注引用，事后正则解析回填原文。
- **本项目体现**：Prompt 强约束（`config.yaml:8-13`）；正则三段式解析（`locate_reference.py:9-29`）。
- **为什么有效**：让用户能验证每个事实；减少幻觉。

### 原理 5：混合检索（Hybrid Search）

- **核心思想**：稠密向量（语义）+ 稀疏向量（关键词）加权融合，兼顾两种召回。
- **本项目体现**：Notebook `WeightedRanker(sparse=0.7, dense=1.0)`（cell 22）。
- **为什么有效**：BGE-M3 同时输出两种向量；Milvus Hybrid Search 一次完成。

### 原理 6：Plan/Memory/Tool/Answer 四模块 Agent

- **核心思想**：把决策、记忆、工具、输出拆成 4 个独立模块。
- **本项目体现**：Notebook `agent_plan` / `memory_global` / `retrieval` / `final_answer`。
- **为什么有效**：清晰对应 ReAct 范式；每模块可独立替换。

### 原理 7：多线程并发（Thread Concurrency）

- **核心思想**：对 N 个独立 URL 的网络请求使用线程池，让总耗时 ≈ max(t_i)。
- **本项目体现**：`threading.Thread` × N（`fetch_web_content.py:51-58`）。
- **为什么有效**：I/O 密集任务在 Python GIL 释放时真实并发。

### 原理 8：异常隔离（Bulkheading）

- **核心思想**：一个子任务失败不应影响其他子任务或整体流程。
- **本项目体现**：单 URL 抓取失败 → error_urls；单 Worker 异常 → 整体继续。
- **为什么有效**：RAG 的"价值密度"高（已花搜索/抓取成本），不应因小失败整体废弃。

### 原理 9：进度可观测（Observability）

- **核心思想**：长任务必须有可观测的进度反馈。
- **本项目体现**：每个 Thread 打印 `Starting/Completed`；Notebook 每个 cell 有 Markdown 标题与输出展示。
- **为什么有效**：RAG 流水线涉及多个外部 API，调试时必须看到进度。

### 原理 10：LLM 输出解析的容错（Fault-Tolerant Parsing）

- **核心思想**：LLM 输出常不规范，解析函数应多重降级。
- **本项目体现**：`ReferenceLocator` 的 `-1` 哨兵值（`locate_reference.py:17`）；Notebook `extract_json_content` 的正则提取（cell 102）。
- **为什么有效**：避免单个 LLM 输出不规范导致整个 pipeline 崩溃。
