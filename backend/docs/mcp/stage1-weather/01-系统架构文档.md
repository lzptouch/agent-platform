# 01_weather-mcp — 系统架构文档

## 1. 项目定位

01_weather-mcp 是一个**最小可运行的 MCP Server 示例**，目标是让初学者在 100 行代码内理解 MCP 协议的核心三要素：
1. **Server 注册**（`FastMCP("weather")`）
2. **Tool 暴露**（`@mcp.tool()` 装饰器）
3. **stdio 传输**（`mcp.run(transport='stdio')`）

底层走的是美国国家气象局（NWS）的 `https://api.weather.gov` 公开 GeoJSON API，因此**完全无需 API Key**，零门槛可跑通。

## 2. 整体架构

```
┌──────────────────┐  stdin/stdout  ┌────────────────────┐  HTTPS  ┌─────────────────┐
│  LLM 客户端      │ ─────────────► │  weather.py        │ ──────► │ api.weather.gov │
│  (Claude Desktop │  JSON-RPC      │  (FastMCP Server)  │  GeoJSON│   (NWS)         │
│   / Cursor / …)  │ ◄───────────── │                    │ ◄────── │                 │
└──────────────────┘                └────────────────────┘         └─────────────────┘
                                                │
                                                ▼ 调试时可选
                                       ┌────────────────────┐
                                       │  mcp_logger.py     │
                                       │  (流量镜像 → 日志)  │
                                       └────────────────────┘
```

## 3. 关键模块拆解

### 3.1 Server 初始化
```python
# weather.py:6-7
mcp = FastMCP("weather", log_level="ERROR")
```

### 3.2 异步 HTTP 客户端封装
```python
# weather.py:17-29
async def make_nws_request(url: str) -> dict[str, Any] | None:
    headers = {"User-Agent": USER_AGENT, "Accept": "application/geo+json"}
    async with httpx.AsyncClient() as client:
        try:
            response = await client.get(url, headers=headers, timeout=30.0)
            response.raise_for_status()
            return response.json()
        except Exception:
            return None
```

### 3.3 Tool 1：州级天气预警（`weather.py:44-61`）
- 装饰器 `@mcp.tool()` 把函数签名 + docstring 自动转成 MCP 的 `tools/list` 描述
- 函数返回 `str` 而不是 `dict`，降低客户端解析负担

### 3.4 Tool 2：经纬度天气预报（`weather.py:64-98`，**两次串行调用**）
- NWS API 强制"两次跳转"：第一次拿 `forecast URL`，第二次才能拿到实际预报
- 这种"链式请求"在 MCP 场景下是**典型的服务器侧组合外部 API**的模式

### 3.5 启动入口
```python
# weather.py:101-103
if __name__ == "__main__":
    mcp.run(transport='stdio')
```

### 3.6 调试利器 mcp_logger.py
- 用 `subprocess.Popen` 启动目标 MCP Server（如 `python weather.py`）
- 启动三个守护线程分别镜像 stdin / stdout / stderr
- 任何经过 stdio 的 JSON-RPC 报文都会落盘到 `mcp_io.log`

## 4. 调用链时序

```
1. 客户端 → stdio → "initialize"     → Server 返回 capabilities
2. 客户端 → stdio → "tools/list"     → Server 返回 [get_alerts, get_forecast]
3. 客户端 → stdio → "tools/call"     → Server 调用 httpx → NWS API
4. Server  ← HTTPS  ← GeoJSON 响应
5. Server → stdio → 格式化字符串     → 客户端展示给 LLM
```

## 5. 本章设计原理与依据

### 5.1 MCP 协议把 stdio 定为本地进程最简传输
- **核心思想**：用 stdio 而非 HTTP 作为本地进程通信
- **本项目中体现**：`weather.py:103` 刻意只使用 `transport='stdio'`，剥离 HTTP 噪音
- **为什么有效**：stdio 无端口、无鉴权，IDE/桌面客户端可直接 `subprocess.Popen`，零部署成本
- **佐证来源**：[官方] Anthropic MCP Protocol Specification "Transports"

### 5.2 `@mcp.tool()` 实现 boilerplate-free 的工具暴露
- **核心思想**：用 Python 类型注解 + docstring 自动生成 MCP `inputSchema`
- **本项目中体现**：`weather.py:44-61` 的 `get_alerts(state: str)` 完全靠装饰器声明工具
- **为什么有效**：减少手工维护 schema 与代码同步的人为错误
- **佐证来源**：[官方] MCP Python SDK FastMCP 源码

### 5.3 异常吞噬返回 None 的容错哲学
- **核心思想**：把错误"数据化"而非"异常化"
- **本项目中体现**：`make_nws_request` 用 `try/except Exception: return None`（`weather.py:28-29`）
- **为什么有效**：MCP Server 一次崩溃整个会话要重建，"失败即 None"对长生命周期 LLM Agent 更友好
- **佐证来源**：[博客] MCP 实战：从零搭建第一个 Server

### 5.4 `log_level="ERROR"` 是 stdio 协议的强约束
- **核心思想**：MCP stdio 协议帧使用换行分隔的 JSON，任何非 JSON 写到 stdout 都会破坏协议解析
- **本项目中体现**：`weather.py:7` 的注释"这个error一定要加"是作者踩坑后的明确警告
- **为什么有效**：客户端按行解析 stdout，INFO 日志会让客户端解析失败
- **佐证来源**：[官方] MCP Protocol Spec stdio 章节

### 5.5 二次请求（points → forecast）的链式 API 组合
- **核心思想**：在 MCP Server 内组合多次外部 HTTP 调用，对外暴露单个 Tool
- **本项目中体现**：NWS API 强制"两次跳转"——第一次拿 `forecast URL`，第二次才能拿到实际预报（`weather.py:73-81`）
- **为什么有效**：MCP Server 适合做"组合外部 API"的薄封装层，把多次 HTTP 调用合并为单次 Tool 调用
- **佐证来源**：[论文] API Composition Patterns (Hohpe-Woolf)

### 5.6 mcp_logger.py 的中间盒镜像代理
- **核心思想**：透明代理实现对被代理进程零侵入的流量捕获
- **本项目中体现**：三个守护线程镜像 stdin/stdout/stderr 到 `mcp_io.log`（`mcp_logger.py:141-189`）
- **为什么有效**：MCP Server 启动失败类问题没有"打印日志"途径，唯一的观测窗口就是 stdio
- **佐证来源**：[博客] Unix 哲学下 `tee`/`script` 工具的中间盒设计

### 5.7 uv + pyproject.toml 而非 requirements.txt
- **核心思想**：使用 PEP 621 标准做依赖管理
- **本项目中体现**：`pyproject.toml:1-16` + `uv.lock` 管理 `httpx>=0.28.1` 和 `mcp[cli]>=1.6.0`
- **为什么有效**：依赖锁定更精确、可重现构建
- **佐证来源**：[官方] PEP 621 / Astral uv 文档
