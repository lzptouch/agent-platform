# 06 流程文档

> **文档目的**：以时序图、流程图、状态机形式描述系统的端到端主流程与各关键子流程，解释"每一步在做什么、为什么这么做"。

## 1. 端到端主流程

### 1.1 主流程文字描述

从用户提交任务到获得最终报告，系统经历 5 个阶段：

1. **任务接收**（CLI / SDK / API 任一入口）
2. **任务拆解**（Orchestrator 调用 LLM 分析 + 拆解）
3. **并行研究**（多个 Worker 通过 ThreadPool 并行执行搜索与分析）
4. **综合初始报告**（Orchestrator 调用 LLM 综合所有 Worker 结果）
5. **迭代优化**（最多 N 次循环：质量评估 → 差距分析 → 补充研究 → 报告修订）
6. **结果输出**（保存文件 / 返回报告 / SSE 推送完成事件）

### 1.3 主流程核心步骤详解

#### 步骤 1：任务接收（`_print_header` + 构造 Orchestrator）

**做什么**：
- CLI 模式：解析 argparse 参数，构造 `DeepResearchAgent`，调用 `research()`
- API 模式：解析 JSON 请求体，构造 `TaskManager` 记录，调用 `run_research_task()`

**为什么这么做**：
- 统一入口，便于上层调用
- 参数校验前置（argparse / Pydantic）

#### 步骤 2：任务拆解（`Orchestrator.decompose_task`）

**做什么**：
1. 调用 `LLMClient.chat(prompt=TASK_DECOMPOSITION_PROMPT.format(task), ...)`
2. 解析返回的 JSON
3. 构造 `TaskPlan` 对象

**为什么这么做**：
- LLM 比硬编码更灵活，能适应各种研究任务
- JSON 结构化输出便于程序处理
- 温度 0.3（`orchestrator.py:172`）确保稳定性

**输入 → 输出**：

```
Input:  "2024年电动汽车市场分析报告"
Output: TaskPlan {
  query_type: QueryTypeAnalysis(type="breadth_first", reasoning="...", recommended_worker_count=4),
  subtasks: [
    SubTask(id="task_1", name="市场规模与增长", search_queries=[...], ...),
    SubTask(id="task_2", name="主要厂商竞争格局", ...),
    SubTask(id="task_3", name="政策环境分析", ...),
    SubTask(id="task_4", name="技术发展趋势", ...),
  ],
  report_structure: { title: "...", sections: [...] },
}
```

#### 步骤 3：并行研究（`Orchestrator.dispatch_workers`）

**做什么**：
1. 确定 `actual_workers = min(子任务数, max_workers, recommended_worker_count)`
2. 创建 `ThreadPoolExecutor(max_workers=actual_workers)`
3. 为每个 SubTask 创建一个 Worker 实例，submit 到线程池
4. 用 `as_completed` 优先取最先完成的结果

**为什么这么做**：
- 线程池适合 I/O 密集型任务（LLM + 搜索都是 I/O 阻塞）
- 每 Worker 独立实例，避免共享状态
- `as_completed` 让用户实时看到进度

#### 步骤 4：综合初始报告（`Orchestrator.synthesize_results`）

**做什么**：
1. 格式化 Worker 结果为文本（`_format_worker_results`）
2. 调用 `LLMClient.chat(prompt=SYNTHESIS_PROMPT.format(...))`
3. 返回 Markdown 格式报告

**为什么这么做**：
- 单一 LLM 调用综合多个 Worker 结果，避免信息丢失
- temperature=0.5（`orchestrator.py:371`）平衡创造性与一致性
- max_tokens=8192（`orchestrator.py:372`）保证报告完整性

#### 步骤 5：迭代优化循环

**做什么**：

```python
for iteration in range(1, max_iterations + 1):
    # 5.1 质量检查
    quality_result = self.check_quality(current_report, task, state.query_type)

    # 5.2 记录迭代
    iteration_record = IterationRecord(...)

    # 5.3 判断是否终止
    if iteration >= min_iterations and score >= threshold:
        break  # 质量达标
    if diminishing_returns_detected:
        break  # 收益递减
    if gap_analysis_says_stop:
        break  # 差距分析建议停

    # 5.4 补充研究 + 修订
    if iteration < max_iterations:
        gap_result = self.analyze_gaps(...)
        supp_tasks = gap_result.supplementary_tasks
        if supp_tasks:
            supp_results = self.dispatch_supplementary_workers(supp_tasks)
            current_report = self.refine_report(...)
```

**为什么这么做**：
- 五重终止条件避免无限循环
- `previous_score` 追踪分数提升，用于收益递减判断
- `analyze_gaps` 让 LLM 自己判断报告哪里不足

#### 步骤 6：结果输出

**做什么**：
- 同步模式：返回 `final_report` 字符串
- 流式模式：yield 进度 + 最终结果
- API 模式：更新 TaskManager，SSE 推送 `final` 事件
- CLI/SDK 模式：自动保存到 `research_output/research_<timestamp>.md`

**为什么这么做**：
- 多形态输出适配不同使用场景
- 持久化便于用户后续查阅

## 2. 关键子流程

### 子流程 A：Worker 的 OODA 循环

#### 时序图

```
LLM (扩展查询)    Search API     SearchWorker (OODA Loop)       LLM (分析)
       │               │                 │                          │
       │               │  ┌── Observe ──┐│                          │
       │               │  │  search()  ││                          │
       │               │◀─┤            ││                          │
       │               │──▶results─────▶│                          │
       │               │                 │                          │
       │               │  ┌── Orient ───┐│                          │
       │               │  │ assess_source││                         │
       │               │  │ identify_gap││                          │
       │               │                 │                          │
       │               │  ┌── Decide ───┐│                          │
       │               │  │ should_term?││                          │
       │               │  │ new_queries?││                          │
       │               │                 │                          │
       │               │  ┌── Act ──────┐│                          │
       │               │  │ 准备下一轮  ││                          │
       │               │                 │                          │
       │               │  (循环或终止)   │                          │
       │               │                 │                          │
       │               │  ┌── Analyze ──┐│                          │
       │               │                 │──JSON output task prompt─▶│
       │               │                 │◀──────result──────────────│
```

#### 每步原理

**A1. Observe（观察）**：`SearchWorker._observe`（`workers.py:276`）
- **做什么**：调用 `SearchClient.search()`，收集 `SearchResult`
- **为什么**：获取外部信息，打破 LLM 知识边界（呼应 ReAct 论文"act → observation"机制）

**A2. Orient（定向）**：`SearchWorker._orient`（`workers.py:302`）
- **做什么**：评估每个来源质量（high/medium/low），识别信息空白（info_gaps）
- **为什么**：来源质量差异大，需要分级；空白识别决定是否继续搜索

**A3. Decide（决策）**：`SearchWorker._decide`（`workers.py:330`）
- **做什么**：判断是"继续搜索"还是"终止分析"
- **判断逻辑**：
  - 无信息空白 → 终止
  - 预算不足 → 终止
  - 有空白 → 生成新查询继续
- **为什么**：避免无效迭代（呼应 OODA 原始思想"快速迭代"）

**A4. Act（行动）**：`SearchWorker._act`（`workers.py:353`）
- **做什么**：执行决策（终止则准备进入分析阶段；继续则执行新查询）
- **为什么**：将决策落实到行动

**A5. Analyze（分析）**：`SearchWorker._analyze_results`（`workers.py:448`）
- **做什么**：用 LLM（`SEARCH_WORKER_TASK_PROMPT`）分析所有搜索结果，输出结构化 JSON
- **为什么**：将非结构化搜索结果转化为可处理的结构化数据

### 子流程 B：迭代优化的三重终止条件

#### 时序图

```
for iteration in 1..max_iterations:
    │
    ├─► check_quality() ──► quality_score
    │                          │
    │                          ▼
    │                    ┌──────────────┐
    │                    │ score >= th? │
    │                    │ AND iter>=min│
    │                    └──────┬───────┘
    │                           │
    │        ┌──────────────────┴──────────────────┐
    │        │ Yes                                  │ No
    │        ▼                                     ▼
    │   ┌─────────┐                       ┌──────────────────┐
    │   │ break   │                       │ check_diminishing│
    │   │ (达标)  │                       │   _returns()     │
    │   └─────────┘                       └────────┬─────────┘
    │                                                │
    │                                ┌───────────────┴────────────┐
    │                                │ Yes                         │ No
    │                                ▼                            ▼
    │                          ┌──────────┐             ┌──────────────────┐
    │                          │ break    │             │ if iter < max:   │
    │                          │ (收益递减)│             │   analyze_gaps() │
    │                          └──────────┘             └────────┬─────────┘
    │                                                              │
    │                                                  ┌───────────┴───────────┐
    │                                                  │ should_stop?          │
    │                                                  ▼                       ▼
    │                                            ┌──────────┐         ┌──────────────────┐
    │                                            │ break    │         │ dispatch_supplement│
    │                                            │ (建议停)  │         │ refine_report    │
    │                                            └──────────┘         └────────┬─────────┘
    │                                                                              │
    │                                                                              ▼
    │                                                                       (next iteration)
```

#### 每步原理

**B1. 质量检查**：调用 LLM 从 6 个维度（完整性/准确性/深度/结构/可读性/来源质量）评估报告
- 为什么：单一分数无法反映多维质量

**B2. 阈值终止**：当 score >= threshold AND iteration >= min_iterations
- 为什么：保证不会因偶然高分而过早停止；保证至少迭代 2 次确保深度

**B3. 收益递减**：检测最近 N 次分数提升是否 < 5
- 为什么：避免"边际成本 > 边际收益"的无效迭代

**B4. 差距分析建议停止**：让 LLM 自己判断"还需要继续吗"
- 为什么：LLM 比硬编码规则更了解上下文

**B5. 补充研究 + 修订**：补做 N 个 supp task 后调用 refine_report
- 为什么：基于差距的补充比随机补充更精准

### 子流程 C：SSE 流式进度推送

#### 时序图

```
客户端                      FastAPI                  TaskManager           Orchestrator
  │                           │                          │                      │
  │──GET /stream───────────▶│                          │                      │
  │                           │                          │                      │
  │                           │   ┌─ event_generator ────────────┐             │
  │                           │   │ 每 0.5 秒检查                │             │
  │                           │   │ task.progress 是否有新事件    │             │
  │                           │   │                             │             │
  │                           │   │ 推送新事件:                 │             │
  │◀─data: {...}\n\n────────│   │   yield f"data: {json}"      │             │
  │                           │   │                             │             │
  │                           │   │ 检查 task.status            │             │
  │                           │   │ if completed/failed:        │             │
  │                           │   │   yield final_event         │             │
  │                           │   │   break                     │             │
  │                           │   └─────────────────────────────┘             │
  │                           │                          │                      │
  │                           │                          │  (Orchestrator.run   │
  │                           │                          │   通过 on_progress   │
  │                           │                          │   回调触发 update_   │
  │                           │                          │   progress)          │
  │                           │                          │◀──on_progress(stage,data)──▶│
  │                           │                          │                      │
```

#### 每步原理

**C1. 异步生成器**：`event_generator()`（`api.py:409`）是 `async def` 函数，用 `yield` 推送事件
- 为什么：避免阻塞 FastAPI 事件循环

**C2. 增量推送**：用 `last_progress_count` 记录已发送位置
- 为什么：避免重复发送

**C3. 轮询间隔**：`await asyncio.sleep(0.5)`（`api.py:442`）
- 为什么：兼顾实时性与 CPU 占用

**C4. 必须有 await**：FastAPI 官方文档要求生成器内有 `await` 才能正确取消
- 为什么：避免客户端断开后任务悬挂

**C5. 缓存控制头**：`Cache-Control: no-cache`、`Connection: keep-alive`（`api.py:447-450`）
- 为什么：SSE 必须禁用缓存，否则事件被代理/浏览器缓冲

## 4. 异常流程与兜底

### 4.1 异常处理矩阵

| 异常源 | 异常类型 | 处理位置 | 兜底行为 |
|--------|----------|----------|----------|
| LLM 调用失败 | 网络/限流 | `tools.py:108` | 返回 `success=False` + error_msg |
| 搜索 API 超时 | `requests.Timeout` | `tools.py:239` | 返回 `success=False` |
| 搜索 API 业务错误 | code != 200 | `tools.py:212` | 返回 `success=False` + msg |
| Worker 异常 | Exception | `orchestrator.py:299` | 单 Worker 失败不影响其他 |
| 任务拆解 JSON 解析失败 | `json.JSONDecodeError` | `tools.py:303-320` | 返回空 dict → 抛异常 |
| 综合报告 LLM 失败 | Exception | `orchestrator.py:375` | 抛异常 → 状态 failed |
| 报告修订失败 | Exception | `orchestrator.py:659` | 返回原报告 |
| TaskManager 内存丢失 | 重启 | 无 | 当前无持久化 |
| API 任务请求级配置覆盖 | 竞态 | `api.py:230` | 多任务并发可能相互覆盖 |

### 4.2 异常流程图

```
┌──────────────────┐
│  Orchestrator.run │
└────────┬─────────┘
         │
         ├─► decompose_task
         │      │
         │      ├─► LLM chat failed → raise Exception → state.status="failed"
```

## 5. 各流程的"为什么这样设计"原理

### 原理 1：先观察后决策（OODA 核心）

- **核心思想**：数据收集（Observe）和分析（Orient）必须先于决策（Decide）和行动（Act）。
- **本项目体现**：Worker 每个 OODA 周期都先 `_observe()` 收集数据，再 `_decide()` 选择下一步。
- **为什么有效**：避免盲目决策；OODA 的核心价值。

### 原理 2：ReAct 风格的"思考→行动→观察"循环

- **核心思想**：推理（Reasoning）与行动（Acting）协同，每一步都基于外部反馈调整。
- **本项目体现**：Worker `_decide()` 中"如果信息不足则生成新查询"体现了"基于观察调整行动"。
- **为什么有效**：避免 LLM 凭空推理导致幻觉。
- **佐证**：[论文] ReAct — Yao et al., ICLR 2023

### 原理 3：进度可观测优先

- **核心思想**：长任务必须有可观测的进度，否则用户会焦虑/误以为卡死。
- **本项目体现**：30+ 进度事件，从 CLI 渲染到 SSE 推送全方位覆盖。
- **为什么有效**：研究任务常耗时数分钟，进度反馈是体验核心。

### 原理 4：迭代优于一次性

- **核心思想**：复杂任务不应期望一次性完美，应通过多轮迭代逼近。
- **本项目体现**：迭代优化最多 5 次（默认）。
- **为什么有效**：首版报告常有信息空白；迭代可针对性补充。

### 原理 5：早停避免浪费

- **核心思想**：当继续的边际收益 < 边际成本时，应及时停止。
- **本项目体现**：收益递减检测 + 质量阈值 + 差距分析建议停止，五重早停保护。
- **为什么有效**：避免无限循环消耗 token 与时间。

### 原理 6：SSE 适合单向实时推送

- **核心思想**：服务器主动推送的实时通知用 SSE 而非 WebSocket。
- **本项目体现**：`/research/{id}/stream` 接口使用 `text/event-stream`。
- **为什么有效**：HTTP 友好、自动重连、文本协议便于调试。

### 原理 7：状态机保证流程严谨性

- **核心思想**：复杂流程用有限状态机管理，避免任意状态转移。
- **本项目体现**：`ResearchState.status` 的 7 个状态。
- **为什么有效**：状态转移显式化；调试时可加断点；测试时易验证。

### 原理 8：异常隔离（Bulkheading）

- **核心思想**：一个子任务失败不应影响其他子任务或整体流程。
- **本项目体现**：
  - 单 Worker 异常被捕获，整体继续
  - 单 Worker 超时不影响其他
  - 报告修订失败返回原报告
- **为什么有效**：研究任务的"价值密度"高（已花很多 token），不应因小失败而整体废弃。

### 原理 9：进度回调解耦核心与展示

- **核心思想**：通过回调函数将核心流程与 UI/日志展示解耦。
- **本项目体现**：`Orchestrator(on_progress=...)` 接受回调；CLI/SDK/API 三种上层各自实现。
- **为什么有效**：同一份核心代码支持多种使用形态。

### 原理 10：生成器（Generator）实现流式 API

- **核心思想**：Python 生成器是实现流式 API 的天然方式。
- **本项目体现**：`research_stream()` 用 `yield` 实现流式。
- **为什么有效**：Pythonic；调用方用 `for` 循环自然处理；无需回调。
