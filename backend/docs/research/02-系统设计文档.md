## 1. 设计目标与约束

### 1.1 功能性需求

| 需求编号 | 描述 | 优先级 |
|----------|------|--------|
| F1 | 接受用户自然语言研究任务，自动生成结构化报告 | P0 |
| F2 | 支持多任务并发执行（API 模式） | P0 |
| F3 | 支持流式进度推送 | P0 |
| F4 | 自动评估报告质量，未达标时迭代优化 | P0 |
| F5 | 支持 CLI、Python SDK、HTTP API 三种使用方式 | P1 |
| F6 | 提供来源质量评估与可信度标注 | P1 |
| F7 | 智能终止（收益递减检测） | P1 |

### 1.2 非功能性需求

| 维度 | 目标 | 实际指标 |
|------|------|----------|
| 端到端耗时 | 简单查询 < 60s；中等查询 3-5min；高复杂度 5-10min | 默认 max_iterations=5 |
| 并发能力 | 单进程支持 3 个研究任务并行 | `TaskManager.executor(max_workers=3)` |
| Worker 并行 | 单任务内支持 6 个 Worker 并行 | `max_workers=6` |
| 错误恢复 | 单 Worker 失败不影响其他 Worker 与整体任务 | 异常隔离 + 失败标记 |
| 可观测性 | 全流程进度可观测 | 30+ 阶段事件回调 |
| 可扩展性 | 新增 Worker 类型无需修改核心代码 | `BaseWorker` 抽象 |
| 可移植性 | 仅依赖 Python 标准库 + LLM/搜索 SDK | 依赖最少化 |

## 2. 关键设计决策（Decision Records）

### 决策 1：采用 Orchestrator-Workers 多 Agent 架构（而非单 Agent）

**问题**：单 Agent 处理复杂研究任务时容易"上下文溢出 + 推理漂移"。

**选项**：
- A. 单 Agent 多轮循环（顺序处理）
- B. Orchestrator-Workers 多 Agent 并行（**最终选择**）
- C. MapReduce 风格批量处理

**理由**：
- 选 B 是因为研究任务可并行化（不同子主题可独立研究），多 Agent 通过**独立上下文窗口**突破单 Agent 的 Token 容量限制；
- 选 B 而非 C 是因为研究需要"综合分析"环节，MapReduce 缺乏该环节；
- Anthropic 2025 实践表明，多 Agent 方案比单 Agent **性能高 90.2%**。

**佐证**：[博客] [译] Anthropic 是如何构建 Multi-Agent Research 系统的（2025）

### 决策 2：采用 OODA 循环而非线性搜索

**问题**：Worker 搜索多少次才算"够"？如何平衡信息充分性与成本？

**选项**：
- A. 固定搜索次数（如每 Worker 搜索 10 次）
- B. OODA 循环 + 收益递减检测（**最终选择**）
- C. LLM 自主决定终止

**理由**：
- A 太僵化，简单任务浪费、复杂任务不够；
- C 难以预测与控制成本；
- B 借鉴军事决策模型（John Boyd, 1970s），通过"观察→定向→决策→行动"四阶段实现**延迟承诺 + 快速迭代**，并通过 `_should_terminate()`（`workers.py:262`）多条件终止。

**佐证**：[博客] OODA Loop — Wikipedia

### 决策 3：采用 ThreadPoolExecutor 而非 ProcessPoolExecutor / asyncio

**问题**：如何并行执行多个 Worker？

**选项对比**：

| 维度 | ThreadPool | ProcessPool | asyncio |
|------|------------|-------------|---------|
| 启动开销 | 极低 | 高（pickle） | 低 |
| 共享内存 | 共享 | 独立 | 共享 |
| CPU 密集并行 | ❌（受 GIL） | ✅ | ❌（单线程） |
| I/O 密集并行 | ✅ | ✅ | ✅ |
| 与 requests 库兼容 | ✅ | ✅ | ❌（需 aiohttp） |
| 调试难度 | 低 | 中 | 中 |

**理由**：
- Worker 主要工作是 LLM 调用 + 网络搜索，本质是 **I/O 密集**；
- ThreadPool 在 I/O 阻塞时自动释放 GIL，可实现真实并发；
- 与现有同步 `requests` 库无缝集成，避免引入异步生态复杂度；
- 限制：实际并发数受限于网络带宽和 API 速率限制。

**佐证**：[官方] concurrent.futures — Python Docs

### 决策 4：采用迭代式质量优化（而非单次生成）

**问题**：如何保证报告质量？

**选项**：
- A. 单次生成，简单粗暴
- B. 迭代优化 + 多重终止条件（**最终选择**）

**理由**：
- 单次生成难以保证 80+ 分质量；
- 迭代优化包含"最少迭代次数 + 最大迭代次数 + 收益递减检测 + 差距分析建议停止"四重保护，避免无限循环；
- 在 2~5 次迭代中，大多数报告可达到 80+ 分。

**佐证**：[博客] LLM Powered Autonomous Agents — Lilian Weng

### 决策 5：采用 SSE 而非 WebSocket 推送进度

**问题**：API 模式如何向客户端推送进度？

**选项**：
- A. 短轮询（每 2s 客户端请求一次）
- B. SSE（**最终选择**）
- C. WebSocket

**理由**：
- A 简单但延迟高、浪费带宽；
- C 全双工但需要新协议、与 HTTP 工具链兼容性差；
- B 单向推送、HTTP 友好、浏览器原生支持（`EventSource`），且 FastAPI 通过 `StreamingResponse` 即可实现。

**佐证**：[官方] FastAPI Custom Response — StreamingResponse

### 决策 6：采用 Pydantic v2 而非 dataclass 定义 API 模型

**问题**：HTTP API 数据模型如何定义？

**选项**：
- A. `dataclass`
- B. Pydantic `BaseModel`（**最终选择**）

**理由**：
- Pydantic 自动类型校验、`json_schema_extra` 支持 OpenAPI 文档生成；
- FastAPI 原生集成；
- 对外暴露的 API 必须做输入校验。

**佐证**：[官方] Pydantic Models

### 决策 7：采用 JSON 字符串 + 正则提取 LLM 输出（而非 Structured Outputs）

**问题**：如何从 LLM 输出中提取结构化数据？

**选项**：
- A. JSON Mode + 提示词约束（**最终选择**）
- B. OpenAI Structured Outputs（JSON Schema 约束解码）
- C. Function Calling

**理由**：
- 本项目使用阿里云 DashScope（OpenAI 兼容协议），部分模型可能不支持 Structured Outputs；
- 提示词约束 + JSON 提取（`extract_json`，`tools.py:292`）是兼容性最强的方案；
- 代价：偶尔 JSON 解析失败，需降级为默认结果。

**佐证**：[官方] OpenAI Structured Outputs

## 3. 模块划分原则

### 3.1 单一职责原则

每个模块只负责一件事：

| 模块 | 唯一职责 |
|------|----------|
| `tools.py` | 提供 LLM / 搜索 / 文本解析的原子工具 |
| `workers.py` | 实现各类 Worker（执行层） |
| `orchestrator.py` | 编排所有 Worker 完成研究任务 |
| `prompts.py` | 集中管理所有提示词 |
| `config.py` | 集中管理所有配置 |
| `api.py` | 暴露 HTTP API |
| `main.py` | 对外 SDK 入口 |

### 3.2 依赖倒置原则

- Orchestrator 依赖 `worker_factory: Callable`（`orchestrator.py:127`），而非具体 Worker 类，便于替换 Worker 类型；
- Worker 依赖 `LLMClient` / `SearchClient` 单例（`tools.py:351,359`），便于 mock 测试。

### 3.3 配置与代码分离

- 所有可变参数集中在 `config.py`，便于运行时调整；
- 提示词集中在 `prompts.py`，便于优化迭代而无需改业务代码。

## 4. 数据模型与状态设计

### 4.1 状态机设计

```
┌──────────┐
│initialized│
└─────┬────┘
      │ decompose_task()
      ▼
┌─────────┐
│ planning│
└─────┬───┘
      │ dispatch_workers()
      ▼
┌────────────┐
│researching│
└─────┬──────┘
      │ synthesize_results()
      ▼
┌─────────────┐
│synthesizing│
└─────┬───────┘
      │ 循环：check_quality → analyze_gaps → dispatch_supplementary → refine_report
      ▼
┌───────────┐
│ iterating │ ◀──→ (continues 1..max_iterations)
└─────┬─────┘
      │ 终止条件：
      │ 1. score >= threshold AND iteration >= min_iterations
      │ 2. diminishing_returns_detected AND recommendation == "stop"
      │ 3. gap_analysis.stop_iteration_recommendation.should_stop
      │ 4. iteration == max_iterations
      ▼
┌──────────┐
│completed│
└──────────┘
```

异常分支：

```
任一阶段 → except → ┌────────┐
                     │ failed │
                     └────────┘
```

### 4.3 状态持久化策略

- **内存状态**：`TaskManager.tasks` 字典（`api.py:96`）保存所有任务状态；
- **持久化状态**：任务完成后写入 `research_output/research_<timestamp>.md` 与 `_meta.json`；
- **重启丢失**：当前实现未做数据库持久化，重启后内存中任务丢失（已规划用 SQLite/Redis 替换）。

## 6. 接口设计原则

1. **最小惊讶原则**：API 参数命名与主流框架一致（如 `max_workers` 参照 concurrent.futures）。
2. **可选参数优先**：所有可调参数都有默认值，调用方可零配置使用。
3. **错误显式化**：所有异常通过 `success=False` + `error_msg` 返回，而非抛异常中断流程。
4. **进度可观测**：任何长任务都提供进度回调（CLI / SDK / SSE 三种方式）。

## 7. 错误处理与降级策略

| 错误类型 | 处理策略 | 代码位置 |
|----------|----------|----------|
| LLM 调用失败 | 返回 `LLMResponse(success=False, error_msg=...)`，上层降级 | `tools.py:108` |
| 搜索 API 超时 | 返回 `SearchResponse(success=False, error_msg="搜索请求超时")` | `tools.py:239` |
| Worker 异常 | 单 Worker 失败不影响其他，结果中标记 `success=False` | `orchestrator.py:299` |
| 任务拆解失败 | 抛出异常，状态置 `failed` | `orchestrator.py:175` |
| JSON 解析失败 | 返回空 dict / 默认结果 | `tools.py:303-320` |
| 报告修订失败 | 返回原报告 | `orchestrator.py:660` |
| API Key 缺失 | 配置加载时 `None`，调用时显式失败 | `config.py:17,28` |

## 9. 安全设计

| 风险点 | 设计方案 |
|--------|----------|
| 恶意任务注入 | 当前无内容审核；建议接入阿里云内容安全 API |
| API Key 泄露 | 通过环境变量注入，不硬编码 |
| Prompt 注入攻击 | LLM 输出通过 JSON 提取，避免直接执行 |
| 资源滥用 | `TaskManager` 限制并发数 3；可通过 `timeout_per_worker` 限制时长 |
| 越权访问 | 当前 API 无认证；生产部署建议加入 JWT 或 API Key 鉴权 |

## 10. 本章设计原理与依据

### 原理 1：最小惊讶原则（Principle of Least Astonishment）

- **核心思想**：API 设计应符合用户已有认知，降低学习成本。
- **在本项目中的体现**：CLI 参数名 `--workers` / `--output` 与 argparse 惯例一致；HTTP API 路径 `/research` 直观；回调函数签名 `(stage: str, data: dict) -> None` 简单通用。
- **为什么有效**：减少用户认知负担，提升 API 可用性。

### 原理 2：防御性编程（Defensive Programming）

- **核心思想**：假设任何外部输入都可能出错，代码应主动检测并优雅降级。
- **在本项目中的体现**：每个 LLM / 搜索调用都有 try/except；JSON 解析有多个 fallback 路径；Worker 失败不中断整体。
- **为什么有效**：在网络不稳定、API 偶发故障的环境下，系统整体可用性显著提升。

### 原理 3：可观测性优先（Observability-Driven Design）

- **核心思想**：系统在设计阶段就内置"对外部可见"的进度与状态，而非事后补打日志。
- **在本项目中的体现**：30+ 进度事件 + ConsoleReporter + TaskManager 进度字典 + SSE 推送。
- **为什么有效**：研究任务常耗时数分钟，用户对"系统在做什么"有强需求；事件回调机制让任何上层（CLI/SDK/API）都能渲染进度。

### 原理 4：单一可观察状态源（Single Source of Truth）

- **核心思想**：所有状态集中在 `ResearchState` 一个对象，避免分散维护导致的不一致。
- **在本项目中的体现**：Orchestrator 内部、API 层都通过 `ResearchState` 传递完整状态；JSON 输出也基于此结构序列化。

### 原理 5：配置外置与运行时可调

- **核心思想**：可变参数不应硬编码，应在运行时可调整而无需改代码。
- **在本项目中的体现**：`config.py` 中所有阈值均可在 API 请求中覆盖（见 `api.py:230-231`）。

### 原理 6：依赖注入与可测试性

- **核心思想**：通过依赖注入解耦核心逻辑与具体实现。
- **在本项目中的体现**：`Orchestrator(worker_factory=...)` 注入 Worker 工厂，便于测试时替换为 mock。
- **佐证**：[设计模式] Dependency Injection — Martin Fowler

### 原理 7：迭代收敛保证

- **核心思想**：任何循环都必须有明确的终止条件，避免无限循环。
- **在本项目中的体现**：
  - 最多迭代次数 `max_iterations=5`
  - 最少迭代次数 `min_iterations=2`（防止过早停止）
  - 质量阈值 `quality_threshold=80`
  - 收益递减检测
  - 差距分析建议停止
  - Worker 内部预算耗尽
- **为什么有效**：五重保护覆盖了所有"该停止"的场景，避免资源浪费。
