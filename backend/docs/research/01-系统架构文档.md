# 01 系统架构文档

> **文档目的**：从架构师视角描述 Deep Research Agent 的整体结构、子系统划分、运行时数据流和部署拓扑。
>
> **目标读者**：架构师、新入职工程师、技术负责人。

---

## 1. 项目概述与定位

Deep Research Agent 是一个**多智能体协作的深度研究系统**，能够将用户的开放式研究问题自动化拆解、并行搜索、汇总，并迭代优化至质量达标。其核心定位是：

- **能力对标**：参照 Anthropic 2025 年公开发布的 "How we built our multi-agent research system" 设计模式（`https://www.anthropic.com/engineering/multi-agent-research-system`）。
- **技术特色**：在 Anthropic 模式基础上，融合了 **OODA 循环**（军事决策模型）、**查询类型分类**（depth_first / breadth_first / simple）、**动态 Worker 调度**与**收益递减检测**。
- **使用形态**：提供 Python SDK、CLI、FastAPI 服务三种使用方式，可作为研究子模块嵌入其他系统。

## 2. 业务背景与核心场景

### 2.1 业务背景

研究类任务（如市场分析、文献综述、技术调研）是典型的**开放式问题**：

- 无法预先枚举所需步骤；
- 需要多轮信息检索与综合；
- 单一上下文窗口难以容纳所有材料。

传统单 Agent 方案容易出现"上下文溢出 + 推理漂移"问题，多 Agent 架构通过**任务并行 + 上下文隔离**提供更稳定的解决方案。

### 2.2 核心场景

| 场景 | 输入示例 | 期望输出 |
|------|----------|----------|
| 市场研究 | "2024年中国新能源汽车市场分析" | 结构化 Markdown 报告 + 来源引用 |
| 技术调研 | "大模型 Agent 的最新进展综述" | 多视角分析 + 引用列表 |
| 学术综述 | "RAG 技术发展现状与趋势" | 学术化报告 + 高质量来源 |
| 商业分析 | "某 SaaS 公司的竞争格局研究" | 商业洞察 + 数据支撑 |
| 简单问答 | "东京的人口是多少" | 直接的事实回答 |

## 5. 关键时序子流程

### 5.1 Worker 的 OODA 循环

```
SearchWorker.execute(subtask)
   │
   ├─ while not _should_terminate():
   │     │
   │     ├─ _observe()      ─→ 执行搜索 (SearchClient.search)
   │     │                       收集 SearchResult 列表
   │     │
   │     ├─ _orient()       ─→ 评估来源质量 (high/medium/low)
   │     │                       识别信息空白 (info_gaps)
   │     │
   │     ├─ _decide()       ─→ 决定: 终止 / 继续 / 生成新查询
   │     │
   │     └─ _act()          ─→ 准备进入下一轮 / 准备进入分析
   │
   └─ _analyze_results()    ─→ LLM 分析 (SEARCH_WORKER_TASK_PROMPT)
                                输出结构化 JSON
```

### 5.2 迭代优化主循环

```
for iteration in 1..max_iterations:
    ① quality = check_quality(report)
    ② record iteration in iteration_history
    ③ if quality >= threshold AND iteration >= min_iterations:
           break  # 达标，结束
    ④ if diminishing_returns_check and iteration >= 2:
           dr = check_diminishing_returns(...)
           if dr.diminishing_returns_detected:
               break  # 收益递减，提前终止
    ⑤ if iteration < max_iterations:
           gap_result = analyze_gaps(report, quality)
           if gap_result.stop_recommendation.should_stop:
               break
           supp_tasks = gap_result.supplementary_tasks
           if supp_tasks:
               supp_results = dispatch_supplementary_workers(supp_tasks)
               report = refine_report(supp_results)
```

## 7. 性能 / 可靠性 / 扩展性架构考量

### 7.1 性能

- **并行优化**：每个研究任务内部，Worker 通过 `ThreadPoolExecutor` 并行执行（`orchestrator.py:269`），可缩短端到端耗时 3~5 倍。
- **预算控制**：每个 Worker 有 `ResearchBudget`（`workers.py:61`），限制搜索次数与分析轮次，避免单任务失控。
- **Token 节流**：LLM 调用温度按任务类型差异化设置（拆解 0.3、汇总 0.5、质量检查 0.2）。

### 7.2 可靠性

- **超时控制**：`future.result(timeout=120)`（`orchestrator.py:287`），单 Worker 超时不阻塞整个系统。
- **错误隔离**：单个 Worker 失败不影响其他 Worker，最终结果中包含失败标记（`orchestrator.py:299`）。
- **状态持久化**：`ResearchState` 集中保存所有中间结果，便于排查和回溯。

### 7.3 扩展性

- **新增 Worker 类型**：通过继承 `BaseWorker` + 实现 `execute()` 即可（`workers.py:79`）。
- **新增工具**：在 `tools.py` 中添加工具类，并通过 `Worker` 调用。
- **替换 LLM/搜索**：仅需修改 `config.py` 与 `tools.py` 中的客户端实现。
- **多任务并发**：`TaskManager`（`api.py:92`）使用独立 ThreadPool 调度多个研究任务。

## 8. 本章设计原理与依据

### 原理 1：Orchestrator-Workers 多 Agent 模式

- **核心思想**：将"规划/协调/综合"职责集中到 Lead Agent（Orchestrator），将"具体执行"委派给多个并行的 SubAgent（Workers），通过职责分离实现"任务并行 + 上下文隔离"。
- **在本项目中的体现**：`Orchestrator` 类负责拆解、调度、汇总、迭代；`SearchWorker` 类负责单个子任务的搜索与分析；两者通过 `TaskPlan` 和 `worker_results` 解耦。
- **为什么有效**：Anthropic 2025 年的实践表明，Lead Agent (Opus 4) + SubAgents (Sonnet 4) 的多 Agent 系统相比单 Opus 4 Agent **性能高 90.2%**（`https://arthurchiao.art/blog/built-multi-agent-research-system-zh/`）。核心机理是**独立上下文窗口让多个 SubAgent 并行推理，扩大了有效 Token 容量**。
- **佐证来源**：
  - [博客] Anthropic Engineering - Multi-agent Research System, 2025 — `https://www.anthropic.com/engineering/multi-agent-research-system`
  - [博客] [译] Anthropic 是如何构建 Multi-Agent Research 系统的（2025） — Arthur Chiao

### 原理 2：OODA 决策循环

- **核心思想**：将复杂任务执行建模为"观察（收集信息）→ 定向（分析）→ 决策（选择下一步）→ 行动（执行）"的迭代循环，强调**延迟承诺**与**快速迭代**。
- **在本项目中的体现**：`SearchWorker._observe/_orient/_decide/_act` 四个方法（`workers.py:276-362`）严格对应 OODA 四阶段，通过 `ResearchBudget` 控制循环次数。
- **为什么有效**：OODA 由美国空军上校 John Boyd 在 1970 年代提出，目的是"**比对手更快完成循环即可获得战术优势**"（`https://en.wikipedia.org/wiki/OODA_loop`）。在搜索任务中体现为：每轮分析结果→判断信息是否充足→决定是否继续搜索→避免无效迭代。
- **佐证来源**：
  - [博客] OODA Loop — Wikipedia
  - [论文] 原始 OODA 思想 — John Boyd, "Destruction and Creation" (1976), "The Essence of Winning and Losing" (1995)

### 原理 3：基于 ThreadPoolExecutor 的并行调度

- **核心思想**：对于 I/O 密集型任务（网络请求、LLM API 调用），Python 的 GIL 不构成瓶颈，**线程池**即可实现真实并发。
- **在本项目中的体现**：外层 `TaskManager.executor`（max_workers=3）并发运行多个研究任务；内层 `Orchestrator.dispatch_workers` 使用线程池并行 Worker。
- **为什么有效**：Python 官方文档明确："ThreadPoolExecutor 受 GIL 限制，只对**释放 GIL 的操作**（如 I/O 阻塞、`time.sleep`、部分 C 扩展）真正并发"（`https://docs.python.org/3/library/concurrent.futures.html`）。本项目中的所有阻塞操作（HTTP 请求、LLM 调用、搜索）都释放 GIL，因此线程池方案既轻量又高效。
- **佐证来源**：
  - [官方] concurrent.futures — Python 3 Docs

### 原理 4：迭代式质量优化（Reflect-Eval-Improve 循环）

- **核心思想**：单次生成难以保证高质量，应通过"生成→评估→识别差距→补充研究→重生成"的多轮循环逼近质量目标。
- **在本项目中的体现**：`Orchestrator.run` 的迭代主循环（`orchestrator.py:722-843`）实现了 ReAct 论文中 Reflexion 范式的简化版，结合了"最低迭代次数 + 最大迭代次数 + 收益递减提前终止"三重保护。
- **为什么有效**：Lilian Weng 在《LLM Powered Autonomous Agents》（2023）中总结，Self-Reflection 类方法（Reflexion / CoH / AD）显著优于一次性生成。
- **佐证来源**：
  - [博客] LLM Powered Autonomous Agents — Lilian Weng

### 原理 5：查询类型驱动的动态调度

- **核心思想**：不同的查询类型（深度优先 / 广度优先 / 简单）需要不同数量的 Worker 和不同研究策略，应根据任务特征自适应调整。
- **在本项目中的体现**：`TASK_DECOMPOSITION_PROMPT` 提示 LLM 判定查询类型（`prompts.py:38-164`），Orchestrator 根据类型调整 `actual_workers`（`orchestrator.py:262-266`）。
- **为什么有效**：Anthropic 实践表明，**sub-agent 数量过多会导致"开销超过收益"**，动态伸缩能更好平衡效率与成本。
- **佐证来源**：
  - [博客] [译] Anthropic 是如何构建 Multi-Agent Research 系统的（2025）

### 原理 6：SSE（Server-Sent Events）流式协议

- **核心思想**：HTTP 长连接 + 文本事件流（`data: ...\n\n`），实现服务器主动推送，避免 WebSocket 复杂度。
- **在本项目中的体现**：`api.py:389-451` 的 `/research/{task_id}/stream` 接口，使用 `StreamingResponse` + `text/event-stream` 推送进度事件。
- **为什么有效**：FastAPI 官方文档指出，SSE 是 **HTTP 友好**（无需新协议）、**浏览器原生支持**（`EventSource` API）、**自动重连**（基于 `Last-Event-ID`）的轻量级推送方案。本项目的研究任务常耗时数分钟，SSE 让前端能实时显示进度。
- **佐证来源**：
  - [官方] FastAPI Custom Response — StreamingResponse
  - [博客] SSE 协议规范

### 原理 7：进度事件回调机制（Observer Pattern）

- **核心思想**：通过回调函数（`on_progress`）将编排层的状态变化通知给 UI/CLI 层，实现关注点分离。
- **在本项目中的体现**：`Orchestrator.__init__(on_progress=...)` 接收回调（`orchestrator.py:127-148`），CLI 通过 `ConsoleReporter` 渲染，SSE 通过 `TaskManager.update_progress` 转发。
- **为什么有效**：回调机制使同一份核心逻辑能同时支持 CLI（同步渲染）、SDK（自定义处理）、API（异步推送）三种使用形态，符合"**单一职责 + 依赖倒置**"设计原则。
- **佐证来源**：
  - [设计模式] Observer Pattern — GoF
