# WorkBuddy 能力扩展 —— 需求分析与总体设计（v2）

> 版本：v2.0（代码校验 + 开源调研后修订）　日期：2026-10-19
> 目标项目：`agent-platform`（FastAPI + Vue 3）
> 范围：Skill 增强、Skill 团队、定时任务、对话/工作双模式

## 1. 代码核对结论（先验证，再设计）

逐文件核对后，确认以下事实。它们是 v1 方案需要修正的根因。

| # | 核对点 | 代码事实 | 对设计的影响 |
| --- | --- | --- | --- |
| 1 | 工具注入位置 | `ToolRegistry.get_combined_tools()` 第一行即 `tools = list(BUILTIN_TOOLS)`，随后无条件返回完整内置工具（`backend/app/services/tool_registry.py:136`） | **只改 system prompt 无法禁用工具**；必须在 ToolRegistry 增加 profile 过滤 |
| 2 | Agent 主循环 | `AgentService.stream()` 以关键字参数接收 `skills/enable_*`，每次调用现构造 `tools` 与 `system_prompt`（`agent_service.py:170-204`） | 加 `mode/session/team` 只需扩展此入口，不必另建 Agent |
| 3 | 消息组装 | `_stream_loop()` 内 `messages` 是局部变量，固定 `system + user` 两条起步（`agent_service.py:228-231`） | 多轮历史需抽出 `build_messages()`，且不能直接回放 tool 消息 |
| 4 | 流式响应 | `api/v1/agent.py:45-63` 用同步生成器包 `StreamingResponse` | **DB Session 必须在生成器内部创建**，不能用 `Depends`（响应返回时依赖已释放） |
| 5 | 会话/认证 | 无会话/用户表或模型（仅有 `user_prompt` 之类参数名），无登录与权限中间件 | 从零建会话体系；本期不做多用户，但预留 `owner` |
| 6 | 定时任务 | 全仓 `apscheduler/cron/schedule/BackgroundScheduler` 0 命中 | 全新模块 |
| 7 | Skill 管理 | `api/v1/skills.py` 仅 list / reload / detail / validate / files 资源读取；`SkillManager` 仅扫描单一 `settings.skills_dir`（`config.py:74`） | 缺 CRUD/启停用/导入导出；需支持第二目录 |
| 8 | 现有持久化 | 仅 Research 用线程池 + `tasks.json` 全量落盘（`research_manager.py:44-69`，目录配置 `config.py:68`） | 该模式适合"少量任务、低频写"，不适合会话/消息 |
| 9 | 调试日志 | `_save_log()` 每轮把完整 messages 写入 `data/outputs/chat_log_*.json`（`agent_service.py:500-517`） | 会话入库后会产生重复存储，需降级为可选调试开关 |
| 10 | 部署形态 | `deploy/backend/Dockerfile:109` 单进程 `uvicorn`，无 `--workers` | 当前可进程内调度；但必须为后续扩 worker 预留防重机制 |
| 11 | 前端 SSE | 已有 `src/api/sse.ts` 封装 | 复用，不重复实现 |
| 12 | 测试基线 | README 称 40 用例；`backend/tests/` 共 5 个测试文件 | 新测试需自建 DB fixture，不能污染开发库 |

### 1.1 结论

v1 文档在**功能拆分与阶段递进**上是可用的，但在**技术承载**与**代码接入点**上有硬伤：JSON 落盘承载不了会话/运行记录的数据量与并发；模式只改 prompt 不生效；历史回放会破坏 tool_call 协议。v2 据此重写数据层、模式层与调度层。

## 2. 原方案问题清单与修正

| v1 设计 | 问题 | v2 修正 |
| --- | --- | --- |
| Session/Message/Team/Task 全部 JSON 落盘 | 每条消息触发全文件重写 O(n)；多线程/多进程并发丢写；无索引、无分页、无事务、无外键；`index.json` 与详情文件易不一致 | **SQLite（WAL）+ SQLAlchemy 2.0 + Alembic**；`DATABASE_URL` 可切 PostgreSQL |
| `mode=chat` 时在 SkillManager 里删 prompt 段落 | 工具数组仍含 `execute_python/write_file/execute_bash`，模型照样能调 | 新增 `ToolProfile`，`get_combined_tools(profile=...)` 与 prompt 同源裁剪 |
| 会话历史整段拼回 messages | `assistant` 带 `tool_calls` 的消息若缺对应 `tool` 消息会被 OpenAI 兼容接口拒绝 | 只回放 `user` + 最终 `assistant` 文本；可选把工具步骤压缩为一条系统摘要 |
| 定时任务 `tasks.json` + Apscheduler 内存 job | 重启后依赖重算；多副本重复触发；补跑无幂等 | 表为唯一真相 + 启动重建 job + `UNIQUE(task_id, scheduled_for)` + DB 租约锁 |
| 双模式 chat/work | WorkBuddy 实际为 **Ask / Plan / Craft** 三态，Plan 需要人工确认后才执行 | `mode=chat|work` + `work.plan_first`（两阶段：plan → approve → execute） |
| 团队 `skill_names` 直接存 JSON | 无法回答"某 Skill 被哪些团队使用"，改名/禁用难以级联 | 增加 `team_skills` 关联表 |
| 会话删除只删 JSON | 无级联，run/event 残留 | 外键 `ON DELETE CASCADE` + 事件表级联 |
| 未定义并发上限 | 定时任务与手动任务同时跑满线程池、打爆 LLM 配额 | 全局并发信号量 + 每任务串行 + 每日次数上限 |

## 3. WorkBuddy 能力对标

公开资料（腾讯 WorkBuddy，2026 年发布）显示其核心概念为：**Task（任务）/ Conversation（对话）/ Skill（技能）/ Expert（专家）/ Automation（自动化）/ Connector（MCP 连接器）**，并提供三种执行模式：

| WorkBuddy 模式 | 语义 | 本项目映射 |
| --- | --- | --- |
| **Ask** | 只聊不动手，不改文件 | `mode=chat` |
| **Craft** | 说干就干，读写文件、执行命令、产出结果 | `mode=work`, `plan_first=false` |
| **Plan** | 先分析拆解、给出计划，用户确认后再执行 | `mode=work`, `plan_first=true` |
| Skills | 内置 + 社区技能包（SKILL.md 目录） | 现有 `skills/` + 新增 `data/skills_custom/` |
| Expert / 专家 | 领域专家（一组技能 + 提示词） | **Skill 团队（Team）** |
| Automation | 7×24 定时触发 | **定时任务（Scheduled Task）** |
| Connector | MCP | 已有 MCP 链 |

> 说明：WorkBuddy 为闭源产品，上述能力来自官方页面与公开评测，字段级实现不可见；落地细节参考同生态开源的 OpenClaw（cron / skills / session）与 Dify（conversation / message / workflow_run）。

## 4. 需求定义（v2）

### 4.1 对话模式（Chat / Ask）

- 只读工具档案：`read_file / list_directory / rag_query / web_research`；MCP 工具**默认不注入**，仅当 Server 注册信息标记 `read_only: true` 时可用（`weather/search` 可标记，`xiaohongshu` 不可）。
- 禁用：`write_file / execute_python / execute_bash`。
- `max_iterations = min(5, settings.max_iterations)`；`enable_reflection` 强制 false。
- Skill 默认不注入（`skills=None` 在 chat 模式解释为 `[]`），用户显式选择才注入。
- 多轮上下文从 DB 读取最近 N 轮（默认 10 条，可配置），只回放最终问答。
- 会话 `mode` 不可变（避免历史语义混乱）。

### 4.2 工作模式（Work / Craft + Plan）

- 全量工具档案 + 可选反思循环；默认开启过程步骤流。
- `plan_first=false`：单次 run 内完成 plan→execute→answer。
- `plan_first=true`：两阶段。
  1. `POST /api/v1/agent/run` 返回 `run.status=awaiting_approval` 与结构化计划（步骤数组）；
  2. `POST /api/v1/agent/runs/{run_id}/approve`（可带 `edited_plan`）→ 恢复执行；
  3. `POST /api/v1/agent/runs/{run_id}/reject` → 关闭 run。
- 产出：`files[]` + 结果摘要，全部落到 run 记录与产物目录。

### 4.3 Skill 团队（Team）

- 字段：`name / description / skill_names[] / prompt_prefix / strategy / enabled`。
- 策略：
  - `none`：全集注入；
  - `sequential`：按 `team_skills.position` 标注 `[步骤 N/M]`；
  - `router`：LLM 从候选中选 1~2 个（失败降级为 `none`，结果缓存 5 分钟）。
- 与 `skills[]` 互斥（同时传 → 422）。
- 一个会话可绑定团队；团队删除时 `sessions.team_id` 置空（`ON DELETE SET NULL`）。

### 4.4 定时任务（Scheduled Task）

- 调度类型：`cron`（5 段 + 时区）或 `interval`（≥60s）。
- 任务载荷：Agent 轮次（本项目只做这一种；命令/脚本载荷列为非目标）。
- 运行记录：`queued/running/success/failed/skipped/interrupted/awaiting_approval`。
- 幂等：`UNIQUE(task_id, scheduled_for)`，重启补跑不会重复。
- 并发：每任务串行（`max_instances=1`），全局并发上限（默认 2）。
- 安全：`work` 模式任务必须显式 `allow_unattended_tools=true`；每日运行上限默认 100。
- 投递（Webhook/IM）：本期非目标，表结构预留 `delivery_json`。

## 6. 数据库选型（核心变更）

### 6.1 为什么必须引入数据库

| 维度 | JSON 文件 | 数据库 |
| --- | --- | --- |
| 写入成本 | 每次追加消息重写整个会话文件 + `index.json` | O(1) INSERT |
| 并发 | 全文件覆盖，多线程/进程易丢写 | 事务 + 行锁；SQLite WAL 单写多读 |
| 查询 | 只能全量加载后内存过滤 | 索引、分页、聚合（"本月失败任务数"） |
| 一致性 | 无外键/无级联，删除易残留 | 外键级联、唯一约束（幂等） |
| 迁移/演进 | 手写兼容代码 | Alembic 版本化 |
| 审计/统计 | 难 | SQL 直接出报表 |
| 数据量 | 每条消息 2 次全文件 IO；1000 会话后明显退化 | 10 万级消息无压力 |

真实需求中，**会话消息是持续追加、定时任务运行记录是持续增长、同时存在 API 线程 + 调度线程 + Agent 执行线程三类写入方**，这正是 JSON 最不擅长的场景。

### 6.2 为什么是 SQLite 而不是 PostgreSQL

- 当前部署为单容器单进程（`deploy/backend/Dockerfile:109` 的 `CMD uvicorn`，`deploy/README.md:242` 明确 worker=1），无独立 DB 服务；
- SQLite WAL 支持"多读单写"，本项目写入是低频小事务（一轮对话一次提交、一次运行一条记录），单写完全够用；
- 零运维、随数据卷持久化，符合"一条 `docker compose up` 可用"的产品形态；
- 用 SQLAlchemy + `DATABASE_URL` 抽象，规模化时切 PostgreSQL 不需要改业务代码；
- Milvus Lite / Chroma 已是嵌入式存储，同一部署哲学。

**触发升级到 PostgreSQL 的条件**（写入 `doc` 作为决策记录）：
1. 需要多副本/多 worker 横向扩展；
2. 会话消息需要全文检索（PG `tsvector`）或跨租户分析；
3. 日运行记录 > 50 万或需要 BI 直连；
4. 需要行级权限/多租户强隔离。

### 6.3 SQLite 配置基线

```python
# 每个连接必须设置
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA foreign_keys=ON;
PRAGMA busy_timeout=5000;

# engine 参数（connect_args 仅 SQLite 使用；PostgreSQL 不传）
create_engine(url, connect_args={"check_same_thread": False, "timeout": 30},
              pool_pre_ping=True)
```

- Session 工厂：`sessionmaker(bind=engine, expire_on_commit=False)`；
- 线程内使用 `with SessionLocal() as db:`，**不跨线程共享 Session**；
- 写事务使用短事务 + 重试（`SQLITE_BUSY` 最多重试 3 次，指数退避）；
- `alembic` 配置 `render_as_batch=True`（SQLite 不支持大多数 ALTER）。

## 7. 数据模型（DDL 概要）

```sql
-- 会话
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,                 -- uuid4 hex
  mode TEXT NOT NULL CHECK (mode IN ('chat','work')),
  title TEXT NOT NULL DEFAULT '',
  team_id TEXT REFERENCES teams(id) ON DELETE SET NULL,
  config_json TEXT NOT NULL DEFAULT '{}',   -- 能力开关、模型、skills
  owner TEXT,                          -- 预留多用户
  archived INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE INDEX idx_sessions_mode_updated ON sessions(mode, updated_at DESC);

-- 消息（seq 保证顺序；steps/files 为展示用 JSON）
CREATE TABLE messages (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  run_id TEXT REFERENCES runs(id) ON DELETE SET NULL,
  seq INTEGER NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('user','assistant','system','tool')),
  content TEXT NOT NULL DEFAULT '',
  steps_json TEXT NOT NULL DEFAULT '[]',
  files_json TEXT NOT NULL DEFAULT '[]',
  meta_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  UNIQUE(session_id, seq)
);

-- 团队
CREATE TABLE teams (
  id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE,
  description TEXT NOT NULL DEFAULT '',
  prompt_prefix TEXT NOT NULL DEFAULT '',
  strategy TEXT NOT NULL DEFAULT 'none'
    CHECK (strategy IN ('none','sequential','router')),
  enabled INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE team_skills (
  team_id TEXT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  skill_name TEXT NOT NULL, position INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (team_id, skill_name)
);

-- Skill 元数据（文件系统仍是内容真相，DB 存索引与启停用状态）
CREATE TABLE skills (
  name TEXT PRIMARY KEY, description TEXT NOT NULL DEFAULT '',
  source TEXT NOT NULL CHECK (source IN ('builtin','custom')),
  path TEXT NOT NULL, frontmatter_json TEXT NOT NULL DEFAULT '{}',
  enabled INTEGER NOT NULL DEFAULT 1, updated_at TEXT NOT NULL
);

-- 定时任务
CREATE TABLE scheduled_tasks (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, prompt TEXT NOT NULL,
  mode TEXT NOT NULL DEFAULT 'work' CHECK (mode IN ('chat','work')),
  plan_first INTEGER NOT NULL DEFAULT 0,
  team_id TEXT REFERENCES teams(id) ON DELETE SET NULL,
  skills_json TEXT NOT NULL DEFAULT '[]',
  enable_json TEXT NOT NULL DEFAULT '{}',   -- mcp/rag/web/reflection/mcp_servers
  schedule_kind TEXT NOT NULL CHECK (schedule_kind IN ('cron','interval')),
  cron_expr TEXT, interval_seconds INTEGER, timezone TEXT NOT NULL DEFAULT 'Asia/Shanghai',
  enabled INTEGER NOT NULL DEFAULT 1,
  allow_unattended_tools INTEGER NOT NULL DEFAULT 0,
  allow_dangerous_tools INTEGER NOT NULL DEFAULT 0,
  daily_run_limit INTEGER NOT NULL DEFAULT 100,
  next_run_at TEXT, last_run_at TEXT, last_status TEXT NOT NULL DEFAULT 'never',
  run_count INTEGER NOT NULL DEFAULT 0,
  consecutive_failures INTEGER NOT NULL DEFAULT 0,
  backoff_until TEXT, last_error TEXT,
  delivery_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
-- cron 与 interval 二选一（CHECK 约束见 migrations）

-- 运行账本（手动 / 定时 / API 统一）
CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  task_id TEXT REFERENCES scheduled_tasks(id) ON DELETE SET NULL,
  session_id TEXT REFERENCES sessions(id) ON DELETE SET NULL,
  trigger TEXT NOT NULL CHECK (trigger IN ('manual','schedule','api')),
  scheduled_for TEXT,                  -- 计划槽位，手动为 NULL
  status TEXT NOT NULL CHECK (status IN
    ('queued','running','awaiting_approval','success','failed','skipped','interrupted','rejected')),
  plan_json TEXT, meta_json TEXT NOT NULL DEFAULT '{}',
  started_at TEXT, finished_at TEXT, duration_ms INTEGER,
  result_summary TEXT, error TEXT, files_json TEXT NOT NULL DEFAULT '[]',
  created_at TEXT NOT NULL,
  UNIQUE (task_id, scheduled_for)      -- 幂等键（SQLite 中 NULL 不冲突，符合手动运行语义）
);
CREATE INDEX idx_runs_task_started ON runs(task_id, started_at DESC);
CREATE INDEX idx_runs_status ON runs(status);

-- 事件回放（替代 JSONL）
CREATE TABLE run_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL, type TEXT NOT NULL,
  payload_json TEXT NOT NULL DEFAULT '{}', created_at TEXT NOT NULL,
  UNIQUE(run_id, seq)
);

-- 调度租约（多进程防重）
CREATE TABLE system_locks (
  name TEXT PRIMARY KEY, owner TEXT NOT NULL,
  expires_at TEXT NOT NULL, renewed_at TEXT NOT NULL
);
```

**设计说明**

- **Skill 内容仍在文件系统**：Agent 通过 `read_file` 读 `SKILL.md`，不便塞进 DB；DB 只做元数据索引与启停用状态，启动时同步（`source=builtin|custom`）。
- **`skills_json` 用于任务配置**：任务与技能是弱关联且无需反向查询；团队才用关联表（需要"Skill 被哪些团队引用"）。
- **`runs` 统一账本**：手动运行也可观测，避免后续再建一套审计表。
- **`run_events` 入 DB**：支持分页、按类型过滤、级联删除；单事件 < 4KB，10 万行量级 SQLite 可承受。

## 9. 阶段划分（逐层递进）

| 阶段 | 主题 | 关键交付 | 依赖 |
| --- | --- | --- | --- |
| **一** | 数据基座 + 双模式 + 会话 | DB/Alembic、`ToolProfile`、sessions/messages/runs、chat/work、`plan_first` 后端状态机 | 无 |
| **二** | Skill 管理 + 团队 | 双目录 Skill、CRUD/导入导出、teams/team_skills、router 策略 | 一 |
| **三** | 定时任务 | scheduler_service、租约、幂等、运行记录/事件 | 一、二 |
| **四** | 前端整合 + Plan 审批 UI + 验收 | WorkView、PlanCard、`/runs/{id}/stream`、E2E、性能与文档 | 一~三 |

每阶段可独立上线；阶段一完成后即具备"双模式 + 多轮历史 + 运行审计"。

## 10. 非目标与风险

**非目标**：多用户/权限体系、Webhook/IM 投递、命令与脚本型定时载荷、分布式任务队列（Celery）、本地模型推理。

| 风险 | 缓解 |
| --- | --- |
| SQLite 写锁争用 | 短事务、批量提交（每轮对话一次）、`busy_timeout` + 重试、WAL |
| 多 worker 重复调度 | DB 租约（60s，20s 续约）；未持锁进程只提供 API |
| 定时任务成本失控 | 每日运行上限、全局并发信号量、失败退避、UI 显式确认 |
| Plan 审批状态丢失 | 计划与 run 同表落库，重启后可继续审批 |
| 历史回放破坏协议 | 只回放 user/最终 assistant；单测覆盖 tool_calls 场景 |
| Skill zip 路径穿越 | 逐条校验 zip 成员，拒绝绝对路径与 `..`；大小/数量上限 |
| 迁移失败 | Alembic 版本化 + 启动前 upgrade + 备份文件（SQLite `VACUUM INTO`） |

## 11. 验收总纲

1. `pytest` 全绿（原 40 + 新增 ≥ 55）；
2. 双模式行为差异有自动化断言（工具集合、迭代上限、历史策略）；
3. 定时任务在重启后不重复、不丢失，手动/定时运行均有完整 event 回放；
4. 容器化部署下 E2E 五场景通过（详见 04）；
5. 迁移可在空库与旧库上重复执行（幂等）。
