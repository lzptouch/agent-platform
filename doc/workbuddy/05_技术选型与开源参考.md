## 2. 定时任务：OpenClaw cron 的启示

OpenClaw（开源，WorkBuddy 技能生态兼容）的 cron 实现要点：

| 设计点 | OpenClaw 做法 | 本项目采纳 |
| --- | --- | --- |
| 任务定义 | job 含 `schedule`（cron/at/every）、`payload`（agentTurn/systemEvent）、`delivery`、`sessionTarget` | 采用：`schedule_kind + payload=agentTurn + session 关联`；`delivery` 只留字段不实现 |
| 执行上下文 | 支持 isolated（独立会话）与 main（主会话） | 采用：定时任务默认独立会话，避免污染用户对话；`session_id` 记录便于回看 |
| 运行历史 | 每次运行有 status/duration/error，支持查询 | 采用：`runs` + `run_events` |
| 等待完成 | `cron run --wait` / `run-now --wait` | 采用：`run-now?wait_seconds=` |
| 错过触发 | **不重放**，直接等下一次；避免重启后雪崩 | 采用：仅 5 分钟宽限内补一次，其余记 `skipped(missed)` |
| 失败处理 | 记录错误，连续失败告警 | 采用 + 指数退避 |
| 会话隔离 | 每个 job 独立 session，可查看历史 | 采用 |

> 依据：https://docs.openclaw.ai/zh-CN/automation/cron-jobs

**不采纳的部分与原因**

| 特性 | 原因 |
| --- | --- |
| `systemEvent` 型载荷（直接注入主会话） | 本项目无 IM 网关，缺少送达通道 |
| `delivery`（WhatsApp/Telegram 等） | 非目标，保留字段 |
| 跨设备节点执行 | 单机部署，无节点概念 |

## 3. 会话与运行模型：Dify 的启示

Dify 的关系模型可概括为：`conversations`（会话）→ `messages`（消息，含 tokens/耗时/反馈）→ `workflow_runs`（一次执行，含 status/inputs/outputs/elapsed_time/total_tokens）。

采纳点：

1. **消息与运行解耦但可关联**：消息用于展示，run 用于审计与重试；本项目 `messages.run_id → runs.id`。
2. **run 有完整状态机**：`running/succeeded/failed/stopped`；本项目扩展 `awaiting_approval/skipped/interrupted`。
3. **统计字段落库**（耗时/tokens）：便于后续成本分析；本项目先落 `duration_ms`、`files_json`，tokens 预留 `meta_json`。
4. **消息分页按 seq 游标**，避免 offset 深翻页。

> 依据（schema 分析）：https://tsight.io/articles/18557136
> 参考实现仓库：https://github.com/langgenius/dify

**不采纳**：Dify 的多租户/工作流 DSL/数据集权限体系——本项目无多租户诉求，避免过度设计。

## 4. 数据库选型

### 4.1 候选对比

| 方案 | 写入并发 | 查询能力 | 运维成本 | 适用判断 |
| --- | --- | --- | --- | --- |
| JSON 文件（v1） | 差（全文件重写） | 无 | 极低 | ❌ 会话/run 高频追加场景不适用 |
| **SQLite + WAL** | 单写多读，短事务足够 | 索引/分页/聚合/JOIN | 极低（单文件） | ✅ 当前单机部署 |
| PostgreSQL | 强 | 强（含全文检索/JSONB） | 中（独立服务/备份/连接池） | 触发条件满足时升级 |
| MySQL | 强 | 强 | 中 | 团队栈偏好时才选，无额外优势 |
| DuckDB | 分析型，写并发弱 | OLAP 强 | 低 | ❌ OLTP 不适用 |
| Redis | 缓存 | 有限 | 低 | 仅用于未来的实时事件广播 |

### 4.2 结论与量化依据

- 本项目单轮对话写入：1 条 user + 1 条 assistant + 约 10~40 条 event；一轮约 20~50 行小 INSERT，SQLite 单写可轻松支撑（WAL 下顺序写 > 1 万 TPS 量级，远高于需求）。
- 读取：会话列表需要 `mode + updated_at` 排序分页；消息需要 `session_id + seq` 游标；运行历史需要 `task_id + started_at` 排序——都需要索引，JSON 无法提供。
- 一致性：删除会话需级联删除消息；定时任务删除后 run 需保留——外键语义明确。
- 迁移：Alembic 版本化，避免 v1 那种"手写 JSON 兼容分支"。
- 部署：`data/app.db` 落在现有命名卷 `agent-platform-data`，`docker compose up` 不变；在线备份用 `VACUUM INTO`。

### 4.3 何时升级 PostgreSQL（写入决策记录）

满足任一条件即评估迁移（SQLAlchemy 下仅改 `DATABASE_URL` + 处理 SQLite 特有 DDL）：

1. 部署多副本或 `uvicorn --workers > 1`（跨进程写锁与租约仍需 DB 级方案）；
2. 需要会话全文检索、跨用户统计、BI 直连；
3. 单库 > 5GB 或日增 run > 1 万；
4. 引入多租户与行级权限。

> 参考资料：
> - SQLite vs PostgreSQL（并发/场景）：https://betterstack.com/community/guides/databases/postgresql-vs-sqlite/
> - SQLite WAL 与并发写：https://intellizu.com/articles/sqlite-vs-postgresql
> - SQLAlchemy 2.0 ORM 文档：https://docs.sqlalchemy.org/en/20/orm/
> - Alembic batch 模式（SQLite ALTER 限制）：https://alembic.sqlalchemy.org/en/latest/batch.html

### 4.4 为什么不用 SQLModel

SQLModel 更薄，但在 Alembic 自动生成、复杂索引/约束、`render_as_batch`、JSON 类型方面不如纯 SQLAlchemy 成熟；项目已有 Pydantic schema 层，ORM 与 schema 分离更清晰。

## 5. 调度器选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **APScheduler 3.x（BackgroundScheduler）** | 进程内、零依赖、支持 cron/interval、`misfire_grace_time`/`max_instances`/`coalesce` | 无跨进程协调、无持久化执行保证 | ✅ 当前单机；配 DB 租约 + 自有表 |
| Celery + beat | 分布式、重试/队列成熟 | 需 broker（Redis/RabbitMQ），部署与运维显著变重 | 规模化后再评估 |
| arq / RQ | 轻量 Redis 队列 | 同样引入 Redis | 不必要 |
| Temporal | 工作流级可靠性 | 重量级、学习成本高 | 过度设计 |
| 系统 cron + CLI | 简单 | 无法在 UI 管理、无运行记录、容器内不便 | ❌ |

**关键实现约束**

- `max_instances=1` 保证同任务串行；`coalesce=True` 避免堆积；`misfire_grace_time=300`。
- **不使用** `SQLAlchemyJobStore`：任务定义已在业务表中，双写会不一致；启动时按表重建 job（`replace_existing=True`）即可。
- 多进程：DB 租约（`system_locks`）+ 续约；租约丢失主动停调度。
- 幂等：`UNIQUE(task_id, scheduled_for)`；SQLite 中 `NULL` 不参与唯一冲突，正好区分手动运行。

> 依据：https://apscheduler.readthedocs.io/en/3.x/userguide.html

## 8. 调研结论摘要

1. **必须上数据库**：会话/消息/运行记录是典型 OLTP 追加型数据，JSON 在并发、查询、一致性三方面都不达标；SQLite+WAL 是当前部署形态下的最优解，且保留 PostgreSQL 升级路径。
2. **模式应对齐 WorkBuddy 三态**：chat（Ask）/ work（Craft）/ work+plan_first（Plan），Plan 必须有审批状态。
3. **调度器用 APScheduler + 自有任务表 + DB 租约**，不用 jobstore 双写，不重放错过槽位，靠唯一键保证幂等。
4. **Skill 内容留文件系统、元数据入 DB**，既兼容社区 SKILL.md 生态，又获得管理能力。
5. **运行账本统一**（手动/定时/API），避免后续再补审计表。
