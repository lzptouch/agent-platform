# 阶段 3：定时任务 —— 代码修改计划与测试计划

> 前置：阶段 1（runs / run_events / RunExecutor）、阶段 2（team / skills）
> 交付：APScheduler 调度、DB 唯一真相、租约防重、幂等触发、失败退避、运行历史与事件回放
> 影响文件：新增 4 个，修改 6 个

---

## 1. 目标

1. cron / interval 两类调度的任务 CRUD，支持启停用、立即执行（可选等待）。
2. 每次触发写 `runs`（统一账本）+ `run_events`（可回放），任务统计可查询。
3. **重启不丢、不重复**：表为唯一真相 + 启动重建 job + `(task_id, scheduled_for)` 唯一键。
4. **多进程/多副本只允许一个调度者**：DB 租约锁。
5. 无人值守安全：work 模式必须显式确认；`execute_bash` 需二次开关；每日次数上限。

## 2. 调度器设计（关键决策）

### 2.1 为什么不用 APScheduler 的 `SQLAlchemyJobStore`

| 方案 | 问题 |
| --- | --- |
| 只用 jobstore | 任务定义与业务字段（prompt/team/enabled/统计）混在 pickle 的 job 里，无法 SQL 查询、无法平滑迁移、无法在前端编辑 |
| 表 + jobstore 双写 | 两处状态，编辑/启停/删除必须保证原子一致，容易出现孤儿 job 或丢失任务 |
| **表为唯一真相 + 启动重建 job**（选用） | `add_job(..., id=task.id, replace_existing=True)`；编辑即"改表 + 重建该 job"；重启时全量重建。逻辑简单，可测试 |

### 2.2 进程模型与租约

```
uvicorn(单进程) ── SchedulerService.start()
                    ├─ acquire lease(system_locks, name='scheduler', ttl=60s)
                    ├─ 成功 → 启动 BackgroundScheduler + 续约线程(20s)
                    └─ 失败 → 只提供 API（多副本中的从节点）

job 触发 → _fire(task_id, scheduled_for)
             ├─ 全局并发信号量(默认 2，等待队列上限 10)
             ├─ INSERT run (UNIQUE task_id+scheduled_for) ← 幂等闸门
             └─ RunExecutor.execute_sync(...) → 更新 run / events
```

- 租约实现：`INSERT OR IGNORE`，随后 `UPDATE system_locks SET owner=?, expires_at=? WHERE name=? AND (owner=? OR expires_at < ?)`，受影响行数=1 即获得。
- 续约线程 daemon；续约失败 3 次 → 主动 `scheduler.shutdown()` 并停止接单（分裂脑保护）。
- 单进程部署时同样生效，为未来 `--workers N` 预留。

### 2.3 时间与触发语义

- 全库时间存 UTC ISO8601；任务带 `timezone`（默认 `Asia/Shanghai`），cron 在该时区解释。
- `misfire_grace_time=300`、`coalesce=True`、`max_instances=1`。
- **槽位（scheduled_for）计算规则**（幂等键，必须确定性，不能依赖"任务入参时间"）：
  - `cron`：`now.astimezone(task.tz).replace(second=0, microsecond=0)` 的 UTC ISO 值（cron 最小粒度为分钟）；
  - `interval`：以 `task.created_at` 为锚点，`idx = floor((now - created_at) / interval)`，`slot = created_at + idx * interval`；即使重启、补跑、并发触发，同一周期算出的 slot 相同；
  - `manual`：`scheduled_for = NULL`（SQLite 唯一索引不约束 NULL）。
- **重启策略**：不重放错过的槽位。启动时重算 `next_run_at`；若错过的槽位在 5 分钟宽限内则由 APScheduler 补一次（同一 slot 仍受唯一键保护），否则记一条 `skipped(reason=missed)`（便于审计）后继续。
- 手动运行 `scheduled_for=NULL`（SQLite 唯一索引对 NULL 不冲突），不占用计划槽位。

### 2.4 超时

Agent 循环是同步阻塞的，无法安全强杀线程。采用**协作式超时**：

- `RunExecutor.execute_sync(..., deadline=now+timeout)`；
- `AgentService._stream_loop` 每轮开始检查 `time.monotonic() > deadline`，超时则中止并 yield `error("timeout")`；
- 外层 watchdog 线程在 `timeout + 30s` 仍未结束时把 run 标为 `failed(timeout_watchdog)`（记录可能仍在跑，UI 标注"已超时"）；
- 默认 `schedule_run_timeout=600`，上限 3600。

### 2.5 失败与退避

- 失败不影响任务启用状态（避免静默停摆），但累加 `consecutive_failures`；
- 连续失败 ≥3 次时 `backoff_until = now + min(60m, 30s * 2^(n-2))`，退避期间的计划触发写 `skipped(reason=backoff)`；
- 成功一次即清零；连续失败 ≥5 次在列表接口返回 `health="degraded"` 供 UI 告警。

### 2.6 无人值守安全

| 风险 | 控制 |
| --- | --- |
| work 任务自动写文件/执行代码 | 必须 `allow_unattended_tools=true`，否则 422 |
| `execute_bash` 任意命令 | 默认在无人值守任务中**剔除**；需额外 `allow_dangerous_tools=true` |
| 成本失控 | `daily_run_limit`（默认 100）、全局并发 2、超时 600s |
| 提示词注入导致越权 | 定时任务不支持切换 MCP 写类 Server（仅只读标记的 Server 可用） |
| 任务无限增生 | 单实例最多 200 个任务（软限制，创建时 409） |

### 3.4 新增 `backend/app/services/scheduler_service.py`

```python
class SchedulerService:
    def __init__(self, run_executor, db_factory=SessionLocal): ...
    # 生命周期
    def start(self) -> None        # 租约 → 恢复中断 → 重建 job → 启动续约
    def shutdown(self, wait=False)
    # 同步
    def sync_task(self, task_id)   # 新增/更新/启停后调用
    def remove_task(self, task_id)
    def recover(self)              # running → interrupted（宽限 5 分钟）
    # 业务
    def create(payload) -> ScheduleOut
    def update(task_id, payload) -> ScheduleOut
    def delete(task_id)            # 删任务；runs 保留（task_id 置 NULL）
    def set_enabled(task_id, enabled)
    def run_now(task_id, wait_seconds=0) -> RunOut
    def list_runs(task_id, page, page_size)
    # 内部
    def _fire(self, task_id: str, scheduled_for: str | None)
    def _cleanup(self)             # 每日 03:30 清理
```

**`_fire` 详细步骤**

1. `with db_session()`：读取任务；不存在/禁用 → 返回。
2. 每日配额：`SELECT count(*) FROM runs WHERE task_id=? AND date(started_at)=today AND status IN (...)` ≥ limit → 写 `skipped(reason=daily_limit)`。
3. 退避检查：`backoff_until > now` → 写 `skipped(reason=backoff)`。
4. `INSERT run(status=queued, scheduled_for=...)`；捕获 `IntegrityError` → 直接返回（幂等）。
5. 全局信号量 `acquire(blocking=False)` 失败 → 状态 `skipped(reason=busy)`。
6. `RunExecutor.execute_sync(...)`（内部把 run 置 running → success/failed，写 events）。
7. `UPDATE task`：`last_run_at/last_status/run_count/next_run_at/consecutive_failures/backoff_until`。
8. 释放信号量。

**`start()` 顺序**

1. 若 `scheduler_enabled=False` → 只读模式（测试/从节点）；
2. acquire lease 失败 → warn + 返回（`health.role="standby"`）；
3. `recover()`（先恢复，避免旧 running 永远悬挂）；
4. 遍历 enabled 任务 `add_job`；
5. 注册清理 job；
6. 启动续约线程。

### 3.6 修改 `run_executor.py`

- `execute_sync(prompt, *, trigger, task_id, scheduled_for, deadline, config...)`：

## 4. 测试计划

### 4.1 校验与 CRUD（`test_schedule_api.py`）

| 用例 | 断言 |
| --- | --- |
| cron 合法 | 201；`next_run_at` 非空；`schedule_text` 可读 |
| cron 非法 | 422（如 `* * *`、`61 * * * *`） |
| 二选一 | 同传/都不传 → 422 |
| 时区非法 | 422 |
| interval < 60 | 422 |
| work 未确认 | `enabled=true` 且未 `allow_unattended_tools` → 422 |
| chat + plan_first | 422 |
| 更新重建 job | 修改 cron 后 `next_run_at` 变化，job 数不变 |
| 删除 | 任务 404，历史 runs 保留且 `task_id=NULL` |
| 软上限 | 第 201 个任务 → 409 |

### 4.2 调度核心（`test_scheduler.py`，全部 mock `RunExecutor`）

| 用例 | 断言 |
| --- | --- |
| 租约互斥 | 同一 DB 启动两个 SchedulerService → 仅一个 `role=primary`，另一个 standby 且无 job |
| 租约过期接管 | 手工把 `expires_at` 改为过去 → 第二个实例续约后接管 |
| 幂等 | 相同 `(task_id, scheduled_for)` 调 `_fire` 两次 → 只 1 条 run |
| 手动运行 | `scheduled_for=NULL` 可多次执行 |
| 每日上限 | 预置 limit 条 run → 再触发记 `skipped(daily_limit)` |
| 退避 | 连续 3 次失败 → `backoff_until` 生效；期间触发 skipped(backoff)；成功后清零 |
| 并发上限 | 信号量占满 → 新触发 `skipped(busy)`，不丢记录 |
| 中断恢复 | 预置 `running` 旧 run → `recover()` 后为 `interrupted` |
| 启动重建 | 建 3 个 enabled 任务 → `start()` 后 job 数=3；禁用任务不注册 |
| 关闭 | `shutdown()` 后 job 全部移除，租约释放 |
| 超时 | mock 执行阻塞 > deadline → run 标 `failed(timeout_watchdog)`（watchdog 路径） |
| 清理 | 预置超期 run → `_cleanup()` 后仅保留最近 N 条 |

### 4.3 真实时钟集成（`test_scheduler_integration.py`，标记 `slow`）

- `interval_seconds=60` 不便于测试 → 测试专用允许 1s（仅当 `settings.debug=True`，或直接构造 `IntervalTrigger(seconds=1)` 注入）；
- 创建任务 → 等待 ≤5s → 至少 1 条 `success`；
- `toggle off` → 3s 内不再新增；
- 重启（shutdown + 新实例 start）→ 不重复执行同一槽位。

### 4.4 事件回放（`test_run_events.py`）

- 定时运行产生 ≥10 条事件 → `GET /runs/{id}/events?after_seq=5` 返回后续条目；
- 级联删除任务/会话后事件仍可通过 run 访问（run 保留）；
- 删除 run（提供管理接口时可）→ 事件级联删除。

### 4.5 安全测试

- zip 导入与定时任务组合：导入含恶意 bash 的 Skill → work 任务未开 `allow_dangerous_tools` 时 `execute_bash` 不在工具集；
- chat 模式定时任务工具集只读；
- 提示词包含 `$(rm -rf /)` 不改变工具策略（仅影响模型输出）。

### 4.6 验收标准（DoD）

- [ ] 单实例下单进程调度，重启后 job 自动恢复且不重复；
- [ ] 两个实例同时启动时只有一个 primary（日志与 health 可验证）；
- [ ] `run-now` 返回 run_id，10 秒内可查到 running/success；
- [ ] 失败任务有 `last_error` 与退避，不静默停摆；
- [ ] 运行历史可按任务分页查询，事件可回放；
- [ ] 新增测试 ≥ 30 条，原测试全绿；`slow` 用例可通过 `-m "not slow"` 跳过。
