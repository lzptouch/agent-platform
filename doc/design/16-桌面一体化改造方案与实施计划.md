## 〇、摘要

### 0.1 三句话结论

1. 项目**当前是两个运行时拼装的产品**：Electron 壳（Node）+ Python FastAPI sidecar。安装包 ~800MB 中 **670MB 是 portable Python**。
2. 本次改造 = **用 TypeScript 重写后端，让软件只剩一个运行时**（Electron/Node），同时**彻底删除 Web 部署面**（nginx / compose / CORS / API Key / 浏览器访问）与 **Docker 编排层**。
3. 数据层**本来就是本地文件**（SQLite + Milvus Lite），所以「Docker 数据库本地化」的真实工作量是**移除 Docker 并把数据统一到 `userData`**，外加**替换 Milvus Lite 向量层**（体积主因，且 JS 生态无等价物）。

### 1.1 原始需求拆解

### 1.2 五项决策的落地（v2 核心）

#### Q1 · 「不需要 web 端的任何内容」——先把一个事实说清

> 用户原话：「**不需要 web 端的任何内容**，在**保证不影响桌面端 UI 和相关功能**的情况下」

`frontend/web/vue-element-plus/` **不是**独立 Web 产品，它是 **Electron 窗口里渲染的界面本体**。删掉它 = 桌面端没有界面。因此本方案把「web 端」严格限定为**部署与访问形态**，全部删除：

| 「Web 端」的具体所指 | 处置 |
| --- | --- |
| `deploy/nginx/`、`deploy/frontend/Dockerfile`、`deploy/backend/*`、`backend/Dockerfile` | **删除** |
| `docker-compose.yml`、`deploy/docker-compose.milvus.yml` | **删除** |
| `main.py` 的 `api_key_guard` 中间件（L154-175）+ `AGENT_API_KEY` + `CORS_ORIGINS` | **删除** |
| `tests/web/`（44 个浏览器 E2E 用例）、CI L2 `web-e2e` job | **删除** |
| `frontend/scripts/ui_probe/*.py` 中依赖浏览器的 Web 断言 | 重写为 Electron E2E |
| **「web」这个词本身** | 目录更名 `frontend/web/vue-element-plus/` → `apps/ui/` |

Vue 的业务代码**一行不改**（零改动论证见 §7.9），正好满足 Q1 后半句。

#### Q2 · 后端语言 = TypeScript

Electron 本身就是 Node 运行时；后端写成 TS 后与壳**共用同一份 Node**，`electron-builder` 一次打包，无需分发 Python。这是 Q2 原话「可以一起用 electron 打包」的直接落地。

#### Q3 · 「默认少数内置，更多从网络下载」→ 影响两个子系统

| 对象 | 默认内置 | 按需下载 |
| --- | --- | --- |
| **Python 运行时** | 一个**最小运行时**（Python 3.11 embeddable，仅标准库，~15MB）：保证 `execute_python` 基础执行可用 | `pandas` / `matplotlib` / `reportlab` 等，按 Skill 需求从 PyPI 下到 `userData/runtime/python-packages/` |
| **Skill** | 内置**少数核心 4 个**：`skill-creator`、`data-analysis`、`pdf`、`frontend-design` | `marketing-materials`、`ralph-loop` 及社区 Skill，从 Skill 市场 / URL 安装 |

详见 §7.6、§7.7。

#### Q4 · RAG 保留功能、不保留数据

- **保留**：`rag_query` / `rag_ingest` 工具、`/api/v1/rag/*` 4 个端点、混合检索语义、台账幂等。
- **不保留**：旧 `backend/data/milvus.db`（3.5MB）**不迁移、不解析**。
- **新库**：`userData/data/vectors/` 从空开始；用户点「重新入库」把 `userData/data/pdf/` 下的 PDF 重灌。
- 收益：**彻底摆脱 Milvus Lite 格式依赖**，向量层可自由重写（§7.1）。

#### Q5 · 「重写，所有都进行重写」

| 层面 | v1 策略 | **v2 策略** |
| --- | --- | --- |
| 后端 28,569 行 Python | 同构移植（保函数边界/命名/注释，逐行翻译） | **Clean-room 重写**：只冻结**外部契约**（HTTP / SSE / DB schema / 文件布局），内部按 TS/Node 惯用法重新设计 |
| `pdf` Skill 的 7 个 Python 脚本 | 保留 Python，走可选轨道 | **全部重写为 TS**（`pdf-lib` + `pdfjs-dist`），Skill 内不再有 Python |

**收益**：可顺手清掉 Python 侧已识别技术债（§3.2）。**代价**：行为漂移风险高于移植 → **必须**用 §6.2 四道闸门约束。

### 1.3 三项交付纪律（v2.1 新增，硬约束）

> 「重写」本身就是最高风险的做法，因此**质量保证不能只靠代码本身**，必须靠纪律。

#### D1 · 功能保持一致——先测现状，再测新体

**问题**：不做基线，就无法证明「改造后功能一致」。人的记忆和文档都不足以作为验收依据。

**做法**（时间轴）：

```
改造前（P0）                   改造中（每阶段）            改造后（P9）
─────────────                 ─────────────              ─────────────
全量功能清单（F-01..F-NN）  →  该阶段涉及的功能项         →  全量重跑基线命令
全量测试执行 + 逐项结论     →  即时回归对比              →  逐项对比矩阵（§12.3）
基线证据归档                →  增量报告                  →  最终等价性判定
```

**「一致」的判定标准**（三层，缺一不可）：

| 层 | 判定对象 | 通过条件 |
| --- | --- | --- |
| L1 契约层 | HTTP 路径/方法/字段/状态码、24 事件、22 表、工具签名 | **零差异**（§6.2 四闸门） |
| L2 行为层 | 每个功能项的实际输出/副作用/DB 变更 | 输出语义等价；副作用集合一致；允许的形式差异须**逐条书面豁免**（§12.3） |
| L3 体验层 | 19 个视图渲染、交互可完成 | 视觉 diff < 2%；关键操作路径可走通 |

**明确不可接受**：某功能「新版本没做」「先砍掉后面补」「能用但不完全一样」——都必须登记为**缺陷**而非差异，且在 M3 前清零。

#### D2 · 测试过程与结果必须记录

**「测过了」不算数**，必须留下可复现、可审计的证据链：

```
doc/test-runs/
└── <阶段>-<日期>/
    ├── README.md            ← 本次测试范围、环境、结论摘要（人读）
    ├── environment.json     ← OS/Node/Electron/commit(人工填)/数据版本
    ├── commands.txt         ← 逐条可复制粘贴的复现命令
    ├── raw/                 ← 原始输出（stdout/stderr/日志/报告文件）
    │   ├── pytest.log
    │   ├── vitest.log
    │   ├── smoke.log
    │   └── e2e-*.log
    ├── results.csv          ← 逐用例：ID、名称、期望、实际、结论、耗时
    └── screenshots/         ← 视觉回归基线/对比图（如适用）
```

**记录粒度要求**：**到「用例」这一级**，不接受只写「后端测试全过」。每行 `results.csv` 必须是可追溯的单条断言级结果。

#### D3 · 不提交任何代码，由人工提交

| 禁止 | 允许 |
| --- | --- |
| `git add` / `git commit` / `git push` / `git merge` / `git rebase` / `git tag` | **读取**：`git status` / `git diff` / `git log` / `git show` |
| `git checkout -b` / `git branch -d` / `git stash` | 在工作区**创建/修改/删除文件** |
| `git remote add/set-url` / 改 `.git/config` / 改 hooks | 运行测试、构建、安装依赖 |
| `--amend` / `--force` / 跳过 hooks | 生成报告、写入 `doc/test-runs/` |

**替代做法**：每个阶段结束时输出「**待提交文件清单**」（§18.3），列出新增/修改/删除的文件及一句话说明；由人工审阅后自行提交。

**理由**：重写会产生数百个文件变更，机器自动提交会把「明确的意图」变成「不可审阅的一坨」；人工提交能保证每个 commit 语义单一、可 review、可回滚。

### 2.3 桌面壳 sidecar 编排链路（现状）

```
双击 Agent Desktop
  ↓
src/main/index.ts
  ├─ 单实例锁 → reclaimOrphan（清孤儿 sidecar）→ 托盘 + 启动页(splash.html)
  ├─ backend.ts:150   spawn(python, ["-m","app.desktop.launcher"])
  │     env: AGENT_DESKTOP=1 / AGENT_DESKTOP_TOKEN / AGENT_DESKTOP_BOOTSTRAP_NONCE
  │          / AGENT_DATA_DIR / AGENT_FRONTEND_DIST / PLAYWRIGHT_BROWSERS_PATH
  │     POSIX: detached=true（独立进程组，退出整组回收）
  ├─ launcher.py:69   sock.bind(("127.0.0.1", 0)) → OS 分配端口
  ├─ launcher.py:80   打印 "AGENT_DESKTOP_READY {json}"（端口 + 路径）
  ├─ backend.ts:192   解析握手 → 拿 port
```

**需改动的耦合点只有 4 个**：

| 耦合 | 位置 | 改法 |
| --- | --- | --- |
| 解释器路径解析 | `paths.ts` `resolvePython()` | → `resolveServerEntry()` |
| spawn 命令 | `backend.ts:150` | → `utilityProcess.fork()` |

### 4.3 进程模型决策

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| **✅ `utilityProcess.fork()`（采纳）** | Electron 官方 Node 子进程；`process.parentPort` 通信；可加载原生模块 | 崩溃隔离；**现有 `backend.ts` 监督器几乎原样复用**；握手协议不变 |
| 主进程内直接跑 | 壳内 `import` 后端模块 | 最简单，但 Agent 循环/PDF 解析会**阻塞 UI 事件循环** → 需 worker_threads，等于重新实现隔离 |
| `child_process.fork` | 普通 Node 子进程 | 几乎等价，但 Electron 官方推荐 `utilityProcess`（生命周期/崩溃语义更好） |

**采纳 `utilityProcess`**：保留「sidecar + 握手 + 探活 + 孤儿回收 + 进程组回收」全部机制，仅把解释器换成 Node 入口。

> 注意：`utilityProcess` 的 stdout/stderr 是**事件**（`child.stdout.on('data')`），不是 `spawn` 的流；`killTree` 用 `child.kill()`，Windows 保留 `taskkill /T` 兜底。

## 五、技术选型

### 5.1 后端语言：TypeScript（Q2 已定）

| 候选 | 评估 |
| --- | --- |
| **✅ TypeScript / Node（Electron 33 → Node 20.18）** | 与 Electron 同运行时；Zod schema **前后端共享**；vitest 全线统一；TS 类型可当「可执行契约」 |
| Rust 重写 | 性能过剩；28.5k 行重写成本极高 |
| Go | 同上，且无法与前端共享类型 |
| 保留 Python | 见 §5.5 方案 B（已因 Q2 排除，仅留作风险退路） |

> **Node 版本约束**：Electron 33 内置 Node 20.18 → `node:sqlite`（Node 22.5+ 才有）**不可用**，故必须用原生模块方案。若 P7 阶段愿意升级 Electron 至 37+（Node 22），可评估改用 `node:sqlite` 消除原生依赖；**本方案默认不升级**（避免大版本升级引入的 API 变更风险）。

### 5.2 HTTP 框架

| 候选 | 评估 |
| --- | --- |
| **✅ Fastify 5** | 性能好；插件生态成熟（`@fastify/static`、`@fastify/multipart`）；TS 类型好；SSE 用 `reply.raw` |
| Hono | 更轻、更贴近 Web 标准；但生态与 Fastify 差距明显，SSE 中间件需更多手写 |
| Express 5 | 最保守，但类型与性能落后，SSE 需手动处理压缩/缓冲 |

**采纳 Fastify**。⚠️ **不要启用 `@fastify/compress`**（会缓冲 SSE）；或对 4 条 SSE 路由单独 `compress: false`。

### 5.3 ORM 与迁移

| 候选 | 评估 |
| --- | --- |
| **✅ Drizzle ORM + drizzle-kit** | TS 原生、类型好、`drizzle-kit generate` 出 SQL 迁移、SQLite 支持好 |
| Prisma | 引擎二进制需跨平台分发，Electron 打包多一层麻烦；冷启动较慢 |
| Kysely | 轻量无引擎，但无迁移工具，需自写 |

**采纳 Drizzle**。迁移策略：`drizzle-kit generate` 出 SQL，启动时由自研 `migrate.ts` 执行（自建 `__migrations` 表，不引第三方 runner）。

**SQLite 驱动**：

| 候选 | 评估 |
| --- | --- |
| **✅ better-sqlite3** | 同步 API、最快、生态最成熟；需 `@electron/rebuild` 重建 ABI + `asarUnpack` |
| `node:sqlite` | 需 Node 22+（Electron 37+），当前不可用 |
| `sql.js`(WASM) | 无原生依赖，但需手动持久化整库到文件，性能与数据安全差 |

**采纳 better-sqlite3**，并把「ABI 重建失败」列为 R5 风险（§13）。

### 5.4 向量检索（Q4 已定：数据不保留 → 可自由重写）

| 候选 | 体积 | 混合检索 | 评估 |
| --- | --- | --- | --- |
| **✅ 自研（SQLite BLOB + 内存 BM25）** | 0 额外 | ✅ 自实现 | 语料小（`milvus.db` 仅 3.5MB，<10k chunk）完全够用；零原生依赖；行为可控可测 |
| `sqlite-vec` | ~2MB（跨平台 .so/.dll/.dylib） | ❌ 无 BM25 | 需自建稀疏腿；原生扩展跨平台打包有坑 |
| `@lancedb/lancedb` | ~30MB（含 native binding） | ✅ 内置 FTS + 向量 | 能力最全，但引入原生绑定 + 体积回升 |
| Milvus Lite（现状） | 82MB + onnxruntime 75MB | ✅ 服务端 BM25 | JS 无等价物，**必须替换** |

详见 §7.1。

## 六、后端重写方案

### 6.1 重写原则（Q5：Clean-room，只冻结契约）

| # | 原则 | 具体含义 |
| --- | --- | --- |
| 1 | **契约冻结** | P0 阶段把 Python 侧的 OpenAPI / 事件协议 / 错误码 / 表 DDL 导出为 `contract/*`，作为**唯一验收基准**；重写期间不得修改契约 |
| 2 | **对外零差异** | 路径、方法、请求/响应字段、状态码、SSE 事件名与顺序、DB 表名列名、文件布局——**一律不变** |

| 4 | **行为补丁可记录但需单列** | 修正 Python 侧的缺陷（如 §2.9-⑥ 缺 `loop_detected`）时，必须**单独成 PR** 并登记，不能混在重写里 |
| 5 | **测试同源** | 629 个 pytest 用例**逐条**重写为 vitest，保持用例名与断言语义（用例名可映射，便于追溯） |
| 6 | **阈值常量集中** | §2.6 的 15 组阈值统一放 `shared/config.ts` 的一个 `LIMITS` 对象，禁止散落 |

### 7.1 RAG 向量层：Milvus Lite → 本地混合检索

#### 现状语义（必须等价）

```python
# services/rag/milvus_store.py
稠密：DashScope text-embedding-v3，1024 维，度量 IP
稀疏：Milvus 2.5 服务端 BM25 Function（text 自动分词，k1=1.5, b=0.75）
融合：WeightedRanker(sparse=0.7, dense=1.0)，limit=10
幂等：doc_id = sha256(路径 | 内容哈希)
```

#### 目标实现

```sql
-- <userData>/data/vectors/chunks.db
CREATE TABLE chunks (
  id         INTEGER PRIMARY KEY,
  doc_id     TEXT NOT NULL,        -- 幂等键
  seq        INTEGER NOT NULL,     -- chunk 序号
  text       TEXT NOT NULL,
  dense      BLOB NOT NULL,        -- Float32Array(1024)
  created_at TEXT NOT NULL
);
CREATE INDEX idx_chunks_doc ON chunks(doc_id);
```

**检索流程**（`domain/rag/search.ts`）：

1. `qDense = await embed(query)`（`openai` SDK → DashScope）
2. **稠密腿**：启动时把全部 `dense` 载入**扁平化 `Float32Array`**（避免逐行反序列化）→ 点积 Top-K
   - 规模：10k chunk × 1024 × 4B ≈ 40MB 内存；点积 ~10ms（放 Worker 线程）
3. **稀疏腿（BM25）**：
   - 分词：`Intl.Segmenter('zh', {granularity:'word'})`（Node 内置，**零依赖**，支持中文）
   - 倒排：`Map<token, postings[]>`，启动时从 `chunks.text` 构建，常驻内存；语料变更增量更新
   - 参数对齐 Milvus 默认 `k1=1.5, b=0.75`
4. **融合**：`score = 0.7 * minmax(bm25) + 1.0 * minmax(cosine)`
   > ⚠️ **唯一需仔细对齐处**：Milvus `WeightedRanker` 内部对两腿做 min-max 归一化，TS 侧必须实现同款。
5. **返回** `text[]`（与现状 `hybrid_search` 返回 `list[str]` 一致）

**索引抽象**（为将来规模增长预留）：

```ts
interface VectorIndex {
  upsert(docId: string, chunks: { text: string; dense: Float32Array }[]): Promise<void>;
  remove(docId: string): Promise<void>;
  search(query: string, topK: number): Promise<{ text: string; score: number }[]>;
}
// 实现：BruteForceIndex（先落地） → 后续可换 HNSW 而不动调用方
```

#### 入库幂等（`domain/rag/ingest.ts`）

保持 `services/rag/ingest.py` 语义：
- `rag_documents` 台账已有 → 跳过（不 embed、不写 chunk）
- 内容变了 → 先 `remove(doc_id)` 后入库
- `recreate=true` → 清台账 + 全量重灌

#### 验收

| 项 | 门槛 |
| --- | --- |
| 检索质量 | 固定 20 条测试 query，**Top-10 集合重合率 ≥ 0.9**（与 Python 侧对比，非逐位一致） |
| 幂等 | 同文档重复入库 3 次，chunk 数不变 |
| 性能 | 10k chunk 单次查询 < 150ms |
| 中文分词 | 中文 query 的 BM25 命中率 > 0 |

### 7.3 调度器：APScheduler → croner

| 能力 | APScheduler（现状） | 目标 |
| --- | --- | --- |
| Cron 触发 | `CronTrigger` | `croner`（标准 5 段 + 扩展） |
| Interval 触发 | `IntervalTrigger` | `croner` interval / `setTimeout` 链 |
| RRULE 触发 | 自研 `rrule.py`（356 行） | npm `rrule` |
| 持久化 job store | **不用**（job 只在内存，DB 只存业务状态） | 同 |
| 并发 | `max_instances` | 继续用 `run_executor` 槽位预算（调度槽 2） |
| 租约 / 幂等 / 退避 / 补跑 | **全部自研**（`system_locks` + `uq_runs_task_slot`） | **原样保留，不动** |

> 关键点：**APScheduler 只承担「什么时候唤醒」**，业务语义全是自研代码 → 替换触发器风险很低。

**实现骨架**：

```ts
// domain/scheduler/service.ts
async function tick(task: ScheduledTask) {
  const slot = await acquireLease(task.id);           // system_locks
  if (!slot) return;                                  // 已被别的实例持锁
  try {
    await insertRunIdempotent(task, scheduledFor);    // uq_runs_task_slot 兜底
    await runExecutor.enqueue(runId, { pool: 'scheduled' });
  } finally { /* 续期由 run 生命周期负责 */ }
}
```

### 7.4 代码执行沙箱：双轨设计（Q3 落地）

#### 现状语义（`services/code_executor.py`，必须保持）

| 边界 | 实现 |
| --- | --- |
| 启动前 | 路径逃逸拦截 + 网络出口检测（默认关） |
| 运行中 | POSIX `setrlimit`（CPU 60s / 内存 1024MB / 句柄 256 / 单文件 64MB）+ 墙钟 180s + 输出上限 64KB（超出即杀） |
| 命令黑名单 | `BLOCKED_COMMANDS` 5 条（`rm -rf /`、`mkfs`、`dd if=`、fork bomb 等） |
| 工作目录 | run 绑定的 workspace_root（运行期锁死）→ 回退全局工作区 → `data/outputs` |
| 写边界 | 仅 `cwd` + manifest `writable_roots` + `outputs` |
| Python 预处理 | matplotlib 强制 Agg + 中文字体；reportlab 注册中文字体 |

#### 目标：Node 轨道（必备）+ Python 轨道（可选）

```
工具 execute_code(language: 'python' | 'javascript', code)
│
├── language='javascript' → Node 沙箱（**永远可用**）
│     · child_process.spawn(process.execPath, [--experimental-permission, entry])
│     · 不可信代码**必须**用子进程（node:vm 不安全，可被逃逸）
│     · POSIX: ulimit -t/-v/-n/-f + 进程组 kill；Windows: Job Object（可选）
│
└── language='python' → Python 沙箱（探测到解释器才可用）
      · 探测顺序：AGENT_PYTHON_BIN → userData/runtime/python/bin/python3 → 系统 python3
      · 找不到 → 明确错误：
          「未检测到 Python 解释器。Python 代码执行不可用。
            可改用 JavaScript，或在 设置 → Python 运行时 中下载/指定。」
      · 沿用现有 setrlimit / 黑名单 / 逃逸拦截（经 python3 shim 启动）
      · 包依赖由 §7.6 的包管理器提供（--target 到 userData/runtime/python-packages）
```

#### 为什么双轨（而非纯 Node）

Agent 生成的代码**绝大多数是 Python**（数据/分析场景），`data-analysis` Skill 依赖 pandas/matplotlib。纯 Node 会直接废掉这类能力。双轨 = 保证**基线可用**（Node）+ **能力完整**（Python 按需）。

```ts
  return {
    send(event: string, data: unknown, id?: number) {
      if (id !== undefined) reply.raw.write(`id: ${id}\n`);
      reply.raw.write(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`);
    },
    ping() { reply.raw.write(': ping\n\n'); },
    end() { reply.raw.end(); },
  };
}
```

⚠️ Fastify 注意事项：**不要启用 `@fastify/compress`**（会缓冲 SSE）。

### 7.9 Vue 前端「零改动」论证

Q1 要求「不影响桌面端 UI 和相关功能」。本方案对 Vue 业务代码的改动 = **0 行**，依据：

| --- | --- |

| SSE | 同源 `EventSource`，事件名与 schema 由契约冻结保证不变 |
| `window.agentDesktop` | preload 未改动 |
| 类型 | `src/api/types.ts` 手写类型与后端 Zod 无运行时耦合；可在 P6 改为从 Zod 推导（**可选优化**，非必须） |
| dev 体验 | `vite.config.ts` 的 proxy 目标从 18040 改到 TS server 端口（**配置项，非业务代码**） |

**唯一建议的改动**（非必须，P5 小项）：

1. 旧库无 `__migrations` 表 → 用新表记录 Drizzle 迁移版本

3. Alembic 12 个迁移的**净效果** = 「空库建到 22 表 + 后续加列」→ 基线一次建到最终态，只需把**加列类**转为 `ALTER TABLE ADD COLUMN`

**三层全部通过才算「功能保持一致」**。L1 通过但 L2 有缺陷 = 不合格。

#### 12.3.2 差异三分类（唯一处置口径）

| 分类 | 定义 | 处置 | 允许数量 |
| --- | --- | --- | --- |
| **等价** | 形式不同但对外可感知行为一致（如日志格式、内部函数名、SQL 执行顺序） | 记录即可 | 不限 |
| **豁免** | 有意为之的差异（如 Web 端能力删除、`loop_detected` 缺陷修复、PDF 表格识别退化） | **必须**写明：理由 + 影响面 + 用户可感知程度 + 是否需文档说明 | **需人工逐条批准** |
| **缺陷** | 功能缺失、行为错误、性能显著劣化 | **必须修复**并重跑 | **0**（M3 前必须清零） |

**红线**：任何「能用但不一样」如果影响用户可感知结果，一律归入**缺陷**，不允许塞进「等价」或「豁免」。判定争议由人工裁决。

**两个文件的判定关系**：

| 场景 | `feature-results.csv` | `diffs.csv` | 结论 |
| --- | --- | --- | --- |
| 完全一致 | `result=pass` | 无此行 | ✅ 通过 |
| 形式差异但行为等价 | `result=pass` | `verdict=equivalent` | ✅ 通过（记录在案） |
| 有意降级并获批准 | `result=pass` | `verdict=waived`（四要素齐全） | ⚠️ 有条件通过 |
| 功能缺失/行为错误 | `result=fail` | `verdict=defect` | ❌ 不通过，必须修复 |

1. 每行判定必须带 `evidence` 路径——无证据的 `pass` 视为**未测**（等同 fail）
2. `waived` 的 `reason`/`impact`/`approved_by`/`owner`/`due` **五要素缺一不可**
3. `diffs.csv` 中 `verdict=defect` 行数 **必须为 0** 才能交付（CI 闸门 4 强制）

| 问题 | 说明 |
| --- | --- |
| 变更量巨大 | 预计 **新增 300+ 文件、修改 50+、删除 200+**（含 `backend/` 整目录）。机器一次性提交会得到一个不可 review 的 commit |
| 语义混杂 | 同一阶段内会同时有「新增 TS 实现」「删除 Python 实现」「改配置」「写文档」四类变更，混在一起无法按需回滚 |
| 需要人判断 | 「这个 Python 文件真的可以删了吗」「这个依赖是不是还要留」——这类判断机器做不了 |
| 回滚需要粒度 | 出问题时要能「只回滚 sidecar 改造，不回滚数据层」→ 必须按主题拆分 |

### 18.5 若发现违规提交（应急流程）

```
发现已执行 git commit（未 push）
  → 立即停止后续操作
  → 报告人工，附 git log 输出（最近 3 条）
  → 等待人工决定（人工可用 git reset --soft HEAD~N 撤回）
  → 执行方不得自行 reset / rebase

发现已执行 git push
  → 立即报告人工，说明推送的分支与 commit 范围
  → 不执行任何 force 操作
  → 不尝试「悄悄修好」
  → 由人工判断是否需要 revert（用新 commit 反向提交，而非 force push）
```

> **红线**：`git push --force`、`git reset --hard` 无论什么理由都**不得**由执行方发起。

## 结语

这次改造的核心只有一句话：**用 TypeScript 重写后端，让产品只剩一个运行时**。

**收益是结构性的**：安装包减 3/4、启动更快、前后端共享同一份类型契约、彻底摆脱跨平台 Python 组装这个长期成本，并顺带清掉 9 项技术债（§3.2）。

> **但「重写」也是最容易悄悄丢功能的做法。** 因此 v2.1 增加了三项纪律：**先测现状建立基线、改造后逐项对比、过程与结果全部留痕**（§1.3、§12），以及**代码只由人工提交**（§18）。这三项共 **+11 人日**，但它把「功能保持一致」从一句承诺变成了 200 行可验证的 CSV + 一份带证据索引的报告。

**代价是一次 28,569 行的高风险重写**。控制手段是 §6 的四道闸门 + §11 的里程碑切分——**M1（89 人日）就能拿到可内测的版本**，之后 M2/M3 可独立验收、可独立中止。

**建议的第一步**：立刻开 **P0（9 人日：契约冻结 + 全量基线测试）**。它本身零风险、不改变任何行为，产出的 6 份契约文件 + 1 份功能基线清单既是重写的验收基准，也能立刻作为「现状到底长什么样」的可执行文档。若届时决定不做 TS 重写，这 9 人日的产出依然有长期价值——**它是后续任何改动（包括只做裁剪）的唯一验收依据**。

若只做 §9 的裁撤（方案 B，8 人日含纪律），也能立刻满足「一个软件、无 Web 端、本地数据」三项需求——**P0 与 B1/B2 可以并行，合计约 14 人日**。

**最后一句提醒**：本方案**不会替你做任何 `git` 操作**。所有代码改动只落在工作区，每个阶段结束交付一份「待提交文件清单」（§18.3），由你审阅后自行提交（D3）。
