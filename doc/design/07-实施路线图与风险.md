## 12. 跨阶段纪律

1. **单阶段单主题**：一个阶段只做一件事；发现新问题记入 `09`，不在本阶段顺手扩范围。
2. **契约先行**：改端点先改 `05`；改事件先改事件表；改表先写迁移草稿。
3. **测试同步**：编码与测试同批次提交；新增能力必须同时新增用例（无测试的需求视为未完成）。
4. **可回滚**：每阶段结束前做一次回滚演练（代码回退 + 迁移 downgrade）。
5. **口径同步**：改了端点数/表数/测试数，同步 `doc/analysis/00_README.md`、`backend/README.md`、`文档.md` 的计数表。
6. **不虚标**：未实现的能力在文档与 UI 中标注为未实现，禁止用硬编码假装支持（当前 `sandbox_available` 即反例）。

## 18. 工作分解与提交规范
### 4.1 分解层级

```
阶段（Stage）        → 例如 S2 权限引擎与执行边界
  ├── 工作包（WP）   → 例如 WP-2.1 规则模型与迁移
  │     ├── 任务卡（Task）→ 半天到 1 天，含完成判据
  │     └── 测试用例（TC）  → 每张任务卡至少 1 条
  └── 出口验收（DoD）
```

任务卡统一模板见 （模板见本篇 §18）。**每张任务卡必须写明：改哪些文件、怎么验证、测什么、回滚方式。**

### 4.2 分支与提交

| 项 | 规范 |
| --- | --- |
| 分支 | `feat/<stage>-<slug>`（如 `feat/s2-permission-rules`）；修 bug 用 `fix/<stage>-<slug>` |
| 提交粒度 | 一个任务卡一次提交；**代码与测试同提交**（无测试的提交不合入） |
| 提交信息 | `S2/WP-2.3: 新增 permission_decisions 表与迁移`（阶段号 + 工作包号 + 一句话） |
| 合并条件 | 分支自身门禁全绿 + 至少一人 review + 阶段文件对应行已勾选 |
| 合并方式 | 阶段内按工作包合并；**阶段出口做一次整体合并到 `main` 并打 tag**：`stage/S<n>-done` |
| 禁止 | 一次提交跨多个工作包；把格式改动与逻辑改动混在一起；提交密钥与本地数据 |

### 4.3 代码提交前的自检（每个工作包）

```
[ ] 类型与静态检查通过（vue-tsc / tsc）
[ ] 新增/修改的函数有对应测试
[ ] 契约变更已同步 doc/design/05 与前端 endpoints.ts
[ ] 无调试残留（print / console.log / TODO 注释掉的代码）
[ ] 无新增硬编码常量（进 config.py 或常量文件）
[ ] 数据变更含迁移与 downgrade
[ ] 对外错误体符合统一格式（code/message/request_id）
```
