## 1. 现状架构

### 1.1 分层

```
入口层
├─ Web：Vite dev（:5185）→ 后端 :8000；生产由后端 mount 前端 dist
├─ 桌面：Electron 壳 → spawn `python -m app.desktop.launcher`（自绑 :0 分配端口）
└─ CLI/计划任务：调用 `app.desktop.launcher`（需 AGENT_DESKTOP 环境变量）
        │
        ▼
后端 Fastify（apps/server/src/main.ts，153 行）
├─ lifespan：迁移 → init_app_state → skill_manager.sync_to_db → scheduler.start
├─ 中间件：仅 CORS（+ desktop_mode 时的 desktop_guard）
├─ 路由：api_router（13 个子路由，prefix=/api/v1）+ 6 个应用级端点
├─ 异常处理：**无**（全仓 0 个 exception_handler）
└─ SPA 回退：仅当 frontend_dist_dir 存在时注册
        │
        ▼
服务层（38 个非 __init__ 模块）
├─ 执行：agent_service（主循环）/ run_executor（执行+落库）/ tool_registry（工具抽象+权限落点）
├─ 能力链：skill_manager · mcp_manager · rag/ · web/ · research/
├─ 领域：session_service · run_service · scheduler_service · team_service · desktop_service · permissions
└─ 遗留：services/agent/（第二套编排）· workers/queue_worker.py（无运行环境）
        │
        ▼
数据层
├─ SQLite（Drizzle 2.0，22 表，WAL）
├─ Milvus（混合检索：稠密 DashScope dim=1024 + 稀疏 BM25）
├─ 文件系统：skills/、data/skills_custom/、data/outputs/、data/uploads/、data/browser/
└─ 模型：DashScope 主 / DeepSeek 备 / OpenAI（Research）—— 三处独立客户端
```

### 1.2 四个运行域

| 运行域 | 承载 | 现状实现 |
| --- | --- | --- |
| 双模式会话 | chat / work 两种会话形态 | `sessions.mode` + `ToolProfile.CHAT/WORK` 工具档案 |
| Skill 团队 | 技能组合 + 三种编排策略 | `teams` + `team_skills`；router 用 LLM 选技能（结果缓存 5 分钟） |
| 定时任务 | 周期执行 + 幂等 + 退避 | APScheduler + `scheduled_tasks` + `runs` 唯一键槽位 + DB 租约 |
| 运行账本 | run / event 可回放 | `runs` + `run_events`（`(run_id, seq)` 唯一）+ SSE 续传游标 |

### 1.3 事件协议

`run_events` 定义 18 种事件类型（见 `doc/analysis/03`）；前端 `WorkspaceView.appendEvent()` 消费 12 类（notice / skills_selected / round_start / round_input / reflection_start / plan / reflection_plan / model_text / reasoning_delta / tool_call / tool_result / files / done）。断线续传用 `after_seq` 游标，30 分钟上限。

**这是本平台最扎实的资产**：竞品多为"看进度"，本平台是"可回放账本"。迁移过程中**不得改动事件语义**，只允许新增。

## 2. 结构性问题诊断

> 完整清单见 `09`；本节只列**影响架构骨架**的 6 条。

| # | 问题 | 结构性影响 | 对策阶段 |
| --- | --- | --- | --- |
| A-01 | **两套 Agent 编排并存**：`services/agent_service.py` 与 `services/agent/*` 各有一套主循环，后者不写 run/session 账本 | "同一个能力"有两种行为，账本与事件协议只覆盖一半；调试时无法判断请求走哪条 | S1：收敛为一套，旧链路降级并显式标注 |
| A-04 | **Research 配置双源**：import 时快照 `settings` + 运行时改写全局 `AGENT_CONFIG` dict | 配置生效时机不可预测，测试难以注入；并发研究任务互相污染 | S1：配置只从 `settings` 读，运行期参数走入参 |
| A-07 | **`mode` 枚举不一致**：DB 与 schema 是 `chat\|work`，桌面服务是 `chat\|work\|plan` | 同一概念三处取值，写入路径决定语义 | S1：全链路 `chat\|plan\|work`，DB 归一为 `work + plan_first` |
| A-09 | **默认绑定全网卡 + CORS `*` + `allow_credentials`** | Web 形态下任何本机进程/网页可调接口，桌面端把执行器放在用户机器上时风险放大 | S1：默认 `127.0.0.1`，CORS 白名单显式配置 |
| A-10 | **无全局异常处理**，多处裸 `except Exception` 返回 500 | 错误响应体不统一，前端无法区分"业务失败"与"服务故障" | S1：统一异常处理 + 错误码 + 请求 ID |
| G-22/A-15 | **上下文与工具全量注入** + **无结构化日志/请求 ID** | 长会话成本与延迟线性上升；线上问题无法定位到具体步骤 | S5（上下文）、S7（可观测） |

**一条判断**：本平台的问题不是"能力不够"，而是**同一能力有多个实现、同一事实有多个来源**。因此 S1 的价值高于任何新功能——它让后续所有阶段的改动都有确定的落点。

## 3. 目标架构

### 3.1 模块边界（目标）

```
apps/server/src/
├── main.py                  # 装配、中间件、统一异常、路由挂载
├── core/
│   ├── config.py            # 唯一配置真相（分环境前缀，desktop/web）
│   ├── llm.py               # 唯一 LLM 工厂（provider 参数化）
│   ├── workspace.py         # 工作空间注册表 + 当前选择（多实例安全）
│   └── errors.py            # 错误码与异常类型
├── db/                      # models.py（目标 15 表）+ migrations/
├── api/v1/                  # 端点层：只做校验与编排，不含业务规则
├── services/
│   ├── exec/                # 执行域
│   │   ├── agent_loop.py    # 唯一主循环（规划→工具→反思→汇总）
│   │   ├── context.py       # 上下文预算/压缩/记忆预筛
│   │   ├── tools/           # 工具注册表 + 内置工具实现
│   │   └── team/            # 黑板、依赖图、角色编排
│   ├── security/
│   │   ├── permissions.py   # 规则存储 + 判定 + 审批
│   │   ├── policy.py        # 规则集（路径/命令/工具/网络）
│   │   └── audit.py         # JSONL 审计
│   ├── workspace/           # manifest、快照、变更、产物
│   ├── scheduler/           # RRULE、幂等、租约、投递
│   └── chains/              # skill / mcp / rag / web / research
└── desktop/                 # sidecar 引导、事件总线、鉴权守卫
```

### 3.2 三条边界规则

| 规则 | 内容 | 落地检查 |
| --- | --- | --- |
| **端点层无业务** | `api/v1/*` 只做入参校验、鉴权上下文、业务调用、响应封装；不含分支逻辑 | 路由文件内不得出现 `if` 形式的业务判定分支（校验除外） |
| **业务层无 IO 直连** | service 不直接读文件/调外部 HTTP，一律经对应网关（tools / chains / db） | 便于替换与测试 |
| **执行域单向依赖** | `exec/*` 可依赖 `security/workspace/scheduler/db`，反向依赖禁止 | 依赖方向在评审清单中逐条核对 |

## 4. 关键数据流（目标态）

### 4.1 一次交互式任务（含审批与 steer）

```
前端 POST /agent/run(mode, plan_first, session_id)
  → agent_loop 建 run（status=running）
  → 组装上下文（预算内：系统 + 记忆预筛≤5 + 历史裁剪 + 工具目录）
  → LLM 调用 → tool_call
  → dispatch(tool_call)
       ├─ 权限判定：allow → 执行
       ├─ ask   → 写 decision + 推 permission.requested → 阻塞等待（上限 120s，超时 deny）
       └─ deny  → 返回拒绝理由给模型
  → 执行（受工作区可写根与命令策略约束）
  → 写前快照 → changes 落库
  → 事件写 run_events（SSE 推给前端）
  → 下一轮前检查 steer 队列：有则并入指令（见 S4）
  → 结束：写 artifacts、token/成本、状态
```

### 4.2 桌面态的进程与事件

```
Electron main
  → spawn sidecar（AGENT_DESKTOP_* 环境变量）
  ← 读 AGENT_DESKTOP_READY {port, token} 握手行（90s 超时）
  → GET /__desktop/bootstrap?t=<nonce> → 302 + HttpOnly Cookie
  → 窗口 loadURL(http://127.0.0.1:<port>/)
  ⇄ 订阅 GET /api/v1/desktop/events（SSE）→ 转 agent:backend-event → 渲染进程
  → 空闲超时/最小化 → 托盘；崩溃 → 退避重启（1/2/4s，3 次熔断）
```

### 4.3 定时任务

```
APScheduler 触发 → 计算槽位 scheduled_for
  → INSERT runs(task_id, scheduled_for)  ← UNIQUE 冲突即跳过（幂等）
  → 独立会话 + 绑定工作空间执行（ask 在无人值守下降级为 deny 并记录）
  → 结束写状态 → 投递（本地通知 / IM Bot / 移动端）
```

## 5. 技术选型现状与结论

| 领域 | 现状 | 结论 | 理由 |
| --- | --- | --- | --- |
| 壳框架 | Electron 33 + electron-builder 25 + electron-updater 6 | **维持** | 前端零改动；`document.md` §11.0.1 已判定 Tauri/Flutter 不划算 |
| 后端形态 | Python Fastify sidecar + portable Python 运行时 | **维持** | `sys.executable` 语义必须保留（冻结会让 `code_executor` 重启应用）；工具生态在 Python |
| 前端 | Vue 3 + TS + Element Plus | **维持** | 现有 16 个视图与 70 个 API 函数全在此栈 |
| 数据库 | SQLite（WAL） | **维持** | 单机部署；唯一键即可满足幂等；升级 PG 路径保留 |
| 向量库 | Milvus（内网 standalone） | **维持**，但路径随 `data_dir` | 本机无 milvus-lite wheel |
| 调度 | APScheduler + 自有表 + DB 租约 | **维持**，RRULE 子集自研 | 不用 jobstore 双写，避免两份真相 |
| 终端/PTY | 无（不执行交互式终端） | **不引入** | 需要时复用 `node-pty`，不自造 |
| 分布式队列 | `workers/queue_worker.py`（无运行环境） | **移出 `app/`** | 单机不需要 |

## 6. 迁移策略

| 原则 | 做法 |
| --- | --- |
| **契约先行** | 任何端点变更先更新 `05-数据模型与API设计.md`，再改代码；前端 `endpoints.ts` 与后端 OpenAPI 必须一致（由 `contract_check.py` 把关） |
| **双写期短** | 需要改数据结构的（如 `mode` 归一），用一次迁移 + 读时兼容，**不做长期双写** |
| **可回滚** | 每阶段独立可回滚：代码可回退、数据用迁移的 `downgrade()` 回退、开关可关（见 `07`） |
| **不静默降级** | 降级路径必须显式（例如 MCP 连接失败要能在 UI 看到红色状态），不得用"假装成功"掩盖 |
| **事件语义冻结** | `run_events` 现有 18 类事件只增不改；新增事件向后兼容 |

## 7. 架构验收标准

| # | 标准 | 验证方式 |
| --- | --- | --- |
| 1 | 只存在一套 Agent 主循环 | 静态检索：主循环入口唯一；`/agent/chat` 的行为与 `/agent/run` 一致并写账本 |
| 2 | 配置只有一处真相 | `config.py` 之外的模块不得在 import 期快照 `settings`；无全局可变配置 dict |
| 3 | `mode` 三态全链路一致 | DB、schema、服务、前端四处取值集合一致；契约测试断言 |
| 4 | 无全网卡默认绑定 | `settings.host` 默认 `127.0.0.1`；代码中所有绑定点读同一个配置 |
| 5 | 统一异常与请求 ID | 每个错误响应含 `code` / `message` / `request_id`；日志可按 `request_id` 检索 |
| 6 | 权限判定单一落点 | 全仓检索：写操作入口只有 `dispatch()` 一条路径 |
| 7 | 事件语义向后兼容 | 旧客户端解析新事件不报错（新事件可忽略） |
