## 一、为什么需要这份对标

桌面 Agent 赛道在 2026 年集中爆发：腾讯 WorkBuddy、字节豆包工作/ TRAE、阿里千问办公、微软 Copilot 统一应用、OpenAI ChatGPT Desktop 同期进入桌面。**这些产品已经把"桌面 AI 工作台"的交互范式跑出来了**，包括大量我们凭直觉想不到的细节。

本文档的目的是：
1. 把这些交互模式**系统地列出来**（而非零散提及）；
2. 对照**我们的代码事实**逐条标注「已有 / 部分 / 缺失」，避免凭印象判断；
3. 把每条结论**指向设计文档的具体篇目**，使对标结果真正落进规格。

#### 3.1.2 三种执行模式

> 腾讯新闻《AI 进展观察》：WorkBuddy「默认 / 计划 / 问答**三种执行模式**」

我们的三态是 `chat` / `plan` / `work`（`stores/workspace.ts` 的 `mode`，`toBackend()` 把 plan 映射为 `work + plan_first`）—— **语义高度一致**，命名不同。

#### 3.1.3 单句指令 + 可打断

> 硅基部落《桌面 AI Agent 混战一个月》：
> 「WorkBuddy 的核心逻辑是**"单句指令发起任务"**——你用口语描述需求，它自己拆解步骤、调用工具、产出结果。」
> 「它有一个设计让我印象深刻：**任务过程中你可以随时打断它，告诉它"这个方向不对"，它会即时调整。**这种交互方式比"等它做完再改"效率高太多了。」

> ⚠ **「打断」有两种语义，不能混为一谈**：
> - **打断（stop）**：中止当前任务 —— 我们已有（见 §五 G-07）
> - **介入并转向（steer）**：在任务运行中追加一条指令，让 Agent 调整方向 —— **我们完全没有**（见 §五 G-08）

#### 3.1.4 人机双写（5.3.11）

> 羊城晚报：WorkBuddy V5.3.5 上线「人机双写」协同编辑，「将 AI 协作权限原生嵌入 Word、Excel、PPT、Markdown、腾讯文档全格式内核，摒弃传统 AI 跨窗口外挂模式」
> 自动化网：「用户框选对应区域后，AI 以**修订/批注**呈现修改内容，不破坏原有版式」

这是**文档编辑范式**，与本平台（Agent 平台 + 5 能力链）的定位差异较大 → 列入非目标（§六）。

#### 3.1.5 安全模型（官方文档，最有参考价值）

腾讯云官方《WorkBuddy 常见问题》原文：

> **三层纵深防御安全架构**
> **1. 技术防御层：沙箱隔离与权限控制**
> - Bash 命令沙箱：AI 操作与真实系统严格隔离
> - **文件系统隔离：只能访问预先授权的工作空间目录，无法访问系统敏感文件**
> - 防沙箱逃逸：阻止对配置文件的写入
> - **默认安全设计：启动时仅拥有只读权限，编辑文件、运行命令需显式用户批准**
> - **分层权限系统：支持 allow（允许）、ask（询问）、deny（拒绝）三种权限规则**
> **2. 管理管控层**：SSO 单点登录、Credit 额度控制、IP 白名单、精细化工具调用权限
> **3. 合规审计层**：Skill 安全审计（skill-scanner）、本地安全检查、**数据本地执行不上传**

执行层的**三类拦截**：

| 层 | 机制 | 触发条件 |
|---|---|---|
| 1 | 沙箱执行 | 改文件、跑脚本、调工具全部在隔离环境内完成，出错不波及真实环境 |
| 2 | **高危操作拦截** | 删除大量文件、批量改系统配置、执行来源不明的脚本 → 要求人工确认 |
| 3 | **访问边界拦截** | 本地文件只在授权目录内可读，目录之外直接被挡 |

「三道兜底」策略（正观新闻）：

> 第一道，默认开启的安全沙箱先判断 AI 的指令，拦下格式化磁盘、遍历系统根目录这类高危操作，**工作空间内的正常读写直接放行**；
> 第二道，任何删除类的操作……
> （要点：**用兜底机制替代逐条弹窗**，避免"逐条授权太繁琐"的体验惩罚）

### 3.4 Cherry Studio（Electron 桌面客户端的交互教科书）

尽管不是 Agent 平台，但它是**开源 Electron 桌面 AI 客户端**，在"在世交互"（presence）上的做法最完整：

| 机制 | 事实 | 来源 |
|---|---|---|

### 5.3 我们已经领先的地方

对标不是为了自我否定。有三项我们的设计**已经领先于多数竞品**：

| 项 | 我们的优势 | 证据 |
|---|---|---|
| **Agent 执行引擎的事件协议** | 18 种 SSE 事件 + `run_events` 表 + `after_seq` 游标续播，**任务可完整回放** | `doc/analysis/03`、`runs.py:52-79`；竞品多为"看进度"，我们是"可回放账本" |
| **MCP 是一等公民** | 3 个 stdio Server + 静态反射 + 工具命名空间；竞品的 MCP 多为插件生态的一层 | `mcp_manager.py:26-45` |
| **运行账本与调度幂等** | `runs` + `run_events` + `system_locks` 租约 + `(task_id, scheduled_for)` 唯一约束 → 无人值守场景的正确性基础 | `doc/analysis/08`；`models.py:187` |

**对标结论**：我们的**引擎层**已经扎实，缺的是**桌面外壳层**（在世交互）与**权限层**。这两层的补齐成本低、收益直接，是桌面端 P0/P1 的正确投放位置。

## 六、明确不做的事（对标后确认的非目标）

| 非目标 | 理由 |
|---|---|
| **人机双写 / 框选修订** | 文档编辑范式，与本平台的 Agent + 5 能力链定位不符（WorkBuddy 5.3.11 的方向） |
| **Diff 审阅视图** | 本平台不是代码编辑器；产物以报告/文档/图片为主，diff 视图收益低 |
| **工具面板（编辑器/浏览器）** | TRAE SOLO 的 IDE 能力；本平台已有独立的 RAG / Web Research 链 |
| **模板库** | 与 Skill 机制重复；Skill 已覆盖"可复用能力" |
| **办公套件连接器（腾讯文档/M365/飞书）** | 属于生态集成，非本平台核心；可作为外部 MCP Server 接入（P2） |
| **语音通话 + 共享屏幕** | 豆包独占；本平台无屏幕理解能力，投入产出比低 |
| **远程下发任务 / 三端同步（首版）** | 需要账号体系与云端同步存储；当前是单用户本机模型（`design/00` §7 非目标） |
