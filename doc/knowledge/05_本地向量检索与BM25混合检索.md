# 本地向量检索与 BM25 混合检索

> **依据代码**：`apps/server/src/domain/rag/store.ts`、`apps/server/src/http/routes/rag.ts`（2026-11-01 复核重写）
> **原理主题**：Embedding 稠密检索 + BM25 稀疏检索 + 加权融合的完整原理，
> 以及本项目「SQLite BLOB + 内存索引」的零依赖实现。
>
> 向量层历史上用 Milvus Lite，**已改为进程内本地实现**（单运行时改造：
> 桌面安装包不能带一个数据库服务）。本篇只讲当前实现。

---

## 一、混合检索要解决的问题

纯向量检索（语义相似）对「型号、编号、专有名词」不敏感——语义相近但
关键词不同的文档会被误排；纯关键词检索（BM25）对「同义不同词」无能为力。
**混合检索**两路并行再融合，取长补长，是生产级 RAG 的标准做法
（Elasticsearch BM25+kNN、Pinecone sparse-dense 同此理）。

## 二、稠密路：Embedding + 内积

- **模型**：DashScope `text-embedding-v3`，**1024 维**（`rag.ts:19`，批 10 条）；
- **度量**：内积（IP）——`BruteForceIndex.search()`（`store.ts:158`）对全部向量
  做点积排序取 top-k；向量经模型侧归一化时，IP ≈ 余弦相似度；
- **存储**：chunk 文本 + Float32Array 向量转 Buffer 存 SQLite BLOB
  （`vectors/chunks.db` 的 `chunks(id, doc_id, seq, text, dense, created_at)`）；
  启动时全量载入内存（`load()`，`store.ts:212`）。

**暴力检索够用吗**：chunk 量级在数千时，1024 维点积 × N 是毫秒级——
桌面单机知识库场景，暴力法比引入索引库（hnswlib/faiss 原生依赖）更稳。
`VectorIndex` 接口（`store.ts:134`）已为将来规模增长预留替换点。

## 三、稀疏路：BM25

BM25（Okapi BM25）是 TF-IDF 的现代形态，打分公式：

```
score(d, q) = Σ_t∈q  idf(t) · tf(t,d)·(k1+1) / (tf(t,d) + k1·(1-b+b·dl/avgdl))
idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))
```

- `k1=1.5`：词频饱和度（出现 3 次后边际收益锐减）；
- `b=0.75`：文档长度归一化强度（长文档不因为词多而占优）；
- 参数对齐 Milvus 默认值（`LIMITS.bm25K1/bm25B`）。

本项目实现（`Bm25Index`，`store.ts:78`）：

- **分词**：`Intl.Segmenter("zh", {granularity:"word"})`——V8 内置，支持中文
  词边界，零依赖；英文/数字再按非字母数字切分（`tokenize()`，`store.ts:39`）；
- **倒排**：`Map<term, docId[]>`（postings 按出现次数重复记录 docId，
  检索时聚合成 tf）；
- 索引在内存，随 `load()` 从 chunks 表重建。

## 四、融合：min-max 归一化 + 加权

`hybridSearch()`（`store.ts:281`）：

1. 两路各取 `max(limit*5, 50)` 候选（放大候选池，给融合留空间）；
2. **min-max 归一化**把两路分数各自压到 [0,1]——BM25 与 IP 量纲不可比，
   不归一化直接加权会被量纲大的一方淹没；
3. 加权求和：`sparse × 0.7 + dense × 1.0`（`LIMITS.ragSparseWeight/ragDenseWeight`），
   语义为主、关键词兜底；
4. 降序取 top-10（`LIMITS.ragLimit`）。

该语义与 Milvus `WeightedRanker` 的内部行为对齐（先归一再加权）。

## 五、入库幂等与切块

- **幂等键**：`doc_id = sha256(路径 | 内容哈希)`（`store.ts:332`）——
  同文件重复入库：先 `DELETE FROM chunks WHERE doc_id=?` 再插（覆盖语义）；
  `recreate=false` 时按台账跳过已入库文件；
- **切块**（`chunkText`，`store.ts:58`）：定长 1000 字符、overlap=0，
  优先在换行/空格处断（窗口内后半找断点），避免硬切句子；
- **PDF 抽取**：极简实现（`Tj` 算子正则，`rag.ts:161`）——复杂排版覆盖有限，
  `pdfjs-dist` 已在依赖中待接入（已知边界）；
- **双库分工**：台账在主库 `rag_documents`（doc_id/路径/哈希/chunk 数），
  向量在 `vectors/chunks.db`——向量库可独立删除重建（从 PDF 重新 ingest 即可）。

## 六、问答层

`POST /rag/query`：命中块编号为 `[1] [2] …` 拼入 prompt →
`rag_model`（默认 deepseek-chat）生成**带引用编号**的回答。
引用让每句结论可回指原文块（可验证性）；当前无结构化兜底
（模型不标编号时没有降级解析）。

## 七、业界对照

| 方案 | 部署 | 混合检索 |
|---|---|---|
| Elasticsearch | JVM 服务 | BM25 + kNN |
| Qdrant / Weaviate | 独立服务 | sparse-dense |
| Milvus Lite | 进程内库（原生依赖） | BM25 Function + dense |
| 本项目 | **零依赖**（SQLite + 内存索引） | 内存 BM25 + 暴力 IP + 加权 |

取舍：用「单机上万 chunk 以内」的规模假设，换掉一切外部服务与原生索引依赖——
这对桌面安装包是正确的经济账。
