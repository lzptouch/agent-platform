# agent 文档集

> **项目定位**：agent 平台，提供 5 条能力链（**Skill / MCP / RAG / Web Research / Deep Research**）
> + 4 个运行域（双模式会话 / Skill 团队 / 定时任务 / 运行账本）
> + 4 个横切域（**权限安全 / 工作区产物 / 上下文成本 / 扩展层**）。
> FastAPI 后端 + Vue 3 + TS + Element Plus 前端 + Electron 桌面壳。
>
> **文档集范围**：`doc/`（本目录）+ `deploy/`（随代码维护的部署手册）。
>
> **目标形态的源头**：WorkBuddy 通用智能工作台 / 一体化内嵌架构的产品定义。
> 它的实现规格（§11）、能力缺口（§2.7）与交互清单（§8）已整理进
> [`design/15-目标形态与实现状态.md`](./design/15-目标形态与实现状态.md)（**逐条带实现状态**），
> 未实现项进 [`design/09`（差距矩阵）](./design/09-差距矩阵与整改清单.md) 与 [`plan/`（批次）](./plan/README.md)。

## 一、四分区结构（2026-10-30 调整）

```
doc/
├─ analysis/   ① 当前代码的事实 + 还剩什么缺陷      （读代码的人看这里）
├─ design/     ② 项目总目标 + 已实现标记 + 差距清单  （做决策 / 排期的人看这里）
├─ plan/       ③ 接下来要做的：范围 · 步骤 · 验收    （执行的人看这里）
├─ testing/    ④ 可执行测试计划（用例 · 门禁 · 工件） （测试的人看这里）
└─ knowledge/  ⑤ 通用原理（为什么这么设计）          （学习的人看这里）
```

> 内容有归属，副本不重复。

> ① **2026-10-29 删除**——原 8 个批次全部交付完毕；

> 原因是剩余问题的性质变了：从「**功能不存在**」变成了「**功能写了但没接线**」与「**声明与实现不符**」。
> ③ **2026-10-30 扩充**——补齐**条目级总台账**、条目级依赖矩阵、工作量估算，
> **④ 2026-10-30 代码级审计后再扩充**——64 项 → **82 项**、92 人日 → **116 人日**：
> 新增 18 项来自「`design/01` 中被误判为 ✅ 的 20 条需求」的逐条复核。
> 风险登记（12 条）、交付定义 DoD（5 条）与执行看板；六个批次文件各补「条目速查表」。
> 原 `plan/_gate/` 校验脚本**尚未重建** → `plan/05` P5-05/P5-06。
>
> **⑤ 2026-10-31 全面复审后新建第七批**——[`plan/07`](./plan/07-全面代码审计整改计划.md)
> **W0~W6（58 项 / 31.5 人日）**：新增
> [`analysis/18`](./analysis/18_全面代码审计报告.md)（**189 条缺陷** + 22 条「声明与实现不符」）。
> 本批与前六批的**根本区别**：问题不是「功能不存在」，而是
> **「代码写了、测试也过了，但生产路径上不生效」**——根因是**验收用例没走真实调用链**
> （同步 vs 流式、mock vs 真实配置、串行 vs 并发、正常路径 vs 早退路径）。
> 因此本批除修复代码外，还包含 **`plan/07` §W5-05「验收口径升级为四维」**——
> 这是**防止同类问题复发**的关键条目。

**分工纪律**（写在 `analysis/00` §4 与 `plan/README`）：

1. `analysis` 只写**代码里存在的实现**与**仍存在的缺陷**，不写计划；
2. `design` 是**目标形态**，其中「状态」列按当前代码标注 ✅已实现 / ⏳部分 / ⛔未实现；
3. **还差什么**统一进 `design/09`（差距矩阵）+ `plan/`（批次）；`analysis/12` 只给缺陷台账的**事实描述**；
4. `testing` 是**可执行测试计划**，是 `plan` 各批次验收用例的来源；
5. 数字口径**唯一来源** = `analysis/00` §5 口径常量表（C01~C28）。
