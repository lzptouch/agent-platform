## 一、部署形态

只有一种部署形态：**单机 Docker Compose，两个容器**。

```
                浏览器 / 局域网客户端
                        │  http://<host>:8080/
        ┌───────────────▼─────────────────┐
        │  agent-web             │  nginx:1.27-alpine
        │  静态直出 /、/assets/*           │  对外唯一端口 8080→80
        │  SPA 回退 → index.html          │
        │  反代 /api/、/docs → backend    │  SSE：proxy_buffering off
        └───────────────┬─────────────────┘
                        │  compose 网络 agent
        ┌───────────────▼─────────────────┐
        │  agent-backend         │  python:3.12-slim
        │  uvicorn app.main:app :8000     │  仅 expose，不对外
        └───────────────┬─────────────────┘
                        │  /app/data
        ┌───────────────▼─────────────────┐
        │  named volume: backend-data     │
        │  milvus.db / research/ /        │
        │  outputs / uploads / pdf / logs │
        └─────────────────────────────────┘
```

设计要点：

| 决策 | 做法 | 理由 |
|---|---|---|
| 对外入口 | 只暴露 nginx 的 8080，backend 仅 `expose: 8000` | 单一入口，便于加 TLS / 限流；后端不直连宿主机 |
| 前端托管 | 多阶段构建（node 构建 → nginx 运行） | 运行镜像只含 dist + nginx，无 node_modules |
| 后端静态托管 | **关闭**（容器内无 `frontend/dist`，`main.py` 自动降级为纯 API） | 职责分离 |
| SSE 流式 | `proxy_buffering off` + `gzip off` + `X-Accel-Buffering: no` | 否则前端收不到逐字输出 |
| 服务发现 | `resolver 127.0.0.11` + 变量式 `proxy_pass` | backend 重建换 IP 后 nginx 不会「启动即 502」 |
| 数据持久化 | 命名卷 `backend-data:/app/data` | 向量库 / 任务 / 产出跨容器重建保留 |
| 密钥 | `env_file: ./backend/.env` | 密钥不进镜像层 |

## 二、组件与端口

| 组件 | 容器名 | 镜像 | 端口 | 说明 |
|---|---|---|---|---|
| 后端 | `agent-backend` | `agent-backend:1.1.0` | `expose 8000` | FastAPI + Uvicorn，健康检查打 `/api/v1/health`（`start_period: 90s`，首次删依赖初始化较慢） |
| 前端 | `agent-web` | `agent-web:${WEB_TAG:-1.1.0}` | `${HOST_HTTP_PORT:-8080}:80` | nginx 静态托管 + 反代；`depends_on: backend healthy` |

对外可访问路径（经 nginx）：

| 地址 | 内容 |
|---|---|
| `http://localhost:8080/` | 前端页面 |
| `http://localhost:8080/api/v1/health` | 后端健康检查 |
| `http://localhost:8080/docs` | Swagger（如需对公网隐藏，删 `agent.conf` 里对应 location） |
| `http://localhost:8080/nginx-healthz` | nginx 自检 |

## 三、文件地图：`deploy/` 每个文件负责什么

```
docker-compose.yml                     主编排：backend + web、命名卷、日志策略
.dockerignore                          构建上下文裁剪（排除 node_modules/.venv/data/.env/doc）
deploy/
├── README.md                          应用部署完整说明（现状→架构→快速开始→排错→实测记录）
├── 部署文件分析与操作手册.md           文件全景与层级 / 两条路线（L0 直启、L1 容器化）/ 验收清单
├── docker-compose.milvus.yml          【可选】真 Milvus 集群覆盖文件（etcd + MinIO + milvus standalone）
├── backend/
│   ├── Dockerfile                     python:3.12-slim 基础镜像；ARG: PIP_INDEX_URL / APT_MIRROR / INSTALL_PLAYWRIGHT
│   └── entrypoint.sh                  启动脚本：建目录 / 可选 ingest / exec uvicorn
├── frontend/
│   └── Dockerfile                     多阶段：node:22-alpine 构建 frontend/web/vue-element-plus → nginx:1.27-alpine 运行；ARG: NPM_REGISTRY
└── nginx/
    ├── nginx.conf                     主配置（gzip / 日志 / 上传体积）
    └── conf.d/agent.conf      站点配置（静态直出 / SPA 回退 / 反代 / SSE / 健康检查）
```

> 两个 Dockerfile 的构建上下文都是**仓库根目录**，所以手工构建需 `-f deploy/... .`；`docker-compose.yml` 已配 `context: .`。

## 四、镜像与构建参数

| 项 | 值 |
|---|---|
| 后端基础镜像 | `python:3.12-slim` |
| 前端构建 / 运行镜像 | `node:22-alpine` / `nginx:1.27-alpine` |
| 后端镜像体积（实测） | ≈ 3.96 GB（Chromium + chromadb/langchain 占大头） |
| 前端镜像体积（实测） | ≈ 74 MB |

| Build Arg | 默认 | 用途 |
|---|---|---|
| `PIP_INDEX_URL` | `https://pypi.org/simple` | 国内换 `https://pypi.tuna.tsinghua.edu.cn/simple` |
| `APT_MIRROR` | 空 | 国内可设 `mirrors.ustc.edu.cn` |
| `INSTALL_PLAYWRIGHT` | `true` | 装 Chromium（小红书 MCP 需要）；设 `false` 可大幅缩短构建时间 |
| `NPM_REGISTRY` | `https://registry.npmjs.org` | 国内换 `https://registry.npmmirror.com` |

> 前端已收敛为唯一实现 `frontend/web/vue-element-plus`，`deploy/frontend/Dockerfile` 固定构建该目录；
> 原 `FRONTEND_APP` / `WEB_TAG` / `frontend/active` 这套「多实现切换」开关已随之移除。

## 五、配置项

### 5.1 Compose 级（环境变量或 `.env`）

| 变量 | 默认 | 说明 |
|---|---|---|
| `HOST_HTTP_PORT` | `8080` | 宿主暴露端口 |
| `WEB_TAG` | `1.1.0` | 前端镜像 tag |
| `FRONTEND_APP` | `web/vue-element-plus` | 前端实现路径 |
| `PIP_INDEX_URL` / `NPM_REGISTRY` / `INSTALL_PLAYWRIGHT` | 见上 | 构建参数透传 |

### 5.2 应用级（`backend/.env`，由 `env_file` 注入）

必填三项：

| 变量 | 用途 |
|---|---|
| `DASHSCOPE_API_KEY` | Agent 主链路（Skill / MCP / 代码执行） |
| `LLM_API_KEY` | RAG 链路（DeepSeek 兼容） |
| `BOCHA_API_KEY` 或 `SERPER_API_KEY` | 深度研究检索引擎（二选一） |

常用可选项：`DASHSCOPE_BASE_URL`、`DEFAULT_MODEL`、`LLM_BASE_URL`、`PLAN_MODEL` / `RAG_MODEL` / `ANSWER_MODEL`、`MILVUS_DB_PATH`、`MILVUS_COLLECTION`、`RESEARCH_OUTPUT_DIR`、`RESEARCH_MAX_CONCURRENT`、`MCP_MAX_SERVERS`、`EXEC_TIMEOUT`、`HOST` / `PORT`。

> compose 内已覆盖 `HOST=0.0.0.0`、`PORT=8000`、`MILVUS_DB_PATH=data/milvus.db`、`RESEARCH_OUTPUT_DIR=data/research`、`RUN_INGEST=false`，`.env` 中同名变量不生效。

## 六、快速开始

```bash
# 1) 准备密钥（已存在则直接编辑）
cp backend/.env.example backend/.env

# 2) 构建（首次较慢，Chromium 下载占大头；不需要小红书能力可关掉）
INSTALL_PLAYWRIGHT=false docker compose build

# 3) 启动
docker compose up -d
docker compose ps          # 等 backend / web 都变 healthy

# 4) 验证
curl -s http://localhost:8080/api/v1/health
```

国内网络建议一次性传齐源：

```bash
PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
NPM_REGISTRY=https://registry.npmmirror.com \
INSTALL_PLAYWRIGHT=false \
docker compose build
```

## 七、运行期行为约定

| 约定 | 原因 |
|---|---|
| 后端以**单进程 uvicorn（worker=1）**运行 | `ResearchManager` 是进程内线程池 + 内存任务字典，多 worker 会导致任务状态不一致。要扩容须先改造成外部任务队列 |
| 任务与报告写 `data/research/tasks.json` + md | 进程重启后靠文件恢复；**删数据卷即等于清空** |
| Web Research 的 Chroma 不持久化 | 每次请求现场建库，设计如此 |
| `docker compose down` 保留数据，`down -v` 清空 | 后者会删掉向量库与全部研究报告 |
| 队列 Worker 无部署编排 | `backend/app/workers/queue_worker.py` 需外部提供 Redis 才能运行；仓库不再附带其部署清单 |

## 八、排错入口

| 症状 | 去哪查 |
|---|---|
| 构建失败、镜像拉不到、端口占用 | `deploy/README.md` §8 排错速查 |
| `/` 正常但 `/api/v1/health` 502 | backend 未 healthy，`docker compose logs backend`；或 `nginx` 反代配置未生效 |
| 流式回答一次性吐出 | nginx 缓冲未关闭，确认用的是 `deploy/nginx/conf.d/agent.conf` |
| 数据重启后消失 | 卷被 `down -v` 删掉或未挂载，`docker volume inspect backend-data` |
| 其他容器化排错 | [07_故障排查手册.md](./07_故障排查手册.md) |
