# 部署故障排查手册

> - **适用范围**：应用自身的容器化部署（`docker compose build/up`、nginx 反代、数据持久化、Windows/Git Bash 环境）
> - **资料来源**：本机真实部署过程中的报错与处置（`deploy/README.md` §8 与实测记录）+ Windows/WSL 环境踩坑
> - **整理日期**：2026-10-18（CI/CD 工程清理后重编）
> - **用法**：按 **症状** 检索（Ctrl+F 关键字），拿到「根因 → 处置 → 验证」

---

## 零、五步排查法（先看这个）

```
① 看日志的"第一行"错误
     docker compose logs --tail 50 backend      # 配置类错误在启动阶段就抛出
     docker compose ps                          # 先确认是 exited 还是 healthy

② 确认"视角"
     - 命令由谁执行？宿主 daemon 还是容器？→ 路径/地址该用谁的坐标系（见 §5）
     - 网络层：走 8080（nginx）还是直连 backend:8000？两者故障范围不同

③ 最小复现
     绕开 nginx / compose，手工执行那一条命令（如容器内 curl 127.0.0.1:8000/api/v1/health）
     手工能成功 → 问题在编排/反代/环境变量；手工也失败 → 问题在应用本身

④ 隔离变量
     换地址（localhost ↔ 127.0.0.1 ↔ 容器名）
     换入口（直连 backend ↔ 经 nginx）
     清状态（重启容器 → 重建容器 → 删卷重建）

⑤ 记录
     把「报错原文 + 根因 + 修法」写回本文档，避免下次重踩
```

## 一、容器与编排

| 症状 | 根因 | 处置 |
|---|---|---|
| `up` 报找不到 `./backend/.env` | 密钥文件未创建 | `cp backend/.env.example backend/.env`，至少填 `DASHSCOPE_API_KEY` / `LLM_API_KEY` / `BOCHA_API_KEY` |
| 改了 `.env` 重启却没生效 | `restart` 不会重建容器，env 在**创建时**注入 | `docker compose up -d --force-recreate backend` |
| backend 长时间 `starting` 后 unhealthy | 冷启动慢（首次初始化 + 依赖导入），`start_period` 不足 | 已在 compose 设 `start_period: 90s`；仍不够则查 `logs` 是否有导入异常 |
| web 起来但立刻 502 | `depends_on: backend healthy` 之外，nginx 缓存了旧 IP | nginx 已用 `resolver 127.0.0.11` + 变量 `proxy_pass`；若仍 502 则 `docker compose restart web` |
| 改了 nginx 配置不生效 | 配置在**镜像构建期** COPY 进去，不是挂载 | `docker compose build web && docker compose up -d web` |
| bind mount 挂成空目录 | **源路径由宿主 daemon 解析**，容器内相对路径宿主不存在 | 传宿主可见绝对路径；Windows 下确认该目录在 Docker Desktop 的 File Sharing 白名单 |
| 容器日志把磁盘写满 | 未配置日志轮转 | compose 已统一 `x-logging` 锚点（`max-size` / `max-file`）；自定义服务需沿用该锚点 |
| 端口冲突（`bind: address already in use`） | 宿主已有服务占用 8080 | `HOST_HTTP_PORT=8081 docker compose up -d` |
| 容器内时间不对 | 时区未注入 | compose 已注入 `TZ=Asia/Shanghai`，镜像内也装了 tzdata |

## 二、构建与镜像

| 症状 | 根因 | 处置 |
|---|---|---|
| 构建报 `failed to resolve source metadata for docker.io/docker/dockerfile:1.7` | Dockerfile 顶部的 `# syntax=` 指令需要拉 BuildKit frontend 镜像，本机加速器拉不到 | **不要写 `# syntax=`**（仓库内 Dockerfile 已移除） |
| 构建极慢 / playwright 下载超时 | 安装了 Chromium（约 3 GB） | `INSTALL_PLAYWRIGHT=false docker compose build`（小红书 MCP 将不可用） |
| `Unable to connect to deb.debian.org` | 境外 apt 源不通 | 传 `--build-arg APT_MIRROR=mirrors.ustc.edu.cn` |
| pip 安装超时 | 境外 PyPI 不通 | 传 `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple` |
| npm 安装超时 | 境外 npm 不通 | 传 `NPM_REGISTRY=https://registry.npmmirror.com` |
| `Head "https://<mirror>/v2/.../manifests/...": EOF` | 本机镜像加速器**缺少该仓库/标签**（如 `minio/minio` 在 USTC 源不可达） | 换加速器，或在 Docker Desktop → Settings → Docker Engine 里去掉/更换 `registry-mirrors` 后重试 |
| `COPY failed: stat ...: file does not exist` | 构建上下文不是仓库根目录，或目标被 `.dockerignore` 排除 | 保持 `context: .`；核对 `.dockerignore` |
| 前端镜像里前端实现不对 | `FRONTEND_APP` 指向了别的实现 | `FRONTEND_APP=web/xxx docker compose build web`，并配合 `WEB_TAG` 区分 |
| 镜像 tag 被覆盖导致无法回滚 | 反复用同一 tag 构建 | 切换实现时换 `WEB_TAG`；重要版本先 `docker tag <img>:1.1.0 <img>:1.1.0-bak` |

## 三、反向代理与 SSE

| 症状 | 根因 | 处置 |
|---|---|---|
| `/` 正常但 `/api/v1/health` 502 | backend 未 healthy，或 nginx 未指向正确 upstream | `docker compose logs backend`；确认 `proxy_pass` 走 `backend:8000` |
| 流式回答一次性全部出现 | nginx 缓冲未关闭 | 确认用的是 `deploy/nginx/conf.d/agent.conf`（含 `proxy_buffering off` + `gzip off` + `X-Accel-Buffering: no`） |
| 长任务请求中途断开 | 反代读超时太短 | 站点配置中 `proxy_read_timeout` 已放大到 3600s；自定义配置需同步 |
| SPA 深层路由 404 | 缺少回退规则 | 非 `/api` 路径须 `try_files ... /index.html` |
| `/docs` 不想对外暴露 | 默认透传 | 删掉站点配置里 `/docs`、`/redoc`、`/openapi.json` 三个 location |
| 上传大文件报 413 | 请求体上限太小 | 调 `client_max_body_size`（`nginx.conf` 中已放宽） |
| 容器重建后 nginx「启动即 502」 | 直接写死 upstream IP | 用 `resolver 127.0.0.11` + 变量形式 `proxy_pass`（仓库配置已采用） |

## 四、数据与持久化

| 症状 | 根因 | 处置 |
|---|---|---|
| 研究报告 / 向量库重启后消失 | 执行过 `docker compose down -v`（删卷），或未挂载卷 | `docker volume inspect backend-data`；`down` 不带 `-v` 会保留数据 |
| `milvus.db` 不存在 | 容器内路径与 `MILVUS_DB_PATH` 不一致 | compose 已设 `MILVUS_DB_PATH=data/milvus.db`（相对 `/app`，即 `/app/data/milvus.db`） |
| 切换独立 Milvus 集群后检索为空 | 原 `milvus.db` 数据**不会自动迁移** | 重新入库：`docker compose exec backend python -m scripts.ingest_data` |
| 想看数据卷里到底有什么 | — | `docker run --rm -v backend-data:/data alpine ls -lhR /data` |
| 写入文件权限不足 | 容器内用户与宿主目录属主不一致（bind mount 场景） | 改回命名卷，或统一 uid；不建议在 Windows 下用 bind mount 存运行时数据 |
| 任务状态在多副本下错乱 | `ResearchManager` 是进程内字典 + 线程池 | **必须单 worker**；扩容前先改造为外部任务队列 |

## 五、Windows / Git Bash / WSL 专属

| 症状 | 根因 | 处置 |
|---|---|---|
| `/var/run/docker.sock` 变成 `C:/Program Files/Git/var/run/...` | MSYS 路径转换 | 命令前加 `MSYS_NO_PATHCONV=1` |
| 改了 `daemon.json` 无效 | Docker Desktop 应用会用内存态覆盖该文件 | 必须重启**应用**（`taskkill //F //IM "Docker Desktop.exe"` → 写文件 → 启动），不是只 `wsl --shutdown` |
| `dial tcp [::1]:xxxx: i/o timeout` | `localhost` 被解析为 IPv6，而端口映射只监听 IPv4 | 地址统一写 `127.0.0.1` |
| Docker 命令卡住 / 引擎异常 | WSL 后端抽风 | `wsl --shutdown` 后等待引擎恢复（循环探测 `docker info`） |
| 路径含空格/中文导致命令失败 | 未加引号 | 一律 `"$BASE/..."`；避免对含空格路径用 `xargs` |
| 换行符警告（`LF will be replaced by CRLF`） | Git 自动转换 | 无害；需要一致可加 `.gitattributes` |

## 六、一键体检脚本

```bash
#!/usr/bin/env bash
# 应用部署体检：只读检查，不改任何状态
set -uo pipefail
cd "$(dirname "$0")"          # 在仓库根目录执行

echo "== 1. 容器状态 =="
docker compose ps

echo "== 2. 关键端点（经 nginx）=="
for U in "8080|前端首页" "8080/api/v1/health|后端健康" "8080/nginx-healthz|nginx 自检"; do
  P=${U%%|*}; N=${U##*|}
  printf '%-16s %s\n' "$N" "$(curl -s -o /dev/null -w '%{http_code}' --max-time 6 "http://127.0.0.1:$P" 2>/dev/null)"
done

echo "== 3. 容器内直连后端（绕过 nginx）=="
docker compose exec -T backend \
  python -c "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:8000/api/v1/health',timeout=6).status)" 2>/dev/null

echo "== 4. 数据卷 =="
docker volume ls | grep -E 'agent|backend-data' || echo "未找到数据卷"
docker compose exec -T backend ls -lh /app/data 2>/dev/null | head

echo "== 5. 镜像 =="
docker images | grep -E 'agent-(backend|web)' || echo "未找到应用镜像"

echo "== 6. 磁盘 =="
docker system df | head -4
```
