## 一、这批解决什么

`analysis/12` §2.3 与 `analysis/06` §7 列出的**前后端契约差异**，本质是**后端语义变了、前端没跟上**：

| 差异 | 后端 | 前端 | 用户可见后果 |
| --- | --- | --- | --- |
| `done.status` | 发送 `status`（含 `awaiting_approval`） | `DoneEv` 未声明不消费 | 无法区分「完成」与「待审批」 |
| `busy` 事件 | 并发满时发送 | `AgentEvent` 联合类型**缺 `busy`** | 用户只看到「流突然结束」，不知道是并发满 |
| `memory_item` 事件 | 记忆工具调用时发送 | 联合类型**缺** | 记忆行为不可见 |
| `references` vs `reference_cards` | 两个不同字段 | 分别消费，无统一抽象 | 两种引用渲染逻辑 |
| 上传白名单 | 后端 `core/uploads.py` + 环境变量可覆盖 | 前端 `upload-policy.ts` **另存一份** | 三方不一致 → 前端放行后端拒绝 |
| `/metrics` 口径 | `runs_today` 实为「最近 24 小时」 | 前端按「今天」展示 | 数字对不上 |
| SSE 重连 | — | 无限重订阅，无退避无上限 | 网络异常时打满 CPU |

### P4-01 · 前端补 `busy` 与 `memory_item` 事件类型（R-28）　<sub>来源：`design/09` **R-28** ／ `analysis/12` **D-40**</sub>

| 要素 | 内容 |
| --- | --- |
| **现象** | 后端发 25 个事件名，前端 `AgentEvent` 联合类型只覆盖 **22** 个——缺 `busy` 与 `memory_item` |
| **根因** | S4 加了 `busy`、S5 加了 `memory_item`，前端 `types.ts` 未同步 |
| **整改** | ① `types.ts` 的 `AgentEvent` 补两个成员；② `WorkspaceView.appendEvent()` 增加 `busy` 分支 → 展示「并发已满，请稍后重试」的**专门提示**（不是通用错误条）；③ `memory_item` → 触发记忆提示 |
| **验收断言** | ① `AgentEvent` 成员数 = **25**（与后端事件名一一对应，单测断言）；② 占用全部并发槽时前端显示「并发已满」而非「未知错误」 |
| **测试用例 ID** | `DOM-04`（`busy` 提示）、`SSE-01` |
| **回归风险** | 低 |
| **回滚** | 移除两个分支 |

### P4-03 · SSE 重连加退避与上限（R-26）　<sub>来源：`design/09` **R-26** ／ `analysis/12` **前端-S6-08**</sub>

| 要素 | 内容 |
| --- | --- |
| **现象** | `streamResearchWithReconnect` 每次断流后固定 `sleep(1000)` 重订阅，**无最大次数、无指数退避** |
| **根因** | 早期实现只考虑「一次断流」场景 |

| **测试用例 ID** | `SSE-RECONNECT-01` |
| **回归风险** | 低 |
| **回滚** | 改回固定 1s |
