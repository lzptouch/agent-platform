> **优先级**：P2 ｜ **规模**：3 人日 ｜ **依赖**：无 ｜ **台账**：`../analysis/12` D-25、D-34、D-29、S-08-06、D-39、S-08-08、S-09-07
> **状态**：✅ 已完成（2026-10-28）——交付实况见 [`../design/08`](../design/08-实现交付记录.md) §17

## 一、目标

修掉七处「字段/参数存在但语义没落地」或「口径不一致」的问题——它们都不影响主流程，但会让运维与排期基于错误数字。

现状（事实）：
- `D-34`：`rag/ingest.py` 增量入库按文件哈希去重**未实现**，重复 chunk 会累积；
- `D-25`：`core/logging.py` 已有 S7 的 JSON 行格式器与上下文，但**没有文件 handler**（仍只在 stderr）；
- `D-39`：`agent_service` 的 `approval_required` 事件**不带 `run_id`**，而前端 `ApprovalRequiredEv.run_id` 必填；
- `S-08-06`：`run_service.count_today_runs` 用 **UTC 日期**，与任务的 `timezone` 字段不一致；
- `S-08-08`：`recover_interrupted` 只在**启动时**跑一次，宽限期外的 `running` 永久停留；
- `S-09-07`：`RUN_INGEST=true` 时每次启动都执行入库，重复启动会重复入库；
- `D-29`：`scheduled_tasks.allow_dangerous_tools` 字段**无生效分支**（危险动作现由权限引擎统一裁决，但该开关仍应真正起作用）。

### 5.2 顺带修掉的既有缺陷（不在原七步里，但同属"口径不一致"）

1. **全新数据库建不起来**：`0001` 用当前 ORM 建表（已是 S2 之后的 `pattern` 结构），
   而 `0002`/`0004` 仍按旧结构（`target`）读写 → **新装环境在 0002 直接崩**（老库不受影响，所以一直没暴露）。
   修法：`0002` 按列名分支写入、`0004` 已是目标结构则跳过重建；新增迁移链冒烟测试。
2. **日志上下文是"定义了不调用"**：`set_context()` 从未被调用 → 即使落盘也检索不到 `request_id`。
   现已在请求中间件与 `run_executor` 真正绑定。
3. **落盘日志被 alembic 抹掉**：`migrations/env.py` 的 `fileConfig()` 会重置 root 的 handler
   并**禁用应用自己的 logger** → 迁移之后应用日志一条都不出。
   修法：`fileConfig(..., disable_existing_loggers=False)` + 文件日志改到迁移**之后**再挂。
4. **e2e 骨架的管道死锁**（`tests/common/harness.py`）：后端 stdout 用 `PIPE` 却从不抽干
   → 缓冲写满后后端阻塞在 write，表现为"跑到一半所有接口超时"。现改为后台线程持续抽干。

### 5.4 遗留（如实标注）

- **Milvus 侧未真机验证**：本机无 `milvus_lite`（Windows），`insert_chunks` / `delete_by_doc_id`
  的真实调用未跑过；幂等逻辑在**台账 + 调用序列**层面测过（不重复 embed/insert、旧版本被删）。
- **旧 collection 自动重建**：老库里的 collection 没有 `doc_id` 字段 → 下次入库会**重建并丢数据**
  （已写告警）。这是"要么重建、要么无法按文档去重"的取舍。
- **采样率默认 20%**：DEBUG 日志会丢 80%（可调 `log_debug_sample_rate=1.0`）。
- **周期巡检以 `started_at` 为基准**：没有心跳字段，长任务超过宽限期仍可能被误判
  （宽限期已按 `schedule_run_timeout + 60` 取值，风险可控但非零）。
