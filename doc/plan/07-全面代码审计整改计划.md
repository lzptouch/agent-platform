### W0-01 · contextvar 跨线程丢失（**根因修复**）

- **优先级**：P0 ｜ **工时**：M ｜ **依赖**：无

**现象**
`backend/app/api/v1/agent.py:47` 把 `executor.execute_stream(...)`（**同步生成器**）直接交给 `StreamingResponse`。Starlette 对同步迭代器走 `iterate_in_threadpool` → `anyio.to_thread.run_sync(_next, iterator)`；anyio 在**事件循环线程**做 `copy_context()`（`_backends/_asyncio.py:2698`），worker 线程用 `context.run(func)`（`:1100`）执行 `next()`。

生成器体内的 `current_run_context.set(ws_ctx)`（`run_executor.py:300`）写入的是**本次 `next()` 的临时 Context 副本**，随 `next()` 返回即丢弃；下一次 `next()` 是**全新的** `copy_context()` → 值全部消失。

**复现**（决定性）
```bash
backend/.venv/bin/python /tmp/repro_ctxvar.py
# → LookupError: <ContextVar name='ctx' ...>
```

**根因**
把「跨请求隔离的可变状态」放在 `contextvars` 上，却把它**写在一个会被 Starlette 跨线程消费的同步生成器里**。`contextvars` 的隔离语义是「**每个执行上下文**一份」，而 Starlette 的同步生成器适配**每次 `next()` 都是一个新上下文**。

**整改（采纳方案 B：显式传递 run 上下文）**

> **方案 A（async 生成器）不成立**：即使包成 async 生成器，只要内部用 `anyio.to_thread.run_sync` 逐次推进，每次调用仍会 `copy_context()` → **仍然断裂**。
> **方案 C（一次性跑完整个 for 循环）** 会失去流式增量，**不采纳**。

```python
# 1) app/services/workspace/service.py —— ContextVar 保留，供同步/阻塞路径使用
current_run_context: ContextVar[dict | None] = ContextVar("run_workspace_ctx", default=None)

# 2) app/services/tool_registry.py —— ToolRegistry 持有 run 上下文（实例级，不走 contextvar）
class ToolRegistry:
    def __init__(self, ..., run_ctx: dict | None = None):
        self.run_ctx = run_ctx          # ← 新增

    @classmethod
    def _emit_artifact(cls, tool_input: dict, run_ctx: dict | None = None) -> dict:
        ctx = run_ctx or current_run_context.get()      # ← 优先显式
        if not ctx:
            return {"error": "当前无运行上下文，无法登记产物"}

# 3) app/services/code_executor.py —— 同理
class CodeExecutor:
    def __init__(self, ..., run_ctx: dict | None = None):
        self.run_ctx = run_ctx
    @property
    def cwd_dir(self) -> Path:
        ctx = self.run_ctx or current_run_context.get()  # ← 优先显式
        ...

# 4) app/services/agent_service.py —— stream() 接受并透传 run_ctx
def stream(self, prompt, model, ..., run_ctx: dict | None = None):
    registry = ToolRegistry(..., run_ctx=run_ctx)
    executor = CodeExecutor(..., run_ctx=run_ctx)
    ...

# 5) app/services/run_executor.py:319 与 :531（审批恢复段）—— 调用点补传
stream = self.agent_service.stream(
    prompt, model, ...,
    run_id=run_id, session_id=session_id,     # ← 同时关闭 AUD-C02
    run_ctx=ws_ctx,                           # ← 核心
)
```

**验收断言**
1. `POST /api/v1/agent/run`（SSE）产出的事件流中，`emit_artifact` 工具结果**不含** `"当前无运行上下文"`；
2. 同一 run 执行后，`SELECT count(*) FROM artifacts WHERE run_id = ?` **> 0**；
3. `SELECT count(*) FROM changes WHERE run_id = ?` **> 0**（写文件类工具至少触发一次）；
4. `SELECT run_id FROM llm_calls WHERE run_id = ?` **非空**；
5. `SELECT prompt_tokens FROM runs WHERE id = ?` **非 NULL 且 > 0**；
6. `tool_load` 之后**第二轮**的请求体里**包含**被 load 的工具 Schema（抓取 OpenAI 兼容请求）。

**测试用例 ID**
`T-AUD-W0-01`（后端，6 个断言）

**回归风险**
- **中**：`ToolRegistry` / `CodeExecutor` 的构造签名变更 → 所有构造点需同步（`core/state.py`、`agent_service.py`）；
- **中**：审批恢复段（`run_executor.py:531`）同样要补 `run_ctx`；
- **低**：`current_run_context` 保留 → 同步路径行为不变。

**回滚方式**
`git revert`；`run_ctx` 参数为**可选**（默认 `None` → 回落到 contextvar），回滚后旧行为立即恢复。

### W0-02 · 记忆端点任意文件读 / 写 / 删

- **优先级**：P0 ｜ **工时**：S ｜ **依赖**：无

**现象**
`app/services/exec/memory.py:176` 的 `delete_memory(scope, path)` 直接 `Path(path).unlink()`，**从不校验 path 是否位于 `memory_root(scope)` 之下**；`write_memory`（`:161`）的 `root / name` 未过滤 `/` 与 `..`。API 层（`api/v1/context.py:93/104/108`）只校验非空。

**根因**
写入侧与删除侧都把「路径」当成了**可信输入**——它来自请求体。

**整改**
```python
# backend/app/services/exec/memory.py
import re
_SAFE_NAME = re.compile(r"^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$")

def _resolve_in_root(scope: str, path: str) -> Path:
    """把用户给的路径限制在 memory_root(scope) 之内。"""
    root = memory_root(scope).resolve()
    p = Path(path).expanduser()
    p = (p if p.is_absolute() else root / p).resolve()
    if not p.is_relative_to(root):
        raise ValueError(f"路径超出记忆根：{path}")
    return p

def write_memory(scope, name, content, *, tags=None) -> MemoryItem:
    if not _SAFE_NAME.fullmatch(name.removesuffix(".md")):
        raise ValueError("记忆名非法（只允许字母/数字/点/下划线/短横线）")
    root = memory_root(scope); root.mkdir(parents=True, exist_ok=True)
    safe = name if name.endswith(".md") else f"{name}.md"
    path = (root / safe).resolve()
    assert path.is_relative_to(root.resolve())          # 双保险
    path.write_text(header + content, encoding="utf-8")
    ...

def delete_memory(scope: str, path: str) -> bool:
    p = _resolve_in_root(scope, path)          # ← 越界直接抛错
    ...
```
```python
# backend/app/api/v1/context.py —— scope 校验 + 异常映射
if scope not in mem.SCOPES:
    raise HTTPException(status_code=422, detail=f"未知记忆作用域：{scope}")
try:
    return {"ok": mem.delete_memory(scope, path)}
except ValueError as exc:
    raise HTTPException(status_code=422, detail=str(exc)) from exc
```
> `memory_root(scope)` 对未知 scope 抛 `ValueError` —— 补上 scope 校验后 `AUD-M32`（500）一并关闭。

**验收断言**
1. `DELETE /api/v1/memories {"scope":"project","path":"/etc/passwd"}` → **422**（不是 200 / 删除成功）；
2. `POST /api/v1/memories {"scope":"project","name":"../../../../tmp/pwned","content":"x"}` → **422**，且 `tmp/pwned.md` **不存在**；
3. `DELETE /api/v1/memories {"scope":"bogus","path":"x"}` → **422**（不是 500）；
4. 合法路径的写入 + 删除仍成功。

**测试用例 ID**：`T-AUD-W0-02`（4 个断言）

**回归风险**：**低** —— 现有合法用法路径不变；仅拦截越界。

**回滚方式**：`git revert`；越界拦截是纯增量校验，回滚后恢复原行为。

### W0-03 · 产物下载路径穿越

- **优先级**：P0 ｜ **工时**：S ｜ **依赖**：无

**现象**
`api/v1/workspace.py:170`：`path = get_workspace_dir() / str(target["path"])` —— `target["path"]` 来自 DB；绝对路径会**胜出**（`Path("/ws") / "/etc/passwd"` → `/etc/passwd`）；且用的是**全局当前工作区**而非 run 绑定的 `workspace_root`。

**根因**
下载端点与 `change_revert`（`workspace.py:141` 用 `_ws_root`）**标准不一致**，且缺 `is_relative_to` 校验。

**整改**
```python
# backend/app/api/v1/workspace.py
from pathlib import Path

@router.get("/artifacts/{artifact_id}/download")
def download_artifact(artifact_id: str, ...):
    artifact = art.get_artifact(artifact_id)          # 需新增 getter
    if artifact is None:
        raise HTTPException(status_code=404, detail="产物不存在")
    root = Path(_ws_root(artifact["workspace_id"])).resolve()
    path = (root / str(artifact["path"])).resolve()
    if not path.is_relative_to(root):                   # ← 核心
        raise HTTPException(status_code=403, detail="产物路径越界")
    if not path.is_file():
        raise HTTPException(status_code=404, detail="产物文件不存在")
    return FileResponse(path, media_type=artifact.get("mime") or "application/octet-stream", ...)
```
**配套**：`services/workspace/artifacts.py:53` 的 `register_artifact` 对工作区外路径**拒绝登记**（不再原样存绝对路径）：
```python
p = (workspace_root / raw_path).resolve()
if not p.is_relative_to(workspace_root.resolve()):
    raise ValueError(f"产物路径越界：{raw_path}")
path = str(p.relative_to(workspace_root.resolve()))
```

**验收断言**
1. 构造 `artifacts.path = "/etc/passwd"` 的行 → 下载端点返回 **403**；
2. `artifacts.path = "../../etc/passwd"` → **403**；
3. 合法相对路径 → **200** 且内容正确；
4. `register_artifact` 传入工作区外路径 → 抛错且 **DB 无新增行**；
5. 属于**历史工作区**的产物，用其 `workspace_id` 下载 → **200**（不再 404）。

**测试用例 ID**：`T-AUD-W0-03`（5 个断言）

**回归风险**：**中** —— 既有产物若曾以绝对路径入库，修复后**将无法下载**（需一次性数据迁移，见回滚）。

**回滚方式**：`git revert`；配套一条数据订正脚本，把历史绝对路径产物重写为相对路径（纳入 `W6`）。

### W1-01 · tool scope 规则可达性

- **优先级**：P1 ｜ **工时**：M ｜ **依赖**：无

**现象**：`permissions.decide()` 在 **file 维度**命中后即 `return`（`:268`），**tool scope 永远到不了**；而内置规则 `("tool","write_file","ask",...)`（`:83`）正是 tool scope。结果：工作区内 `write_file` **恒 ALLOW**（无审批），与规则表相反。`effective_level()`（`:570`）只用 tool 维度 → **API 返回的档位与实际裁决不一致**。

**根因**：规则求值顺序把「更具体的维度」放在「更粗的维度」之前，且**命中即返回**，没有 fallback。

**整改**
```python
# backend/app/services/security/permissions.py :: decide()
def decide(self, request: PermissionRequest) -> Decision:
    # ① tool 维度优先（内置规则都写在这个维度）
    rule = _match_rules("tool", request.tool, rules, request.workspace_id)
    if rule:
        return Decision(rule.decision, rule.reason, "tool", request.tool)
    # ② file 维度（命中后不再 return，继续走 tool fallback）
    if request.path is not None:
        rule = _match_rules("file", request.path, rules, request.workspace_id)
        if rule:
            return Decision(rule.decision, rule.reason, "file", request.path)
        if _is_under(request.path, ws_root):
            return Decision(ALLOW, "工作区内路径", "file", request.path)
    # ③ command 维度
    ...
```
> **同时修 `effective_level()`**：必须用与 `decide()` **相同的请求形状**计算，否则 API 返回的档位仍与实际裁决不一致。

**验收断言**
1. 工作区内 `write_file` → 决策为 **ask**（而非 allow）；
2. `GET /permissions/rules` 返回的 `effective_level` 与实际 `decide()` 结果**一致**；
3. `set_level("readonly")` 后 `execute_bash` → **deny**；
4. 显式 `allow` 的 tool 规则仍生效（不被 file 维度的 allow 抢先）。

**测试用例 ID**：`T-AUD-W1-01`（4 个断言）

**回归风险**：**高** —— 改变了默认裁决顺序，**所有工具调用都会多走一次 tool 维度匹配**。必须先跑全量回归并对比裁决分布（建议加一条「裁决分布快照」测试）。

### W3-02 · RAG collection 重建时同步清台账

- **优先级**：P0 ｜ **工时**：S ｜ **依赖**：无

**现象**：`create_collection(recreate=False)` 在检测到旧 schema 缺 `doc_id` 时会 `drop()` 重建（`milvus_store.py:56`），但**没有清台账**（只有 `recreate=True` 才 `ledger.clear_ledger()`）→ collection 空、台账说「已入库」→ **全部 skip** → **RAG 库静默为空**。

**根因**：幂等键（台账）与目标状态（collection）**不同步更新**——这是「增量幂等」最危险的形态。

**整改**
```python
# backend/app/services/rag/milvus_store.py
def create_collection(self, recreate: bool = False) -> tuple[Any, bool]:
    """返回 (collection, 是否重建过)。"""
    ...
    if need_recreate:
        self._drop_and_recreate()
        return col, True
    return col, False

# backend/app/services/rag/ingest.py
col, recreated = create_collection(recreate=recreate)
if recreated:
    logger.warning("collection schema 变更已重建 —— 同步清空入库台账")
    ledger.clear_ledger()          # ← 关键：台账与目标状态同步
```
> **更稳的方案**：让幂等判定**不依赖台账**，而依赖 collection 内的实体数（`col.num_entities`）。改动面大，本批采用「重建即清台账」+ 开关。

**验收断言**
1. 构造「旧 schema collection + 已有台账」→ 执行入库 → **collection 内有实体**（当前：0）；
2. 入库日志**不出现**「跳过 N」而实际为空的组合；
3. 正常增量入库（无 schema 变更）→ 幂等跳过**仍然生效**（不重复插入）。

**测试用例 ID**：`T-AUD-W3-02`（3 个断言）

**回归风险**：**中** —— 清台账会导致**重新入库**（Embedding API 调用量上升）。需在日志中明确告警。

**回滚方式**：`git revert`；`clear_ledger()` 加开关 `settings.rag_clear_ledger_on_recreate`（默认 True）。

### W5-05 · **验收口径升级**（本次审计最重要的流程改进）

- **优先级**：P0 ｜ **工时**：M ｜ **依赖**：无（可先行）

**现象**
`design/01` §9 的 ✅ 判定口径是：「代码有生效逻辑 **且** 有测试覆盖 **且** 有阶段执行记录」。**这三条都成立，仍可能出现「测试走同步路径、生产走 SSE 路径」**。22 条虚高 ✅ 全部源于此。

**整改**：把口径升级为**四维**，并要求**逐维给出证据**：

| 维度 | 判定依据 | 缺失时的处理 |
| --- | --- | --- |
| ① **生产路径可达** | 该能力在**真实调用链**上被触发（不是「某处有个函数」） | ⛔ 或 ⏳ |
| ② **真实调用链覆盖** | 测试用例走的是**与生产相同的调用路径**（同步 vs 流式、mock vs 真实配置、串行 vs 并发） | ⛔ 或 ⏳ |
| ③ **异常路径覆盖** | 早退分支、失败分支、并发分支**有独立断言** | ⏳ |
| ④ **状态机终态一致** | 状态迁移有守卫，终态**不可被覆盖** | ⏳ |

**新增门禁**（写入 `plan/05` 的 CI 矩阵）：
- **G-1 流式门禁**：任何走 `StreamingResponse` 的端点，必须有一条**通过 HTTP 实跑**的用例（不是直接调 service 函数）；
- **G-2 配置门禁**：任何「读配置文件」的分支，必须有用例**真的写一份配置文件**再跑（如 MCP 必须写 `~/.agent/mcp.json`）；
- **G-3 异常路径门禁**：任何 `acquire`/`release` 配对资源（信号量、槽位、锁），必须有「早退后资源仍可用」的断言；
- **G-4 幂等门禁**：任何幂等机制，台账状态与目标状态必须在**同一分支**更新；
- **G-5 并发门禁**：任何标称「并行/隔离/池化」的能力，必须有 ≥2 并发用例。

**验收断言**
1. `design/01` §9 的口径段落包含上述四维；
2. `plan/05` 的 CI 矩阵包含 G-1~G-5；
3. 22 条 `AUD-Fxx` 中，每条都能指出它**违反了哪一维**。

**测试用例 ID**：`T-AUD-W5-05`（3 个断言）

**回归风险**：**低**（流程）；但会**显著提高后续批次的验收成本**（这是有意的）。

**回滚方式**：不适用（文档）。

### 11.5.4 变异可检出性验证（W11-01 的验收口径）

### 11.5.5 外科式变异验证（**只注入单个缺陷**）

> ⚠️ 上面的 `git stash` 验证**不够干净**：`git stash` 回退的是 **git HEAD**
> （远早于 P1~P6 的未提交改动），不只回退本批改动。
> 因此又做了一次**外科式变异**——用脚本精确注入**单个**缺陷再恢复：

| 变异 | 注入内容 | 结果 |
| --- | --- | --- |
| W2-01 槽位泄漏 | `_fail()` 中去掉 `_release_slot()` 调用 | **2 failed** → 恢复后 **passed** |
| W0-01 contextvar | 把 `run_agent` 换成**真实修复前实现**（同步生成器 → `StreamingResponse`） | **2 failed**（失败信息精确指向「artifacts 表为空」「写盘未落在 run 绑定工作区」）→ 恢复后 **passed** |

> 第一版变异曾试图「去掉 `ctx.run`」——**无效**：因为 `asyncio.to_thread` 本身就会
> `copy_context()` 一次，整个 `drain` 仍在同一 Context 内 → contextvar 并未丢失。
> 真正的原实现是「同步生成器直接交给 `StreamingResponse`」，
> 由 Starlette 的 `iterate_in_threadpool` **逐次** `copy_context()` → 才会断。
