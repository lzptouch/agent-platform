### W7-01 · SPA 回退路由路径穿越

- **优先级**：P0 ｜ **工时**：S ｜ **依赖**：无

**现象**
`backend/app/main.py:273-283` 的 `spa_fallback` 用 `target = FRONTEND_DIST / full_path` 后直接 `target.is_file()` → `FileResponse(target)`，**无 `resolve()` + `is_relative_to` 校验**。

**运行时验证**
```
full_path='../secret.txt'    → is_file()=False
full_path='../../secret.txt' → is_file()=True   ← 逃逸成功
```
`Path.is_file()` 跟随 `..` 解析；`full_path` 是路径参数，`%2e%2e%2f` 被 uvicorn 解码即成为 `../`。

**根因**
这是「路径边界用字符串拼接而非 `is_relative_to`」在一轮 `analysis/18` §1.2 根因 ④ 中列举的第 7 处 —— 但它**逃过了两轮审计**，原因是：`include_in_schema=False` 使它**不出现在 OpenAPI 端点表**中，人工核对端点清单时必然被跳过；且它位于 `@app.get` 装饰器下的普通函数，视觉上与普通静态托管无异。

**整改**
```python
# backend/app/main.py
@app.get("/{full_path:path}", include_in_schema=False)
def spa_fallback(full_path: str) -> FileResponse:
    """SPA 路由回退：非 /api 路径一律返回 index.html；/api 未匹配路径保持 404。"""
    if full_path.startswith("api/"):
        raise HTTPException(status_code=404, detail=f"API 路径不存在: /{full_path}")
    dist_root = FRONTEND_DIST.resolve()
    try:
        target = (dist_root / full_path).resolve()
    except (OSError, ValueError):
        return FileResponse(dist_root / "index.html")
    # ← 核心：必须落在 dist 目录内，否则一律回退 index.html
    if full_path and target.is_file() and target.is_relative_to(dist_root):
        return FileResponse(target)
    return FileResponse(dist_root / "index.html")
```
> **顺带**：`/assets` 的 `StaticFiles` 挂载由 starlette 自行处理路径安全，无需改动；但需在 `AUD2-C01` 的验收里确认 `/assets/../../etc/passwd` 也被拒绝。

**验收断言**
1. `GET /../../secret.txt` → **不返回**该文件（返回 index.html 或 404）；
2. `GET /assets/../../etc/passwd` → **404**；
3. `GET /some/spa/route`（不存在的 SPA 路由）→ 仍返回 **index.html**（SPA 路由回退不被破坏）；
4. `GET /api/v1/nonexistent` → **404**（API 未匹配路径仍保持 404，不被 SPA 回退吞掉）；
5. `GET /index.html` 与 `GET /` → **200**。

**测试用例 ID**：`T-AUD2-W7-01`（5 个断言，**必须走 HTTP**）

**回归风险**
- **中**：`is_relative_to` 会拒绝带符号链接指向外部的真实文件 —— 这是**期望行为**，但需确认 `frontend/dist` 内没有指向外部的软链；
- **低**：SPA 路由回退行为不变。

**回滚方式**：`git revert`；**不建议回滚**（这是可直接利用的文件读取）。

### W7-02 · 桌面令牌随任意 URL 外发

- **优先级**：P0 ｜ **工时**：S ｜ **依赖**：无

**现象**
`frontend/desktop/src/main/ipc.ts:171-173`：
```ts
const target = new URL(url, base);
... http.get(target, { headers: { "X-Agent-Desktop-Token": handle.token } })
```
`url` 完全由渲染进程提供；`new URL(url, base)` 在 `url` 是绝对地址时**忽略 `base`**。

**根因**
「把用户输入拼进 URL 后再加凭据」的模式，且缺少 **origin 白名单**。

**整改**
```ts
// frontend/desktop/src/main/ipc.ts
const target = new URL(url, base);
const allowed = `http://127.0.0.1:${handle.port}`;
if (target.origin !== allowed) {
  return fail("E_INVALID", `目标 origin 不被允许: ${target.origin}`);
}
... http.get(target, { headers: { "X-Agent-Desktop-Token": handle.token } })
```

**验收断言**
1. 渲染进程传入 `http://evil.com/x` → IPC 返回**失败**，且**没有**向外部发起任何请求（用 mock 断言 `http.get` 未被调用）；
2. 传入 `http://127.0.0.1:<本机端口>/api/v1/health` → **成功**；
3. 传入 `http://127.0.0.1:<其它端口>/x` → **失败**（origin 必须精确匹配，不能只比 host）。

**测试用例 ID**：`T-AUD2-W7-02`（3 个断言）

**回归风险**：**低** —— 渲染进程本来只应访问本机后端。

**回滚方式**：`git revert`。

### W7-03 · cron / RRULE 槽位的时间锚点（**定时任务停摆**）

- **优先级**：P0 ｜ **工时**：M ｜ **依赖**：无

**现象（三处同源）**
| 位置 | 现状 |
| --- | --- |
| `scheduler_service.py:490` | `cursor = row.created_at` → `for _ in range(200)` 取最后一个 |
| `scheduler_service.py:523` | `expand_slots(rule, local_anchor, limit=400, horizon_days=370)` 同样以 `created_at` 为锚 |
| `scheduler_service.py:928` | `cursor = since` → `for _ in range(200)` |

**运行时验证**
```
_cron_last_fire() 返回 : 2026-10-29 09:20:00+00:00   ← 第 200 次迭代的截断值
真实最近一次触发时刻   : 2026-10-31 09:15:00+00:00
偏差                   : 47.9 小时
```
后果：`scheduled_for` 被钉死 → `uq_runs_task_slot` 冲突 → `create_run()` 返回 `None` → `scheduler_service.py:595` 判定「槽位已执行过，跳过」→ **此后每次触发都用同一陈旧槽位 → 任务永久停摆，日志只打 INFO**。

**停摆阈值**：`*/*1` ≈ 3.3 h ｜ `*/5` ≈ 16.7 h ｜ 每小时 ≈ 8.3 d ｜ 每天 ≈ 200 d ｜ RRULE DAILY ≈ 400 d

**根因**
**正向遍历「从创建时刻到现在」** —— 迭代次数与任务年龄耦合，任务越老越早失效。正确做法是**从 `now` 逆向求最近一次触发**。

**整改**
```python
# backend/app/services/scheduler_service.py
def _cron_last_fire(self, row) -> str | None:
    """最近一次 cron 触发时刻（**从 now 逆向求**，不依赖任务年龄）。"""
    trigger = self._build_trigger(row)
    now = datetime.now(timezone.utc)
    # get_next_fire_time(prev, now) 反查：以 now 为锚向前找第一个 <= now 的触发点
    prev = trigger.get_next_fire_time(None, now - timedelta(days=1))   # 粗定位
    # 逐个向前回退，直到 next > now
    while prev is not None and prev <= now:
        nxt = trigger.get_next_fire_time(prev, now)
        if nxt is None:
            break
        prev = nxt
    # prev 即「最近一个 <= now 的触发点」的前一个，用它算最后一次
    return prev.strftime("%Y-%m-%dT%H:%M:%S") if prev else None
```
> **更稳妥的实现**：用 `trigger.get_next_fire_time(None, now)` 拿到**下一次**触发，再减去一个周期得到上一次；或直接维护「上次实际触发时刻」到 `scheduled_tasks` 表（**推荐**：加一列 `last_fired_at`，由调度器在成功触发后更新，槽位直接取该值 + 当前周期）。
> **推荐方案**：新增 `scheduled_tasks.last_fired_at` 列（迁移 `0014`），槽位 = `last_fired_at` 的下一个触发点。**彻底消除「计算最近触发点」这一脆弱推导**。

**配套（同一批次）**
- `scheduler_service.py:928`（补跑）：改为从 `since` **逆向**求窗口内最后一次触发；
- `scheduler_service.py:523`（RRULE）：`expand_slots` 增加 `anchor=now` 的反向模式；
- `rrule.py:245`（`AUD2-H08`）：`rrule_to_cron` **丢弃 INTERVAL**、`DAILY` 的 `*/N` 落在日-of-月字段 → 触发时刻与 RRULE 语义系统性偏离。**必须与本项一起修**，否则槽位对了、触发还是错的。

**验收断言**
1. `created_at` 为 **2 天前**的 `*/5` 任务 → `_compute_slot()` == **最近一次 `*/5` 触发时刻**（偏差 < 5 分钟）；
2. `created_at` 为 **400 天前**的 DAILY 任务 → 槽位 == **最近一次 00:00**；
3. 连续触发 3 次 → `runs` 表新增 **3 行**，`scheduled_for` **互不相同**；
4. `FREQ=WEEKLY;INTERVAL=2` → 两次触发间隔 **≈ 14 天**（不是 7 天）；
5. `FREQ=DAILY;INTERVAL=2` → 触发日期间隔 **2 天**（不是每月 1/3/5 日）；
6. 任务存活 48 小时后**仍在执行**（回归测试用「把 created_at 改老」模拟）。

**测试用例 ID**：`T-AUD2-W7-03`（6 个断言，含 3 条**时间推进型**用例）

**回归风险**
- **中**：`scheduled_for` 的计算方式变化 → **存量 `runs` 表中已有槽位**与新算法不一致 → 可能出现一次重复执行（幂等键不同）。**缓解**：迁移时把 `scheduled_tasks.last_fired_at` 初始化为「最近一次触发点」，保证首轮不重复；
- **中**：`rrule_to_cron` 改语义 → RRULE 任务的触发时刻会**变化**（原本是错的）→ 需在 `design/01` 记录。

**回滚方式**：`git revert` + 回滚迁移 `0014`（`last_fired_at` 列可保留，不影响旧逻辑）。

### W7-04 · 调度租约原子获取

- **优先级**：P0 ｜ **工时**：M ｜ **依赖**：无

**现象**：`scheduler_service.py:138`
```python
row = db.get(SystemLockRow, LEASE_NAME)
if row is None:
    db.add(SystemLockRow(name=LEASE_NAME, owner=self.owner, ...))
```
读—判断—写之间**无锁、无条件更新、未捕获并发插入的 `IntegrityError`**。

**影响**
- 两个副本同时启动 → 都读到 `None` → 都 `add` → 其一提交时抛未捕获的 `IntegrityError` → **冒泡出 `start()`，整个调度器启动失败**；
- 或两者都判定自己拿到租约 → **双 primary 双调度** → 同一任务被触发两次。

**根因**
根因 ⑦（资源配对与生命周期校验缺失）。

**整改**
```python
# backend/app/services/scheduler_service.py
def _acquire_lease(self) -> bool:
    now = datetime.now(timezone.utc).isoformat()
    with db_session() as db:
        # 单条条件更新：只有「不存在」或「已过期」或「是我」时才接管
        stmt = (
            update(SystemLockRow)
            .where(SystemLockRow.name == LEASE_NAME)
            .where(
                or_(
                    SystemLockRow.owner == self.owner,
                    SystemLockRow.expires_at < now,
                )
            )
            .values(owner=self.owner, expires_at=(now + ttl))
        )
        res = db.execute(stmt)
        if res.rowcount:
            return True
        # 不存在 → 尝试插入（可能并发失败）
        try:
            db.add(SystemLockRow(name=LEASE_NAME, owner=self.owner, expires_at=...))
            db.flush()
            return True
        except IntegrityError:
            db.rollback()
            return False        # ← 并发失败 = 别人拿到了，不是错误
```
> **同时**：`_renew_lease` 也应改为条件更新（`WHERE owner = :me`），避免「续租时已被别人接管」仍续成功。

**验收断言**
1. **两个线程并发**调用 `_acquire_lease()` → **有且只有一个**返回 `True`；
2. 第二个进程启动 → `start()` **不抛异常**，进入 standby；
3. 租约过期后 → 另一进程可接管（`expires_at < now`）；
4. 续租时 `owner` 已被别人接管 → 续租**失败**（rowcount=0）→ 进入 standby。

**测试用例 ID**：`T-AUD2-W7-04`（4 个断言，**必须真并发**）

**回归风险**：**低** —— 单副本行为不变。

**回滚方式**：`git revert`。

### 9.6.7 实施过程中**新发现**并修复的缺陷

| # | 缺陷 | 说明 |
| --- | --- | --- |
| **N-05** | `mcp_manager.py` 只导入 `MCPConnection` 却用 `MCPEndpoint` | **NameError**（比审计预测的 TypeError 更早触发） |
| **N-06** | `aggregate_run()` 在自己的 session 里写 `runs` 行 | 提交后 `version_id` 自增 → `finish()` 的 flush **匹配 0 行** → `StaleDataError` → **整个 run 收尾失败**（潜伏于 `run_id` 恒 NULL 之后，W2-02 修复才暴露） |
| **N-07** | `expand_slots` / 触发器游标保留 dtstart 的**时刻** | 槽位是「该日 BYHOUR:BYMINUTE」→ `slot < cursor` 恒成立 → **DAILY / WEEKLY 规则展开不出任何槽位** |
| **N-08** | `_cron_last_fire` 是 `@staticmethod` 却用 `self` | NameError |
| **N-09** | 会话过期判定 `if issued_at`（`0.0` 为假） | **fail-open** —— 签发时间缺失时过期检查被整个跳过（由新写的 DNS 用例抓出） |
| **N-10** | `permissions.decide()` **从不检查 `tool` scope** | 内置 8 条 tool 规则（含 `write_file→ask`）**全是死规则**；用户写的 `tool:xxx→deny` 也永不生效；**「权限档位」机制因此完全失效**（`set_level()` 写的就是 tool 规则，而 `effective_level()` 恒返回 "allow"） |
| **N-11** | `rescue_missed_runs` 只取前 20 个任务且状态无条件写 `rescued` | 其余任务永不补跑；被退避/配额跳过也报「已补跑」 |

> **N-10 的语义决策**（两轮实施后定稿）：
> ① tool scope 在**该维度没有更具体规则时**才生效 —— `file` 规则（priority=1）
> 比 `tool` 规则更具体，应由它胜出（`test_四类scope分流` 正是这条断言）。
> ② **deny 立即生效**：用户显式写的 `tool:xxx→deny` 立即拒绝。
> ③ **ask 只作兜底**：内置默认 `tool:write_file→ask` 不会把「工作区内路径」的 ALLOW
> 升级成 ASK —— 否则每次写文件都弹审批卡，直接违反 `F-SEC-11`「工作区内常规读写**零弹窗**」。
> ④ **附带收益**：`set_level()`（readonly/ask/allow）写的就是 tool 规则，
> 修复后**权限档位机制首次真正生效**（此前 `effective_level()` 恒为 "allow"）。
