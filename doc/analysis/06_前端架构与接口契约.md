| `runSSE<T>(url, onEvent, options)` | 通用 SSE 解析 | `fetch` + `Accept: text/event-stream`；`TextDecoder({stream:true})` 处理跨 chunk 多字节；按 `\n` 切分并 `replace(/\r$/,'')` 兼容 `\r\n`；**只认 `data:` 前缀**；单条 `JSON.parse` 失败跳过不中断流；`window.__sseDebug` 调试开关 | `sse.ts:34-94` |

| `streamResearchWithReconnect(streamUrl, statusUrl, onProgress, onFinal, signal)` | **断流自动续订 + 去重** | 去重键 `` `${stage}\|${timestamp}` ``；流结束后回查状态，`completed/failed` 才结束，否则 `sleep(1000)` 重订阅；网络不可达 1s 重试；最终态时手工合成 `final` 事件 | `sse.ts:122-179` |

**解析约定**：用 `startsWith('data:')` + `slice(5).trim()`，**兼容无空格的 `data:`**（与后端 `f"data: {json.dumps(...)}\n\n"` 的带空格输出兼容）。

> **桌面事件流前端未消费**：`GET /api/v1/desktop/events` 的 SSE 只在 Electron 壳侧订阅（`apps/desktop/src/main/backend-events.ts`）；Web 端 `stores/desktop.ts` 只调 `/desktop/status` 与 `/desktop/components` 两个普通 REST。

# 第二部分 原理剖析

## 九、为什么前端用原生 fetch 而不是 axios

| 维度 | 原生 fetch | axios |
| --- | --- | --- |
| SSE | ✅ `response.body.getReader()` 可流式读 | ❌ 默认缓冲整个响应，需额外配置 |
| AbortController | ✅ 原生 | 早期版本需 CancelToken（已废弃） |
| 体积 | ✅ 零依赖 | +~30 KB |
| 拦截器 | ❌ 需手写 | ✅ 内置 |

平台的四条 SSE 端点都需要流式读取，axios 的默认行为会把 `text/event-stream` 当普通响应缓冲完再返回，流式感完全丧失。因此选原生 fetch，代价是**拦截器、重试、请求队列都要手写**（`client.ts` 的 `request()` 就是手写的最小实现）。

## 十、为什么 SSE 解析要自研 `runSSE` 而不是用 EventSource

| 维度 | `runSSE`（自研 fetch） | 原生 `EventSource` |
| --- | --- | --- |
| 请求方法 | ✅ 支持 POST（`/agent/run` 需要 body） | ❌ 仅 GET |
| 自定义请求头 | ✅ 可带 `Authorization` 等 | ❌ 仅 URL 参数 |
| 取消 | ✅ `AbortController` | ❌ 需 `close()` |
| 自动重连 | ❌ 需手写（本项目用 `after_seq` 游标） | ✅ 内置（但协议级重连不含业务游标） |
| 事件名 | ❌ 本项目只用 `data:`，不用 `event:` 字段 | ✅ 内置 `event`/`id` 字段解析 |

`/agent/run` 是 POST + 请求体 + SSE 响应的组合，EventSource 根本发不出 POST，只能自研。本项目的后端只用 `data:` 行、不用 `event:` 行，因此 `runSSE` 只解析 `data:` 前缀，比完整 SSE 规范简单。

## 十一、为什么研究进度流要「断流续订 + 去重」三件套

`GET /research/{id}/stream` 的最长时长 1800 秒，期间任何网络抖动都会断流。前端的处理（`sse.ts:122-179`）：

1. **断流后回查状态**：流结束 ≠ 任务结束。断流后先 `GET /research/{id}` 查真实状态，只有仍是 `running` 才重订阅；
2. **全量重放 + 去重**：重订阅从 `sent=0` 全量重放，与已有事件按 `stage|timestamp` 去重，避免时间线出现重复阶段；
3. **限速**：每次断流后 `sleep(1000)`，避免疯狂重连。

这套机制的本质是：**把 SSE 从「一次性流」升级成「可恢复的轮询」**，用业务层的 stage 序号替代传输层的连接保活。

## 十二、为什么取消语义要「后端状态为准」

前端断开 SSE 连接**不等于**后端停止执行——服务端生成器可能还在跑工具。前端因此采用「先 `runCancel`（后端置取消标志），再 `ctl.abort()`（清理连接）」的双步策略（`src/composables/useRunInterrupt.ts`）。

同理，steer 的语义是「下一个工具边界注入」，不是「立即改变当前轮」——UI 必须如实说明生效时机，否则用户会误以为指令没生效。

## 十三、为什么前后端契约要有一个「唯一事实源」

**现状**：项目**不再维护独立的前后端契约文档**——原前端 `docs/` 目录（`api-contract.md` / `sse-protocol.md` / `design-tokens.md`）已整体删除。契约的唯一事实源是**代码 + 本目录两篇**：

| 契约面 | 事实源 |
|---|---|
| HTTP 端点（路径 / 参数 / 错误码） | `05_HTTP接口总览.md` + `apps/server/src/http/routes/` + `apps/server/src/http/routes/*.ts` |
| 前端端点常量与类型 | `src/api/endpoints.ts`、`src/api/types.ts` |
| SSE 事件（类型 / 字段 / 消费方） | `03_Agent执行引擎与事件协议.md` + `src/api/types.ts` |
| 设计 Token | `src/styles/tokens.css` |

**为什么不再单独写一份契约文档**：平行文档必然与代码漂移——被删除的那份契约文档就出现过端点数 35 vs 58、事件数 15 vs 18、端口 5173 vs 5185 的漂移，根因是它与代码**不同库不同构**、没有自动同步机制。把事实写进「与代码同库的分析篇目」比维护一份平行文档更省事也更可靠。

本目录的处理是：
- 端点与事件的事实写进 `05_HTTP接口总览.md`（后端）与本篇 §4/§5（前端），**两处都带行号**；
- 契约差异单列 §7，作为**问题清单**而非「应当如此的约定」。
