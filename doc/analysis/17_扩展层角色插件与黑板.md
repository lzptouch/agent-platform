# 扩展层：角色 / 插件 / 黑板

> **依据代码**：`apps/server/src/http/routes/extensions.ts`、`domain/skill/scanner.ts`、`db/schema.ts`（roles/plugins/board_items/agent_messages 表）（2026-11-01 复核）

# 第一部分 现状事实

## 一、定位与接线状态总览

| 模块 | 数据面 | 管理 API | 执行链路接线 |
|---|---|---|---|
| 角色（roles） | `roles` 表 | ✅ CRUD（4 端点） | ❌ `role_id` 路由参数接收后不产生效果 |
| 插件（plugins） | `plugins` 表 | ✅ scan/install/rollback（4 端点） | ⚠️ 安装只落库，不触发 Skill 重载之外的副作用 |
| 黑板（boards） | `board_items` + `agent_messages` 表 | ✅ items/messages（4 端点） | ❌ 不被 Agent 执行链路使用 |
| 多 Agent 编排 | — | `POST /orchestrate` | ❌ 登记即返回（无实际执行） |

## 二、角色（Roles）

- 表结构：`name`（唯一，**创建后不可改名**）/ `title` / `identity` / `expertise[]` /
  `boundaries[]` / `workflow[]` / `output_style` / `tools[]` / `skills[]` /
  `model_tier` / `builtin` / `enabled`；
- 端点：`GET/POST /roles`、`PATCH/DELETE /roles/{id}`（内置角色不可删，422）；
- **当前生效边界**：纯管理面（CRUD + 前端 RolesView 展示）。
  `/agent/run` 接收 `role_id`，但执行器 `prepare()` 不读取角色
  （无 prompt 注入、无 `model_tier` 选模型、无 `tools[]` 上界裁剪——
  `mergeTools` 的 `roleTools` 参数存在但无人传入，见 `03` §三）。

## 三、插件（Plugins）

- **扫描**（`POST /plugins/scan` → `domain/skill/scanner.ts`）：对目录递归
  内容规则匹配（curl 管道 shell / `rm -rf /` / 凭据读取 / sudo / base64 解码执行
  五条模式 + 缺 SKILL.md 检查）→ 等级 `low/medium/high/critical`，
  `high/critical` → `rejected_by_default=true`；
  响应形状 `{level, findings[], scanned_files, total_bytes, requires_confirmation,
  rejected_by_default}`（前端直接消费）；
- **安装**（`POST /plugins/install`）：写 `plugins` 行（`uq_plugins_name_version`），
  存 manifest JSON；状态 `installed`；
- **回滚**（`POST /plugins/rollback`）：同名版本 ≥2 时，当前版本置
  `rolled_back`、上一版本回 `installed`（409：无历史版本）；
- 当前安装**只登记不部署文件**（不涉及 Skill 目录拷贝）。

## 四、黑板（Blackboard）

- `board_items`：`{board_id, title, detail, status(pending/done), assignee, deps[], result}`；
- 端点：列/增/完成（`complete` 只置 `done` + 写 result——**无依赖图重算**）；
- `agent_messages`：`{board_id, from_role, to_role, kind, content, refs[]}`，
  只有读端点（`GET /boards/{id}/messages`），当前无写入方；
- 前端 `BoardView`（/admin/boards）。

## 五、多 Agent 编排（`POST /orchestrate`）

校验 `strategy ∈ parallel/sequential/review` + 非空 task → 生成 `board_id` →
**直接返回 `{ok, board_id, status:"queued"}`**——无编排执行器、无 worker 分派。
属 API 层占位（语义为「已受理」）。

## 六、前端视图

RolesView / PluginsView / BoardView 三个管理页（/admin/roles、/admin/plugins、
/admin/boards）。

# 第二部分 原理剖析

## 七、为什么插件扫描要「默认拒绝高危」

插件是**第三方代码进入用户机器**的通道。`rejected_by_default` 把
high/critical 级发现变成「需要显式确认才能继续」——安全的默认值 +
明确的用户意图，而不是「一路下一步」。扫描只读不写（`scan` 端点无副作用），
让「先看看里面有什么」零成本。

## 八、为什么角色要有「工具上界」设计（即使当前未接线）

角色的 `tools[]` 声明是**能力收缩**语义：营销角色不该能执行 bash。
它叠加在权限引擎之上（上界裁剪工具清单，权限引擎仍逐次判定）——
两层各管一段：角色管「这个身份该看见什么工具」，权限管「这次调用准不准」。
当前执行路径未传入（§二），属接线缺口（`../design/09` 附录，原 `doc/plan/`）。

## 九、为什么黑板需要依赖与状态字段

多 Agent 协作的核心问题是「子任务之间的序」。`deps[]` + `status` 让
黑板能表达 DAG（就绪判定 = 依赖全部 done）。当前 `complete` 端点不触发
重算（§四）——字段已就位，流转逻辑待接线。

## 十、为什么编排端点可以「先受理后执行」

`POST /orchestrate` 返回 `board_id` + `queued` 的语义是**异步任务受理**：
调用方拿到句柄后应通过黑板/消息端点跟踪。当前执行器缺位使该语义
停在受理层（§五），但接口形状已为异步执行留好位置。

# 第三部分 已知边界

1. 角色不进入执行链路（§二）；2. 插件安装不落文件（§三）；
3. 黑板无写入方/无依赖流转（§四）；4. 编排无执行器（§五）；
5. `agent_messages` 表只有读路径。
