# 第一部分 现状事实

## 一、定位与接线状态总览

S6 阶段引入的扩展层包含四个模块。本次复核的核心结论：

| 模块 | API 端点 | 前端视图 | **Agent 执行链路消费** | 判定 |
|---|---|---|---|---|
| **角色**（roles） | 4 | `RolesView.vue` | ❌ 不参与工具裁剪、不注入 system prompt | **仅 API 层生效** |
| **插件**（plugins） | 4 | `PluginsView.vue` | ✅ 安装的技能会进入 `custom_skills_dir` → 被 Skill 链加载 | **真正生效** |
| **黑板**（boards） | 4 | `BoardView.vue` | ❌ 执行链路完全不使用 | **仅 API 层生效** |
| **多 Agent 编排**（orchestrator） | 0 | — | ❌ `TeamOrchestrator` 仅被测试引用 | **未接线** |
| **Agent 消息 / 收费站**（messaging） | 2 | `BoardView.vue` | ❌ `tollgate` / `build_main_context_block` 未接运行时 | **仅 API 层生效** |

> ⚠️ **概念澄清**：扩展层的「黑板」与运行时的「团队」是**两个完全不同的概念**——

> - **黑板**（`exec/team/blackboard.py`）= 多 Agent 协作的任务板，**只存在于 API 层**。

# 第二部分 原理剖析

## 七、为什么插件是唯一「真正生效」的扩展

插件的产出物是**技能文件**——安装到 `custom_skills_dir` 后，`SkillManager.reload()` 就能发现它，而 Skill 链是**运行时主链路的一部分**（system prompt 注入 + 模型自主 `read_file`）。

也就是说，插件不需要任何**新的执行路径**就能生效：它只是「另一种分发 Skill 的方式」。这就是它比角色/黑板更「实」的根本原因。

角色与黑板则相反：它们需要**新的执行语义**（角色要能裁剪工具、注入 prompt；黑板要能被 Agent 读写），而这些语义在主循环里没有对应的钩子。

## 八、为什么角色要做「工具上界」但当前不生效

角色模型里的 `tools_json`（工具上界）与 `model_tier`（模型档）表达的是「**最小权限 + 能力匹配**」的意图：

| 概念 | 语义 | 现状 |
|---|---|---|
| `ToolProfile`（chat/work） | **按运行模式**裁剪工具 | ✅ 已实现，判定点在 `ToolRegistry.get_combined_tools` |
| `Role.tools_json`（角色上界） | **按角色身份**裁剪工具 | ⬜ 未实现 |

两者的关系应该是「**交集**」——一个 run 的实际工具集 = `ToolProfile` 允许的 ∩ `Role.tools_json` 允许的。当前只有前者。

这个设计本身是合理的（模式是粗粒度、角色是细粒度），但**缺了角色这一层，角色就只是一个描述性元数据**。

## 九、为什么黑板要有「环检测」

黑板的核心机制是**任务项之间的依赖图**。如果 A 依赖 B、B 依赖 C、C 又依赖 A，那么：

- `readiness()` 永远返回「都不 ready」——死锁；
- 没有任何任务项能开始——整个黑板卡死。

因此 `would_create_cycle()` 在**写入时**（而不是计算就绪时）就拒绝成环的依赖边。这是把「不变量检查」放在**状态变更点**而非「查询点」的设计——查询点检查太晚，写入点检查才能保证图始终无环。

## 十、为什么「上下文收费站」是个好设计（即使还没接线）

多 Agent 场景下最贵的成本是**上下文**：每个 Agent 的原始输出都可能有几万字，若全部汇入主上下文，主 Agent 的 prompt 会爆炸。

「收费站」的设计是：子 Agent 的输出**先经过一道压缩/摘要闸门**，主上下文只接收：
- 压缩后的通知（结论 + 置信度）；
- 结构化引用列表（`refs_json`）——需要细节时可回溯。

这与本平台 Agent 循环里的「工具结果截断 8000 字符」是同一个思路的推广：**在信息进入昂贵上下文之前先做一次经济化处理**。
