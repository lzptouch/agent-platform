# 第一部分 现状事实

## 一、并发模型实测

每个执行域的**真实并发原语**（非推测）：

| 执行域 | 并发原语 | 并发度 | 证据 |
|---|---|---|---|
| **Agent 循环**（单请求内） | 串行 for 循环 | 1（一轮一轮来） | `agent_service.py:429` |
| **Agent 请求间** | 无限制（uvicorn worker 内协程） | 受 worker 数与事件循环限制 | `agent_service.py` |
| **工具分发** | **同步** `dispatch()` | 串行（一个 tool_call 跑完再下一个） | `tool_registry.py:225-288` |
| **MCP 调用** | **每次调用新建 stdio 子进程** | 无池化，进程拉起开销 ~百 ms 级 | `mcp_manager.py:162-197` |
| **内置工具执行** | `subprocess.run`（阻塞）+ rlimit 限额 | 占用调用线程 | `code_executor.py`；`exec/limits.py:253` |
| **Research 任务层** | `ThreadPoolExecutor` | 3（`research_max_concurrent`） | `core/config.py:79`；`research_manager.py:37` |

| **SSE 连接** | 每连接一个生成器 | 无连接数指标/上限 | `api/v1/{agent,runs,research,desktop}.py` |

## 二、瓶颈识别

### 2.1 七个瓶颈（按严重度排序）

| # | 瓶颈 | 根因 | 后果 |
|---|---|---|---|
| **B1** | **SQLite 单写者** | WAL 下写仍互斥；事件账本高频写（批量 20 条/2 s）+ 会话写 + 调度写集中在同一库 | 高并发下 `SQLITE_BUSY`，写延迟抖动；极端时 `retry_on_locked` 耗尽 |
| **B2** | **MCP 每次调用新建子进程** | `stdio_client` 每次 `python <server>.py` 拉起解释器 + FastMCP 初始化 | 每次 MCP 工具调用固定付出 ~百 ms 级进程开销；高频调用时延迟显著 |
| **B3** | **LLM 调用非流式** | `chat.completions.create()` 不带 `stream=True`，完整响应后才产 `model_text` | 首 token 延迟 = 完整响应时间；用户长时间无反馈 |
| **B4** | ~~交互式 SSE 无并发护栏~~ **已修**（S4 WP-4.4） | `execute_stream` 现占用 `BoundedSemaphore`（`acquire_slot=True`） | 交互与调度共享同一预算，超限返 `busy` 事件 |
| **B5** | **调度执行阻塞调度线程** | `BackgroundScheduler` 线程里调 `execute_sync` → 内部 `subprocess.run` 阻塞 | 长任务占用调度线程，后续触发被延迟 |
| **B6** | **Milvus Lite 单文件** | 文件锁 + 单机 | 多副本部署时多个后端写同一 `milvus.db` 会冲突；写并发受限 |
| **B7** | **交互与调度共用 2 个并发槽** | `schedule_max_concurrent=2` 同时约束两条链路 | 一个长任务即可占满预算，交互请求全部返回 `busy` |

### 2.2 各瓶颈的量化参考

| 瓶颈 | 量级估算（基于参数，非压测） |
|---|---|
| B1 SQLite | `busy_timeout=5000` + 退避 50/100/200ms ×3 → 单次写最坏 ~5.35 s；事件写 20 条/批 → 单次事务 |
| B2 MCP | 每次调用一次 Python 启动（~50-200ms）+ FastMCP 初始化；10 次连续调用 ≈ 1~2 s 纯开销 |
| B3 LLM | 非流式 → 首 token 延迟 = 完整响应（长答案数秒~数十秒） |
| B5 调度线程 | `execute_sync` 最坏 `max_iterations=20` 轮 × 每轮 LLM+工具，单次任务可跑数分钟 |
| B7 共享槽 | 全平台**同时只能跑 2 个 Agent 运行**（无论交互还是定时） |

### 2.3 ⚠️ 「MCP 连接池化已落地」的说法**不成立**

旧文档称「S7 起 MCP stdio 连接池化」。本次复核确认：

| 事实 | 证据 |
|---|---|
| `chains/mcp/transport.py` **整文件未接线**——全仓仅 3 处引用（`api/v1/system.py:25,64` 取 `pool_size()`、测试、包 `__init__`） | `backend/app/services/chains/mcp/transport.py` |
| 运行时 MCP 调用走 `mcp_manager.py:162-197` 的 `asyncio.run` + `stdio_client`，**每次新建会话** | `backend/app/services/mcp_manager.py:162-197` |
| `pool_size()` 因此**恒为 0**，`/api/v1/metrics` 的 `mcp_connections` 恒为 0 | `backend/app/api/v1/system.py:64` |
| `transport.py` 自身还有骨架问题：stdio 手写 JSON-RPC（`id` 恒 1）、HTTP 腿是自造 REST 约定、`_http_tools` 未归一化 | `transport.py:109-194` |

**B2 依然是当前真实存在的瓶颈**，且比文档描述的更严重——因为没有任何池化尝试在生产路径生效。

# 第二部分 分级改造方案

> **全部为「未实现（参考设计）」**，按优先级排列。

## P0：正确性优先

### 3.1 SQLite 写锁加固（未实现）

| 措施 | 说明 |
|---|---|
| `retry_on_locked` 与 `busy_timeout` 协调 | 当前 `busy_timeout=5000` 已兜底多数情况；把 `append_events` 的重试次数与 `append_message`（20 次）对齐 |
| 事件写合并 | 已做（批量 20 条/2s）；可进一步把「同一 run 的连续事件」在事务内合并为更少事务 |
| 读写分离评估 | SQLite 无真正读写分离；若并发写压力大，评估 `DATABASE_URL` 切 PostgreSQL |

### 3.2 交互式 SSE 并发护栏 ✅ 已落地（S4）

**已实现**：交互路径与调度**共用** `schedule_max_concurrent`，超限时返回 `busy` 事件（不静默丢弃）；`execute_sync` 自行持槽并传 `acquire_slot=False`，避免预算折半。

### 3.3 交互与调度拆分为独立并发上限（未实现）

当前两条链路共用 2 个槽（见 B7）。建议拆为两个独立信号量：

```python
# 未实现（参考实现）
self._interactive_sem = BoundedSemaphore(settings.interactive_max_concurrent)  # 如 4
self._scheduled_sem = BoundedSemaphore(settings.schedule_max_concurrent)      # 保持 2
```

## P1：延迟优化

### 3.4 LLM 调用改流式（未实现）

`chat.completions.create(stream=True)`，增量产出 `model_text`。收益：首 token 延迟从「完整响应时间」降为「网络 RTT + 首个 token」。

> 需同时补 `sse_first_token_seconds` 指标（见 `10` §4.2）。

### 3.5 MCP stdio 连接池化（**未实现**——`transport.py` 未接线）

为每个 Server 维护一个**长驻 stdio 子进程池**（如每 Server 2 个连接轮换），替代「每次调用新建」。需注意跨事件循环持有 `ClientSession` 的坑（这正是当初选「每次新建」的原因——池化需在同一事件循环内复用）。

**前置**：先把 `chains/mcp/transport.py` 接入运行时（或重写 `MCPManager` 内部），否则池化代码写了也不会生效。

### 3.6 Web 爬虫加并发上限（未实现）

当前每 URL 一个原生线程、无信号量。改为 `ThreadPoolExecutor(max_workers=N)` 或加 `BoundedSemaphore`。

## P2：结构升级

### 3.7 Milvus Lite → Standalone（未实现）

`deploy/docker-compose.milvus.yml` 已提供叠加文件。切换后：`MILVUS_DB_PATH` 指向服务地址，解除单文件锁，支持多副本读。

### 3.8 uvloop + 多 worker（未实现）

```bash
uvicorn app.main:app --workers 4 --loop uvloop
```

**硬约束**：多 worker = 多进程 = 多副本。必须先满足：

1. 调度租约（已具备，`system_locks`）；
2. Milvus Standalone（否则多进程写同一 `milvus.db` 冲突）；
3. SQLite 换 PostgreSQL 或接受多副本各写各的（数据分裂）。

**不建议在当前单文件存储下开多 worker。**
