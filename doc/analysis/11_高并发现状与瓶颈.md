# 第一部分 现状事实

## 一、并发模型实测

每个执行域的**真实并发原语**（非推测）：

| 执行域 | 并发原语 | 并发度 | 证据 |
|---|---|---|---|
| **Agent 循环**（单请求内） | 串行 for 循环 | 1（一轮一轮来） | `agent_service.py:335` |
| **Agent 请求间** | 无限制（uvicorn worker 内协程） | 受 worker 数与事件循环限制 | `agent_service.py` |
| **工具分发** | **同步** `dispatch()` | 串行（一个 tool_call 跑完再下一个） | `tool_registry.py:198-253` |
| **MCP 调用** | **每次调用新建 stdio 子进程** | 无池化，进程拉起开销 ~百 ms 级 | `mcp_manager.py:145-168` |
| **内置工具执行** | `subprocess.run`（阻塞） | 占用调用线程 | `code_executor.py:16-160` |
| **Research 任务层** | `ThreadPoolExecutor` | 3（`research_max_concurrent`） | `core/config.py:70` |
| **Research 任务内** | `ThreadPoolExecutor` | ≤ 6（`AGENT_CONFIG.max_workers`） | `orchestrator.py:263-315` |
| **Web 爬虫** | 每 URL 一个原生 `threading.Thread` | 无上限（由 Serper 返回数决定） | `web/fetch_web_content.py` |
| **调度并发** | `BoundedSemaphore(2)` | 2（`schedule_max_concurrent`） | `run_executor.py:43` |
| **交互式 SSE** | **占信号量**（S4 起与调度共用预算） | `schedule_max_concurrent`（默认 2），超限返回 `busy` 事件 | `run_executor.py`（`acquire_slot=True`） |
| **SQLite 写** | WAL + 单写者 | 写互斥，靠 `retry_on_locked` + `busy_timeout=5000` | `db/base.py:43-125` |
| **Milvus Lite** | 单文件库 | 文件锁 | `rag/milvus_store.py` |
| **SSE 连接** | 每连接一个生成器 | 无连接数指标/上限 | `api/v1/{agent,runs,research}.py` |

## 二、瓶颈识别

### 2.1 六个瓶颈（按严重度排序）

| # | 瓶颈 | 根因 | 后果 |
|---|---|---|---|
| **B1** | **SQLite 单写者** | WAL 下写仍互斥；事件账本高频写（批量 20 条/2 s）+ 会话写 + 调度写集中在同一库 | 高并发下 `SQLITE_BUSY`，写延迟抖动；极端时 `retry_on_locked` 耗尽 |
| **B2** | **MCP 每次调用新建子进程** | `stdio_client` 每次 `python <server>.py` 拉起解释器 + FastMCP 初始化 | 每次 MCP 工具调用固定付出 ~百 ms 级进程开销；高频调用时延迟显著 |
| **B3** | **LLM 调用非流式** | `chat.completions.create()` 不带 `stream=True`，完整响应后才产 `model_text` | 首 token 延迟 = 完整响应时间；用户长时间无反馈 |
| **B4** | ~~交互式 SSE 无并发护栏~~ **已修**（S4 WP-4.4） | `execute_stream` 现占用 `BoundedSemaphore`（`acquire_slot=True`） | 交互与调度共享同一预算，超限返 `busy` 事件 |
| **B5** | **调度执行阻塞调度线程** | `BackgroundScheduler` 线程里调 `execute_sync` → 内部 `subprocess.run` 阻塞 | 长任务占用调度线程，后续触发被延迟 |
| **B6** | **Milvus Lite 单文件** | 文件锁 + 单机 | 多副本部署时多个后端写同一 `milvus.db` 会冲突；写并发受限 |

### 2.2 各瓶颈的量化参考

| 瓶颈 | 量级估算（基于参数，非压测） |
|---|---|
| B1 SQLite | `busy_timeout=5000` + 退避 50/100/200ms ×3 → 单次写最坏 ~5.35 s；事件写 20 条/批 → 单次事务 |
| B2 MCP | 每次调用一次 Python 启动（~50-200ms）+ FastMCP 初始化；10 次连续调用 ≈ 1~2 s 纯开销 |
| B3 LLM | 非流式 → 首 token 延迟 = 完整响应（长答案数秒~数十秒） |
| B5 调度线程 | `execute_sync` 最坏 `max_iterations=20` 轮 × 每轮 LLM+工具，单次任务可跑数分钟 |

# 第二部分 分级改造方案

> **全部为「未实现（参考设计）」**，按优先级排列。

## P0：正确性优先

### 3.1 SQLite 写锁加固（未实现，见 `../plan/03`）

| 措施 | 说明 |
|---|---|
| `retry_on_locked` 与 `busy_timeout` 协调 | 当前 `busy_timeout=5000` 已兜底多数情况；把 `append_events` 的重试次数与 `append_message`（20 次）对齐 |
| 事件写合并 | 已做（批量 20 条/2s）；可进一步把「同一 run 的连续事件」在事务内合并为更少事务 |
| 读写分离评估 | SQLite 无真正读写分离；若并发写压力大，评估 `DATABASE_URL` 切 PostgreSQL |

### 3.2 交互式 SSE 并发护栏 ✅ 已落地（S4）

**已实现**：交互路径与调度**共用** `schedule_max_concurrent`，超限时返回 `busy` 事件（不静默丢弃）；`execute_sync` 自行持槽并传 `acquire_slot=False`，避免预算折半。

## P1：延迟优化

### 3.3 LLM 调用改流式（未实现，见 `../plan/04`）

`chat.completions.create(stream=True)`，增量产出 `model_text`。收益：首 token 延迟从「完整响应时间」降为「网络 RTT + 首个 token」。

### 3.4 MCP stdio 连接池化 ✅ 已落地（S7）

为每个 Server 维护一个**长驻 stdio 子进程池**（如每 Server 2 个连接轮换），替代「每次调用新建」。需注意跨事件循环持有 `ClientSession` 的坑（这正是当初选「每次新建」的原因——池化需在同一事件循环内复用）。

## P2：结构升级

### 3.5 Milvus Lite → Standalone（未实现，见 `../plan/06`）

`deploy/docker-compose.milvus.yml` 已提供叠加文件。切换后：`MILVUS_DB_PATH` 指向服务地址，解除单文件锁，支持多副本读。

### 3.6 uvloop + 多 worker（未实现，见 `../plan/06`）

```bash
uvicorn app.main:app --workers 4 --loop uvloop
```

**硬约束**：多 worker = 多进程 = 多副本。必须先满足：
1. 调度租约（已具备，`system_locks`）；
2. Milvus Standalone（否则多进程写同一 `milvus.db` 冲突）；
3. SQLite 换 PostgreSQL 或接受多副本各写各的（数据分裂）。

**不建议在当前单文件存储下开多 worker。**

## P3：容量参考（建议先测再调）

以现有 **325 个 pytest** 与 **91 个端点**为基线，建议补的可测量指标：

| 指标 | 测量方式 |
|---|---|
| 首 token 延迟 | `agent/run` 从请求到首个 `model_text` 的时间 |
| tool_call P95 | 各工具执行的 95 分位耗时 |
| 并发写 QPS | 并发 `append_events` 的吞吐与 `SQLITE_BUSY` 率 |
| SSE 并发连接数 | 当前活跃 SSE 连接数 |
| 调度触发延迟 | 计划触发时间 vs 实际 `started_at` 的差 |

# 第三部分 已知边界与观察

| 编号 | 观察 | 证据 |
|---|---|---|
| S-11-01 | 所有线程池（Research ×2 层、调度信号量）都是**进程内**的，无跨进程协调；多副本时各副本独立计数 | `backend/app/services/research/`；`run_executor.py` |
| S-11-02 | Web 爬虫用原生 `threading.Thread` 且无并发上限，URL 数由外部 API 决定，极端查询会拉起大量线程 | `backend/app/services/web/fetch_web_content.py` |
| S-11-03 | `list_tools_with_schema()` 不走缓存，Agent 每轮构造工具定义都重新 `import` + 反射 MCP Server 模块 | `backend/app/services/mcp_manager.py:120-140` |
| S-11-04 | `_stream_loop` 的 `messages` 无长度上限，仅受 `max_iterations=20` 约束；每轮工具结果最多 8000 字符，最坏上下文数十万 token | `backend/app/services/agent_service.py:335-419` |
| S-11-05 | SSE 无心跳机制，长时间无事件的连接依赖 Nginx `proxy_read_timeout=3600s` 保活，中间代理可能提前断开 | `deploy/nginx/conf.d/agent.conf:37` |
| S-11-06 | `tasks.json`（Deep Research）全量读写，任务数增长后每次 `_save_tasks()` 都是 O(n) 写 | `backend/app/services/research/research_manager.py:63` |
| S-11-07 | 调度线程阻塞（B5）在高频短任务下不明显，但在 plan_first 长任务下会让其它任务的触发被延迟 | `backend/app/services/run_executor.py:275-319` |
