# 第一部分 现状事实

## 一、日志（`shared/logger.ts`）

- **结构化 JSON 行**：`{ts, level, logger, message, request_id?, ...extra}`；
- 级别 DEBUG/INFO/WARNING/ERROR；**DEBUG 按 logger 维度采样**（`log_debug_sample_rate=0.2`，
  同一 logger 采样决策缓存一致）；
- **文件轮转**：`userData/logs/app.log`，10MB × 5 份（`log_file_max_bytes` /
  `log_file_backup_count`）；
- **请求 ID 串联**：`X-Request-ID` 经 `AsyncLocalStorage` 贯通（`shared/errors.ts:16`），
  错误体与响应头都带它；
- 桌面壳另有 `userData/logs/backend.log`：sidecar 的 stdout/stderr 流水与
  壳侧编排事件（启动/重启/孤儿回收/唤醒），`apps/desktop/src/main/index.ts:184`。

## 二、健康与指标端点

### `GET /api/v1/health`（`routes/system.ts:26`）

`status / version / skills_loaded / api_key_configured / llm_available /
web_search_available / research_*（5 字段）/ rag_collection / rag_entities /
mcp_servers_available / output_dir / database / scheduler{...} / desktop_mode` —
前端「系统状态」页逐字段消费。

### `GET /api/v1/metrics`（`routes/system.ts:72`）

- `concurrency{running, limit}`、`success_rate`（含/不含 skipped 两个口径）、
  `runs_24h`（`runs_today` 为兼容别名）、`terminal_runs_24h`、
  `duration_ms{samples, p50, p90}`（下标法取分位，非插值）；
- `llm{provider, model}`、`mcp_connections`；
- 扩展：`counts`（22 表逐表行数）、`uptime_seconds`、`memory_bytes`(RSS)、`node_version`。

### 成本观测

- `llm_calls` 逐次计量（模型/tokens/延迟/单价快照/成本）；
- `GET /runs/{id}/cost`（单 run 聚合）、`GET /cost/estimate`（历史 p50~p90 区间 +
  单价表）、`GET /cost/estimate/tokens`（预估）；详见 `16` §4。

## 三、事件与账本（运行期可观测性的主干）

- `runs` + `run_events`：每次运行的完整事件流（26 种事件类型，C15）落账，
  可分页回放、可 SSE tail（`08` §5）；
- 前端 RunTimeline / RoundGroup 直接消费事件流——**UI 的时间线就是观测界面**；
- 权限审批留痕：`permission_decisions` 表（含 latency_ms、decided_by）+
  桌面事件总线的 `permission_requested/permission_resolved` 事件。

## 四、桌面事件总线（`http/events.ts`）

- 进程内环形缓冲（最近 **200** 条，`MAX_EVENTS`），单调递增 `id`；
- `GET /desktop/events`：SSE 外发，`after_id` 补发断连期间事件，`max_events` 有界模式；
- 事件来源：工作区切换、调度补跑、权限审批等（`bus.publish(...)`）；
- 壳订阅后桥接到渲染进程（`agent:backend-event` IPC），驱动通知与状态 UI。

## 五、当前缺什么（事实陈述，方案在 `../design/09` 附录）

| 维度 | 现状 |
|---|---|
| 指标导出 | 无 Prometheus/OTel exporter，只有 `/metrics` 拉取式快照 |
| 分布式追踪 | 无（单机单进程，request_id 已贯通日志与错误体） |
| LLM 追踪 | 无 Langfuse 类接入；`llm_calls` 表承担计量（无 prompt 内容留痕） |
| 告警 | 无主动告警通道；桌面端靠系统通知（`notifications.ts`） |
| 审计导出 | `permission_decisions` 在库内，无独立审计日志文件 |

# 第二部分 原理剖析

## 六、为什么观测主干是「事件账本」而不是「指标管道」

Agent 系统的关键问题是「**这次运行为什么是这个结果**」——指标回答不了，
只有逐步事件（哪轮调了什么工具、模型回了什么、谁批准了写文件）能回答。
把事件当**一等账本**（SQLite 有序表 + seq 游标）而不是 fire-and-forget 日志，
换来的是：UI 时间线、断线续传、事后审计、E2E 断言共用同一份数据。

## 七、为什么 DEBUG 日志要按 logger 采样而不是全局开关

桌面端日志写用户磁盘，DEBUG 全开会放大 IO 且冲淡关键信息；
按 logger 维度做 0.2 采样（且决策缓存），既保留代表性样本用于排错，
又把体积锁住。需要完整 DEBUG 时把 `log_debug_sample_rate` 调 1 即可。
