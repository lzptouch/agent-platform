# 第一部分 现状事实

## 一、定位

两层问题：①上下文窗口是稀缺资源（怎么省）；②LLM 调用是真金白银（怎么算）。

## 二、上下文预算

### 2.1 历史回放裁剪（✅ 生效）

`sessionService.buildHistory()`（`session/service.ts:342`）：

- 只回放 `user` / 最终 `assistant` 文本（tool 消息与 `meta.tool_only` 过滤）；
- 双预算：`session_history_limit=10` 条 + `session_history_max_chars=8000` 字符，
  从旧到新裁剪；**保证首条是 user**（OpenAI 兼容要求）；
- `GET /sessions/{id}/context` 返回回放预览 + `estimated_tokens` +
  `budget_ratio`（0.85）。

### 2.2 事件侧截断（✅ 生效）

`tool_call` 入参截 4000 字符、`tool_result` 结果截 2000 字符（`03` §九）；
`run_events.payload_json` 落库截 60000 字符。

### 2.3 压缩/摘要（⬜ 配置与契约保留，未执行）

`context_compact_threshold=0.7` / `context_summary_threshold=0.85` /
`context_keep_recent_turns=3` / `context_budget_ratio=0.85` 均为配置位；
契约事件 `context_compressed` / `context_trimmed` 保留——**当前循环无发射点**
（`03` §5.4），无压缩执行代码。

### 2.4 工具延迟装载（⬜ 同上）

`LazyToolLoader` 与 `tool_search`/`tool_load` 引导工具存在（`tools/registry.ts:303`），
但执行器未把 loader 挂进运行上下文（`03` §三）——当前每次调用都带全量
合并后的工具 Schema。

## 三、记忆

### 3.1 三层作用域（管理面 ✅ 生效）

`user / workspace / project` 三作用域，各对应 `userData/memory/<scope>/*.md`；
`GET/POST/DELETE /memories`、`POST /memories/clear`；写入时同步 `memory_index`
表（path/scope/summary/size），删除仅限三作用域目录内（403）。

### 3.2 注入（⬜ 未接线）

`context_memory_enabled` / `context_memory_max=5` 只被 `/memories` 的响应形状
消费；Agent 循环**不读记忆文件**（system prompt 组装无记忆块）；
契约事件 `memory_item` 无发射点。

## 四、成本核算（✅ 完整生效）

### 4.1 计量（`exec/accounting.ts`）

每次 LLM 调用 `recordCall()` 落一行 `llm_calls`：
`run_id, session_id, model, provider, role, prompt_tokens, completion_tokens,
cached_tokens, latency_ms, price_snapshot, cost`。
usage 缺失时用 `estimateTokens()` 兜底（`exec/tokens.ts`：英文 4 字符≈1 token，
CJK 1.5 字符≈1 token，每条消息 +4 角色开销）。计量失败只告警不阻断主流程。

### 4.2 计价（`accounting/pricing.ts`）

- 单价表：7 个模型（qwen-plus/max/turbo、deepseek-chat/reasoner、gpt-4o/4o-mini）
  + 兜底价；`pricing_json` 配置可覆盖；
- **单价快照**：调用时把当时单价写进 `price_snapshot`——**改价不影响历史金额**；
- 公式：`(prompt-cached)/1000×入价 + cached/1000×缓存价 + completion/1000×出价`，
  保留 8 位小数。

### 4.3 聚合与查询

- run 收尾时 `aggregateRun()` 聚合回写 `runs` 行（`04` §2.2）；
- `GET /runs/{id}/cost`：单 run 明细 + 单价表；
- `GET /cost/estimate`：最近 200 条（`limit*4`）`llm_calls.cost` 的
  **p50/p90**（中位数/下标法 90% 分位）+ 全量单价表——前端 RunCostBar
  据此显示「本次 vs 历史区间」；
- `GET /cost/estimate/tokens`：按 token 数预估单次成本（扩展端点）。

## 五、前端消费

`ContextMeter`（上下文占用比）、`RunCostBar`（实际 + 区间）、
`SettingsView`（单价表）、`SystemStatusView`（健康字段）。

# 第二部分 原理剖析

## 六、为什么历史裁剪用「条数 + 字符」双预算

条数限制防「碎轮次堆积」，字符限制防「单轮超长」。两者从旧到新裁剪
（新的对话更相关），且强制首条为 user——这是 OpenAI 兼容接口的配对要求，
不是可选项（见 `03` §八）。

## 七、为什么 token 估算不用 tiktoken

桌面安装包要零外部模型依赖；tiktoken 的词表按模型而异，而本平台
**多提供方**（DashScope/DeepSeek/OpenAI 兼容）。「英文 4 字符、中文 1.5 字符」
的启发式误差可接受——它只用于 usage 缺失时的兜底与前端预览，
真实计量以 provider 返回的 `usage` 为准。

## 八、为什么成本要「单价快照」而不是「实时查价目表」

历史金额必须** immutable**：改价后回看旧 run，金额不该变。
快照把计价从「查询时函数」变成「写入时事实」，审计与对账才可重复。
（改价只影响新调用——这正是财务系统的通用做法。）

## 九、为什么记忆是「文件系统 + DB 索引」而不是纯 DB

记忆内容（md）是用户可直接编辑/版本管理的文件；索引（摘要/大小/作用域）
服务列表页查询。与 Skill 的「文件为真、DB 为索」同构（`02` §七）。
注入侧未接线是当前边界，不是设计缺失（`03` 的循环需要决定
「何时注入、注入哪几条」的检索策略，属 `../design/09` 附录（批次）范畴）。

## 十、为什么成本聚合到 `runs` 行而不是每次查 `llm_calls`

列表页/详情页高频读，聚合值随 `finish()` 一次性物化（写一次，读 N 次）；
`llm_calls` 保留逐次明细供下钻。物化通过 `registerUsageProvider` 注入完成，
避免 accounting ↔ run 的循环依赖（`http/context.ts:58`）。

# 第三部分 已知边界

1. 压缩/摘要/记忆注入/工具延迟装载：配置位与契约事件保留，执行未接线（§2.3/§3.2/§2.4）；
2. token 估算是启发式（§七）；
3. 无 token 硬预算（只有观测，没有熔断）。
