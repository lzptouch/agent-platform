# 第一部分 现状事实

## 一、定位

本域回答 Agent 平台里最实际的两个问题：

| 问题 | 答案 | 实现 |
|---|---|---|
| **「这次对话塞了多少东西进模型？」** | 上下文预算 + 两级压缩 + 三层记忆 | `services/exec/context.py`、`exec/memory.py` |
| **「这次运行花了多少钱？」** | LLM 计量 + 单价快照 + 成本聚合 | `services/exec/accounting.py`、`core/pricing.py` |

两者都挂在 Agent 主循环的两个点上：

```
每轮组装 messages 前 → ContextBudget.usage() → 超阈值则 compress / trim
每次 LLM 响应后     → response.usage → record_call() → llm_calls 表
```

### 2.2 预算计算

`ContextBudget.for_model(model, ratio)`（`exec/context.py:62-65`）：

- `window = MODEL_CONTEXT_WINDOWS.get(model, 32_000)`（表 `:18-26`，7 个模型）
- `token_limit = window * ratio`；`char_limit = min(400_000, window * ratio * 4)`
- `usage()`（`:75-84`）返回 `{tokens, chars, ratio, token_limit, char_limit}`；`ratio = tokens / window`

**token 估算**：`estimate_tokens()`（`:40-46`）——中文 `cjk/1.5` + 其它 `other/4`，**无 tiktoken 依赖**；真实 token 由 `llm_calls` 表事后校正（`agent_service.py:370-373` 取 `response.usage`）。

# 第二部分 原理剖析

## 六、为什么要两级压缩而不是一级

单一「超阈值就摘要」的策略有两个问题：

1. **抖动**：token 在阈值附近波动时，会反复触发摘要，每次都损失信息；
2. **浪费**：轻微超限就丢掉全部工具结果明细，代价过高。

两级设计把「超一点」和「超很多」分开处理：

| 级别 | 代价 | 适用 |
|---|---|---|
| **裁剪**（0.70） | 低——只丢最旧的工具结果，保留全部用户/助手文本 | 轻微超限 |
| **摘要**（0.85） | 高——丢掉全部历史细节，换成一段摘要 | 严重超限 |

裁剪的**价值分排序**是关键：它不是简单地按时间丢，而是**优先丢低价值内容**（普通工具结果）而保留高价值内容（报错、Traceback、`_important` 标记）。

## 七、为什么 token 估算不用 tiktoken

| 维度 | 自研估算（当前） | tiktoken |
|---|---|---|
| 依赖 | 零 | 需装包，且要维护各模型的编码表 |
| 精度 | 中文 `cjk/1.5` + 其它 `other/4`，**误差约 ±20%** | 精确 |
| 维护 | 无 | 模型更新时要更新编码表 |
| 离线可用 | ✅ | ✅ |

自研估算的误差对「阈值判定」这个用途是够的——因为阈值本身就是**相对量**（占窗口的 70% / 85%），而不是绝对 token 数。且真实 token 由 `llm_calls` 表事后校正，两者可以互相校准。

## 八、为什么成本要「快照单价」而不是「实时查价目表」

若成本按**当前价目表**回算，改价会让历史账目全部失真——无法回答「上个月到底花了多少」。

`price_snapshot` 把单价固化到每一行 `llm_calls` 上，使得：

- 历史成本**不可变**；
- 改价只影响**新**调用；
- 审计与对账有确定依据。

代价是价目表本身没有版本管理——无法回答「这个价是什么时候改的」。

## 九、为什么记忆是「文件系统 + DB 索引」而不是纯 DB

| 需求 | 文件系统 | DB |
|---|---|---|
| 存长文本记忆（可能几百字） | ✅ 自然 | 可但别扭 |
| 人可读 / 可手改 | ✅ | ❌ |
| 增量索引与预筛 | ❌ 需旁路 | ✅ `memory_index` 表 |

所以记忆**正文在文件**（`*.md` + frontmatter tags），**索引在 DB**（`memory_index` 表）。预筛打分在 DB 侧完成，只把命中条目的摘要注入上下文——避免把全部记忆塞进 prompt。

## 十、为什么成本聚合到 `runs` 行而不是每次都查 `llm_calls`

`llm_calls` 是**明细表**，一次运行可能有几十到上百行。前端每次渲染成本条都去聚合明细表会产生不必要的查询。

在 `run_service.finish()` 时把聚合结果**冗余写入 `runs` 行**（`prompt_tokens` / `completion_tokens` / `llm_calls` / `estimated_cost`），让「看一次运行花了多少」变成 O(1) 读取。代价是冗余数据需要保证一致（当前由 `finish()` 单点写入保证）。
