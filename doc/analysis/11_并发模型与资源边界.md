# 并发模型与资源边界

> **依据代码**：`apps/server/src/domain/run/executor.ts`、`db/client.ts`、`workers/sandbox.ts`、`http/routes/{runs,research,desktop}.ts`、`shared/config.ts`（2026-11-01 复核）
>
> 本篇只描述**当前代码的**并发模型与资源边界（原「改造方案」内容属计划，已移至 `../design/09` 附录，原 `doc/plan/`）。

# 第一部分 现状事实

## 一、进程模型

- **单 Node 进程**承载全部 HTTP + Agent 循环 + 调度器（桌面态为 Electron
  `utilityProcess`，与主进程崩溃隔离）；
- Node 事件循环：LLM 调用、SSE 写出是异步 IO，**可并发**；
  better-sqlite3 是**同步 API**——DB 读写会短暂阻塞事件循环（毫秒级，单机可接受）；
- 子进程边界：代码执行（bash/Python/Node 脚本）与外部 MCP Server 是独立子进程。

## 二、槽位信号量（`run/executor.ts:31-76`）

| 槽池 | 上限 | 排队超时 | 溢出行为 |
|---|---|---|---|
| 交互槽（`trigger != 'schedule'`） | **4**（`interactive_max_concurrent`） | 30s | 发 `busy{limit}` 事件 + `done{failed}` |
| 调度槽（`trigger == 'schedule'`） | **2**（`schedule_max_concurrent`） | 30s | 同上 |

- 两个信号量**独立**：调度长任务不占交互槽；
- `Semaphore` 实现：计数 + FIFO 等待队列 + 定时器超时（超时返回 false）；
- `finally` 中 `release()`——异常路径不泄槽。

## 三、SQLite 单写者模型（`db/client.ts`）

- WAL 模式：读不阻塞写、写不阻塞读；**写-写互斥**；
- `busy_timeout=5000`（连接级等待）+ 显式退避重试 50/100/200ms
  （`withWriteRetry`，吸收 `SQLITE_BUSY/SQLITE_LOCKED`）；
- 事务即重试单元：`transaction(fn)`；
- 调度器 tick、Agent 事件落账、权限决策写库都走这一套——实测无死锁
  （写者只有一个连接，重试只发生在与 WAL 检查点/外部写冲突时）。

## 四、SSE 长连接

| 端点 | 轮询间隔 | 上限 | 备注 |
|---|---|---|---|
| `runs/{id}/stream` | 300ms（DB tail） | 3600s | `max_events` 有界模式可测 |
| `research/{id}/stream` | 500ms + 心跳 | 3600s | 监听器直推 + 状态轮询兜底 |
| `desktop/events` | 300ms | 3600s | 环形缓冲 200 条 |
| `agent/run`（POST） | 事件驱动直出 | 随 run 结束 | 无读超时（前端 `timeoutMs=0`） |

连接断开由 `channel.closed` 感知，循环退出；服务端无连接数配额
（单机形态，渲染进程一个）。

## 五、子进程执行边界（`workers/sandbox.ts`）

| 边界 | 值 | 实现 |
|---|---|---|
| 墙钟超时 | 180s（`exec_timeout`） | 定时器 → 杀进程组 |
| CPU | 60s | POSIX `ulimit -t`（`/bin/sh -c 'ulimit ... && exec ...'`） |
| 内存 | 1GB | `ulimit -v`（KB） |
| 句柄 | 256 | `ulimit -n` |
| 单文件 | 64MB | `ulimit -f`（512B 块） |
| 输出 | 64KB/通道 | 超出**立即杀**（`limitHit=max_output_bytes`） |
| 命令黑名单 | 5 条（`rm -rf /`、`mkfs`、`dd if=`、`:(){`、`shutdown`） | 启动前拦截 + 审计日志 |
| 写路径 | cwd（run 绑定工作区）+ outputs | `checkPathAllowed`（桌面态写必查） |

- 进程组管理：POSIX `detached:true` → `process.kill(-pid)` 整组 SIGKILL；
  Windows 兜底 `taskkill /T /F`（无 rlimit 等价物，限额在 Windows 不生效——诚实标注）；
- Python 轨道可选（`detectPython()` 三级探测：环境变量 → userData runtime → 系统
  python3）；Node 轨道（`process.execPath`）永远可用。

## 六、上传与请求体

- `bodyLimit = 100MB`（`upload_max_request_bytes`）；multipart 单文件 50MB
  （`upload_max_file_bytes`，超限落盘后删除并 413）；
- 扩展名白名单（`files.ts:16`，可用 `UPLOAD_ALLOWED_EXTENSIONS` 覆盖）。

## 七、调度并发

- 调度槽 2（§二）之外，调度器本身是**单进程内定时器集合**；
  多副本防重靠 `system_locks` 租约（`08` §三）；
- 定时任务日配额（默认 100/任务/本地日）防失控。

# 第二部分 现状评估（事实）

| 维度 | 结论 |
|---|---|
| 交互并发上限 | 4 个 run + N 个 SSE 观察者；超出报 `busy`（语义明确） |
| 已知阻塞点 | better-sqlite3 同步写在大批量事件落账时阻塞事件循环（已由批量事务缓解） |
| 内存 | RAG 向量全量载内存（`rag/store.ts:212`）——chunk 数 × 4KB（1024 维 float32）线性增长 |
| 任务持久化 | `tasks.json` 全量读写（`07` §八） |
| 单机定位 | 无集群/多副本设计；租约只为崩溃回收与防双开 |
