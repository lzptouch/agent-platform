### 1.2 五个根因（189 条缺陷收敛到 5 类系统性病因）

> **这是本次审计最重要的产出**：绝大多数条目不是「写错了」，而是**同一个机制缺陷在 20+ 处重复显形**。修根因比逐条打补丁便宜一个数量级。

#### 根因 ① —— **同步生成器 + `contextvars` 的跨线程丢失**（引发 6 条严重 / 13 条中危）

Starlette 对**同步**迭代器走 `iterate_in_threadpool` → `anyio.to_thread.run_sync(_next, iterator)`。anyio 的 `run_sync_in_worker_thread`（`_backends/_asyncio.py:2698`）在**事件循环线程**里做 `context = copy_context()`，再把 `context` 交给 worker 线程执行 `context.run(func, *args)`（`:1100`）。

**后果**：生成器体内 `contextvar.set()` 写入的是**本次调用的临时 Context 副本**，该副本在 `next()` 返回后即被丢弃；下一次 `next()` 是一次**全新的** `copy_context()` → **上一次 set 的值全部消失**。

`backend/app/api/v1/agent.py:47` 把 `executor.execute_stream(...)`（同步生成器）直接塞进 `StreamingResponse`，`backend/app/services/run_executor.py:300` 在生成器体内 `current_run_context.set(ws_ctx)` —— **正好踩中**。

**可执行复现**（`/tmp/repro_ctxvar.py`，用仓库自己的 venv 与 starlette/anyio 版本）：

```python
def gen():
    ctx.set({"run_id": "R1"})
    yield "first"
    yield f"second sees={ctx.get()}"   # ← LookupError: <ContextVar name='ctx'>
```
输出：
```
LookupError: <ContextVar name='ctx' at 0x1055126b0>
```
（真实代码里 `current_run_context` 的 `default=None`，所以是**静默拿到 None**，比抛异常更危险。）

**波及的能力（全部声称已交付，实则失效）**：

| 受影响能力 | 读取点 | 实际行为 |
| --- | --- | --- |
| 产物登记 `emit_artifact` | `tool_registry.py:516` | `ctx=None` → 恒返回 `{"error": "当前无运行上下文，无法登记产物"}` → **`artifacts` 表在生产 SSE 路径恒空** |
| 写盘工作目录 | `code_executor.py:107` | 回落**全局**工作区 → 与 run 绑定的 `wb-{日期}-{id}` **不一致** |
| 变更账本 + 写前快照 | `code_executor.py:395/400` | `if ctx:` 不成立 → **快照与 `record_change` 全部跳过** → 变更表恒空 |
| 权限审计 run 归属 | `agent_service.py:141` | `run_id=None` → 审计行 `run_id` 恒空 |
| 工具延迟装载 `tool_load` | `tool_registry.py:585` | `loader=None` → **回写被跳过** → `tool_load` 只返回说明，实际不装载 |
| 每轮重算工具集 | `agent_service.py:651` | `_loader=None` → 不再重算 `openai_tools` → 延迟装载**只生效一轮** |

#### 根因 ② —— **「单元测试通过」被当成了「生产路径生效」**（引发 22 条「声明与实现不符」）

`design/01` 判定 ✅ 的口径写的是「代码有生效逻辑 **且** 有测试覆盖 **且** 有阶段执行记录」。但这三条都成立时，仍可能出现「**测试走的是同步调用路径，生产走的是 SSE 路径**」——测试直接调 `agent_service.stream()`（同线程，contextvar 有效），生产走 `StreamingResponse`（跨线程，contextvar 失效）。

**本次审计发现 22 条 `design/01` 标 ✅ 的需求在生产路径实际不成立**（§6）。它们有一个共同特征：**交付时的验证用例没有覆盖真实调用链**。

#### 根因 ③ —— **参数在调用链上被静默丢弃**（引发 9 条中危）

`run_id`/`session_id`（成本归属）、`role_id`/`debug_prompt`（角色/调试）、`workspace_id`（权限作用域）、`count`/`freshness`（搜索参数）、`risk`（风险等级）、`round`/`limit`（事件条数）、`env`（MCP 环境变量）——**签名里有、调用点不传**，下游默默用默认值。

**特征**：不报错、不告警，**结果静默错误**。其中 `MCPEndpoint(env=...)` 因 dataclass 无该字段 → **直接 TypeError**（见 `AUD-C04`）。

#### 根因 ④ —— **路径边界用字符串前缀而非 `is_relative_to`**（引发 6 条高危 + 4 条严重）

`str(target).startswith(str(base))` 在 sibling 目录场景下**恒为真**：

| 位置 | base | 逃逸目标 | 结果 |
| --- | --- | --- | --- |
| `skill_manager.py:225` | `<root>/skills/foo` | `<root>/skills/foo-evil/x` | ✅ 放行 |
| `skill_manager.py:225` | `<root>/skills/foo` | `<root>/skills/foo_evil/secret.md` | ✅ 放行 |
| `workspace.py:170` | `<workspace>` | `/etc/passwd`（绝对路径） | ✅ 放行 |
| `memory.py:176` | — | **无任何边界校验** | ✅ 任意删除 |
| `context.py:98` | — | **无任何边界校验** | ✅ 任意写入 |
| `plugins.py:156` | `<plugins_dir>` | `../../../../tmp/evil` | ✅ 越界写 |

#### 根因 ⑤ —— **状态机缺终态守卫 / 幂等键被非执行记录占用**（引发 7 条高危）

`runs` 表有乐观锁 `version_id`（`db/models.py:202`），但 `finish()` **不检查当前状态**（`run_service.py:214`）→ 迟到的 `finish(success)` 覆盖 `interrupt_run()` 写的 `interrupted`。同时 `create_run` 的唯一键 `uq_runs_task_slot(task_id, scheduled_for)` 被**「退避中」「超配额」这类 skipped 记录占用**（`scheduler_service.py:571`）→ 该槽位**永久无法补跑**。

### 1.3 一句话结论

> **主干链路（FastAPI + Vue + SQLite + Alembic + 5 能力链）架构清晰、分层合理、测试基线健康（626+101 全绿）；但生产路径上存在 11 条严重缺陷，其中 6 条由「同步生成器跨线程丢 contextvar」这一个机制引发，导致「产物登记 / 变更追踪 / 成本统计 / 延迟装载 / 工作区绑定 / 权限审计」六项已声明交付的能力在 SSE 主路径上完全失效。**
>
> **同时，`design/01` 的 94/95 条 ✅ 存在 22 条虚高**（§6）——根因是验收用例未覆盖真实调用链，而非实现本身错误。**修复代码的同时必须同步订正文档状态列**，否则下一轮复核会重复踩同一个坑。

### AUD-C01 · 同步生成器跨线程丢失 `current_run_context` —— 6 项已交付能力在生产路径失效

- **位置**：`backend/app/services/run_executor.py:300`（`current_run_context.set(ws_ctx)`）
- **触发链**：`api/v1/agent.py:47` → `StreamingResponse(event_stream())` → `starlette/concurrency.py:57` → `anyio/to_thread.py:65` → `anyio/_backends/_asyncio.py:2698`（`copy_context()`）→ `:1100`（`context.run(func, *args)`）
- **机制**：见 §1.2 根因 ①。每次 `next()` 都在**新 Context 副本**中执行，生成器体内的 `set()` 随副本一起丢弃。
- **复现**：`/tmp/repro_ctxvar.py` → `LookupError: <ContextVar name='ctx'>`（真实代码 `default=None` → 静默 None）
- **影响**（全部为 `design/01` 声称已交付的能力）：

  | 能力 | 失效表现 | 文档声称 |
  | --- | --- | --- |
  | 产物登记 `F-WS-08` | `artifacts` 表**恒空**，产物列表恒空 | P2-12 已交付「生产路径不再恒空」 |
  | 一任务一工作空间 `F-WS-02/03` | 写盘 cwd 与 run 绑定目录**不一致** | P2-18/P2-19 已交付「运行期锁死」 |
  | 变更追踪 `F-WS-05/07` | `changes` 表**恒空**，无法 diff / 回退 | P2-18 已交付 |
  | 延迟装载 `F-CTX-01` | `tool_load` 只返回说明，**实际不装载** | P2-02 已交付「真正生效」 |
  | 成本计量 `F-CTX-09/10` | `runs.prompt_tokens` 等**恒 NULL/0** | 已交付 |
  | 权限审计 `F-SEC-07/14` | 审计行 `run_id` **恒空**，无法按 run 还原 | 已交付 |

- **根因**：把「跨请求隔离的可变状态」放在 `contextvars` 上，却把它**写在一个会被 Starlette 跨线程消费的同步生成器里**。

### AUD-C11 · RAG collection 被重建后台账未清 —— 增量入库全部被跳过，库是空的

- **位置**：`backend/app/services/rag/ingest.py:54-74` + `backend/app/services/rag/milvus_store.py:49-57`
- **证据**：
  ```python

  ...
  ```

## 九、审计结论与后续

1. **架构层面无需重构**。分层（api / services / core / db / schemas）、依赖方向、事务边界、路由组织均合理，本篇未发现需要推倒重来的问题。
