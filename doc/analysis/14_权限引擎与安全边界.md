# 第一部分 现状事实

## 一、定位与入口

权限引擎横切在**工具分发之前**：任何写类工具要真正执行，都必须先过 `ToolRegistry.dispatch()` 的权限判定。

```
工具调用
  → ToolRegistry.dispatch()                 ← 唯一判定落点
    → _check_permission()                   ← 归一化请求 + 三态判定
      → PermissionService.enforce()
        → decide(request, rules)            ← 纯函数
        ├─ allow → 直接返回
        ├─ deny  → 直接返回
        └─ ask   → 有人审批？阻塞等待（120s）→ 无人？立即 deny
    → 写 permission_decisions 表（pending → resolved）
    → 写 .agent/audit/audit.jsonl
```

**HTTP 层直接触发权限判定的端点只有一处**：`POST /api/v1/changes/{change_id}/revert`（`api/v1/workspace.py:102-112`）。

# 第二部分 原理剖析

## 七、为什么权限判定放在「工具分发」而不是「HTTP 层」

三种可选的落点：

| 落点 | 问题 |
|---|---|
| HTTP 层中间件 | 拿不到「工具名 + 入参」，无法判定 file/command/network 维度 |
| HTTP 层逐端点 | 118 个端点要写 118 遍判定，且**新增端点必然漏判** |
| **工具分发入口**（本项目） | 所有写操作必经此点；新增工具自动纳入判定 |

因此 API 层只有一处直接调引擎（`revert`），其余全部通过 `ToolRegistry.dispatch()` 间接覆盖。这是**「一个不可绕过的收敛点」**的设计。

## 八、为什么规则用「三态」而不是「布尔允许」

布尔允许无法表达「**这一类要人确认**」。三态（`deny` / `ask` / `allow`）把「策略强度」变成一维序：

```
deny > ask > allow
```

这带来两个能力：

1. **冲突裁决有确定顺序**——同优先级多规则命中时取最严（`_match_rules`）；
2. **无审批通道时的降级有明确语义**——`ask` 在「没人能审批」时降级为 `deny` 而非 `allow`（**宁可拒绝，不可放行**）。

## 九、为什么沙箱要「诚实标注」而不是「假装有」

`sandbox.probe()` 返回 `level="policy_only"` 而**不是** `available=False`——因为策略层隔离（路径归一化 + 规则集 + 写前快照 + rlimit）**确实存在并生效**，只是不等于 OS 级隔离。

诚实的标注让调用方能做正确的决策：知道没有 OS 沙箱 → 就不把不可信输入交给执行器；知道有策略层 → 可以放心把「读」类工具放开。

## 十、为什么写文件要有「写前快照」而不是「事后备份」

事后备份无法回答「这个文件之前长什么样」——如果写操作本身损坏了文件，事后备份已经晚了。写前快照（`workspace/snapshots.py`）在**执行之前**拷贝原文件，使得：

- 变更可 diff（`changes` 表记前后哈希 + 快照引用）；
- 变更可回退（`revert()` 从 `snapshot_ref` 恢复，并**再写一条 `op=revert` 记录**保证可追溯）。

快照失败**不阻断写入**（仅告警）——这是有意的取舍：快照是辅助能力，不该成为主流程的单点故障。

## 十一、为什么审计写 JSONL 而不是只写数据库

| 维度 | 数据库 | JSONL |
|---|---|---|
| 追加写 | 需要事务 | 直接 append |
| 人工检索 | 需要 SQL | `grep` / `tail` 即可 |
| 与工作空间同生命周期 | 需另设清理 | 随工作空间归档 |
| 防篡改 | 可被 UPDATE | 纯追加，语义上更「不可变」 |

审计日志的诉求是「**留证据**」而非「做统计」，JSONL 更合适。代价是无法高效做聚合查询。
