# 第一部分 现状事实

## 一、定位与分层

```
domain/security/
├── permissions.ts         # 纯函数判定引擎 decide()：规则匹配 + 信任分层回落
├── policy.ts              # 归一化纯函数：路径 / 命令 / 网络
└── permission-service.ts  # 服务层单例：规则缓存 + 阻塞审批 + 落账 + 事件
```

## 二、权限模型

- **三态**：`allow / ask / deny`；**五作用域**（C25）：`tool / file / command / network / action`；
- 规则行：`{scope, pattern, decision, risk, workspace_id, priority, origin, expires_at,
  hit_count, last_hit_at}`，唯一约束 `(scope, pattern, workspace_id)`；
- **内置规则 18 条**（C32，`BUILTIN_RULES`，`permissions.ts:64`）：
  禁止路径 4（~/.ssh /** 等）+ 危险命令前缀 7（`rm -rf /`、`mkfs`…）+
  只读工具放行 3 + `emit_artifact` 放行 + 写/执行类 ask 3 + 高危动作 3；
- 启动时 `ensureBuiltinRules()` **幂等收敛**（去重保 priority 最小者 + 补齐缺失）；
- 档位聚合：`effectiveLevel()` 对危险工具集（write_file/execute_python/execute_bash）
  取最严 → `readonly / ask / allow`；`setLevel()` 批量写规则。

## 三、判定流程（`decide()`，`permissions.ts:220`）

1. **归一化**（policy.ts）：
   - 路径：`~` 展开 → 绝对化（以 **run 绑定的工作区根**为 cwd）→ realpath → 大小写归一；
   - 命令：去重定向 → POSIX 词法切分（处理引号）→ 按 `;`/`&&`/`||` 拆段，取各段**最严**；
   - 网络：URL → host:port，本地地址直接放行；
2. **高危动作最先判**（`batch_delete`/`system_config_write`/`external_script_exec`，
   不能被「工作区内 allow」放行）；
3. **scope 分流匹配**：同 scope 内 priority 升序 + 最长命中；同优先级冲突
   `deny > ask > allow`；
4. **信任分层回落**（未命中规则时）：
   工作区内路径 allow → 技能目录只读可信根（读类 allow）→ 工作区外写 ask →
   只读工具 allow → 其余 ask（默认询问）；
5. 工具维度的 deny 立即生效（先于文件/命令回落）。

## 五、审批面（`PermissionService`）

### 5.1 阻塞审批机制（机制完整，待执行路径接入）

`enforce()`（`permission-service.ts:299`）：allow → 直返；deny → 落账直返；
ask → 审批通道活跃时**阻塞等待**（`pending` Map + Promise），否则立即拒绝。

- **超时 120s 按 deny**（C22；计时器 `unref` 不阻止进程退出）；
- 用户四种选择：`allow_once`（不落库）/ `allow_session` / `allow_workspace`
  （落一条放行规则）/ 拒绝；
- 决策落 `permission_decisions` 表（pending → resolved，含 latency_ms、decided_by），
  并通过桌面事件总线发 `permission_requested` / `permission_resolved`。

### 5.2 审批通道活性

桌面形态恒活（`settings.desktop_mode` 即真）；否则看最近 10s 是否有人拉取
待审批列表（`noteChannelPoll()`——前端的轮询本身就是心跳）。

### 5.3 无人值守

`setUnattended(true)` 上下文（调度触发）中：ask 一律 deny（任务不挂起等待）；
危险工具另需任务级 `allow_dangerous_tools` 二次开关才放行。

### 5.4 管理端点

`permissions/*`（规则 CRUD + 档位 + 待审批 + 决策提交 + 沙箱实况）与
`desktop/permissions*`（读/改规则、临时决策 once/always/deny——仅 always/deny 落库）。
`recordHit()`（命中计数）当前**无调用方** → `hit_count` 恒 0。

## 六、桌面守卫（HTTP 层）

`http/app.ts:66`：桌面态下 `/api/v1/` 强制会话（401），Host 白名单（421），
静态资源豁免；引导端点免鉴权（否则换不到 Cookie）。详见 `13` §4。

# 第二部分 原理剖析

## 七、为什么权限判定设计在「工具分发」层而不是 HTTP 层

工具调用不经过 HTTP（模型在循环内发起），HTTP 中间件拦不住。
判定引擎因此是纯函数（`decide(request, rules)`），与传输层解耦——
这也让它可以脱离服务单测（契约测试冻结语义）。当前执行路径未接入（见文首
⚠️），设计意图不变，接线属于 `../design/09` 附录（批次）范畴。

## 八、为什么规则用「三态」而不是「布尔允许」

`ask` 是关键态：把「放行/拒绝」之外的第三种可能——**问人**——变成一等语义。
三态让默认姿态可以是「新事物先问」（未知工具/工作区外写默认 ask），
而不是二选一系统里常见的「默认放行」或「默认拒绝」两个极端。
冲突裁决 `deny > ask > allow` 保证最严规则永远赢。

## 九、为什么「审批通道不活跃时 ask 按 deny」

阻塞等待一个永远不会来的审批 = 死等。审批是**交互设施**：
没有审批方时，安全的默认是拒绝。这让同一份规则在交互态（有人看）与
无人值守态（定时任务）下都成立——后者由 `unattended` 上下文显式标记。

## 十、为什么归一化必须是纯函数且与执行器同基准

路径归一化的 cwd 基准必须是 **run 绑定的工作区根**（而不是进程 cwd 或全局
当前空间）——否则运行中切换工作空间会改变判定结果（TOCTOU 类不一致）。
`decide()` 从 `request.workspace_root` 取基准（`permissions.ts:225-231`），
与执行器锁死同一来源（`setCurrentRunContext`）。

# 第三部分 已知边界

1. `enforce()` 无执行路径调用方（见文首 ⚠️）；`classify()` / `recordHit()` 同样无调用方；
2. 沙箱是**策略层 + 进程限额**，非容器隔离；`/permissions/sandbox` 如实返回
   限额与 Python 可用性（`available: true` 指策略层生效）；
3. Windows 无 rlimit 等价物（限额不生效，诚实标注）；
4. 敏感信息扫描回调点预留未挂（§四末行）；
5. `AGENT_API_KEY` 配置位无读取方（Web 形态退场遗留）。
