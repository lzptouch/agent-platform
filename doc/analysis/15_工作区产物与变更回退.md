# 第一部分 现状事实

## 一、定位

工作区是「**一次运行的空间**」：把 Agent 的写操作、产出文件、变更记录、审计日志全部收敛到一个目录，使「跑完之后留下了什么、能不能退回去」有确定答案。

三张表 + 一个目录约定：

| 概念 | 真相源 | 表/路径 |
|---|---|---|
| **工作空间**（容器） | SQLite `workspaces` + 磁盘目录 | `data/wb-YYYYMMDD-xxxxxx/` |
| **变更**（逐文件改了什么） | SQLite `changes` + 快照目录 | `.agent/snapshots/{seq}/` |
| **产物**（交付物清单） | SQLite `artifacts` | `artifacts/` |
| **清单**（工作空间元信息） | 磁盘 `manifest.json` + DB `manifest_json` | `.agent/manifest.json` |

## 二、目录结构约定

`apps/server/src/domain/workspace/manifest.ts:1-13`：

# 第二部分 原理剖析

## 九、为什么「一次运行一个工作空间」而不是「一个项目一个工作空间」

两种模型的差别：

| 模型 | 优点 | 缺点 |
|---|---|---|
| **一个项目一个空间**（长期） | 多次运行共享产物、变更可累积 | 并行运行互相污染；回退语义模糊（回到哪一次？） |
| **一次运行一个空间**（本项目） | 运行之间完全隔离；回退语义明确（回到本次运行前） | 跨运行的产物需要显式「另存」 |

平台选了后者，因为 Agent 运行是**「带副作用的批处理」**——隔离比共享更重要。跨运行的产物汇聚由 `artifacts.save_as()` 显式完成（用户主动触发，不是隐式共享）。

## 十、为什么变更要「逐文件一条记录」而不是「一次运行一条记录」

一次运行可能写 100 个文件。粒度决定能力：

| 粒度 | 能回答的问题 |
|---|---|
| 一次运行一条 | 「这次改了什么？」 |
| **逐文件一条**（本项目） | 「这个文件改了什么？」「把这个文件退回去」「把这次运行的所有改动都退回去」 |

逐文件粒度让「diff 面板」「单文件回退」「批量回退」三种交互都成为可能，代价是 `changes` 表行数与写放大。

## 十一、为什么回退要「写一条 `op=revert` 记录」而不是「删掉原记录」

删掉原记录会让变更历史**失真**——用户看到的是「这个文件从没被改过」，而不是「改过又被退了」。

保留 `op=revert` 记录让历史成为**事实的完整序列**：create → modify → revert。代价是表会累积「已回退」的记录，需要靠 `op` 过滤。

## 十二、为什么快照失败不阻断写入

快照是**辅助能力**（用于 diff 与回退），不是写操作的**前置条件**。如果快照失败就阻断写入，那么一个磁盘空间不足或权限问题会导致 Agent 完全无法工作——而 Agent 写文件往往只是生成中间产物，未必需要回退能力。

「失败只告警」的取舍是：**主流程的可用性优先于辅助能力的完整性**。

## 十三、为什么 `save_as` 的 `dest` 不做路径限制（以及它的代价）

`save_as` 是**用户主动**触发的「把产物存到别处」——目标是用户自己选的目录。限制它反而是多余的。

但这与 `revert` 的策略**不一致**：`revert` 写的是工作区内的工作空间根，受路径限制；`save_as` 可以写系统任意位置。两条写路径的策略差异会在安全评审中被质疑（见 `12` SEC-4）。

## 十四、为什么上传白名单要「禁止清单优先于白名单」

如果先查白名单再查禁止清单，一个同时满足两者的扩展名（同时被白名单允许又被禁止）会因实现顺序而行为不一致。把禁止清单放在**前面**并让它**无条件拒绝**，规则就没有歧义。

同理，`.sh`/`.bash`/`.zsh` 被显式保留（视为源码而非可执行二进制）——但 `BLOCKED_COMMANDS` 在执行侧另有约束。
